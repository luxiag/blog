# Next.js 进阶实战：App Router、缓存分层、Server Actions 与性能治理

很多人学 Next.js，停留在三个点：文件路由、`fetch` 拉数据、部署到 Vercel。

这当然能把项目跑起来，但一旦进入真实业务，你很快会遇到这些问题：

- 为什么同一个页面有的地方应该静态，有的地方又必须动态？
- 为什么我明明调用了 `fetch`，结果数据不刷新，或者刷新得太猛？
- 为什么加了 Server Actions 之后，表单提交简单了，但边界和安全变复杂了？
- 为什么首页 Lighthouse 很高，线上却还是有人反馈“慢”？

这篇文章不讲入门，而是从工程视角，系统拆解 **Next.js 进阶最关键的能力模型**。

---

## 一、先建立正确心智：Next.js 不只是 React 框架

到了 App Router 时代，Next.js 的本质已经不是“React + 路由”这么简单了。

它更像一套整合运行时：

1. **React Server Components（RSC）负责服务端组件树生成**
2. **Route Segment 负责路由级别的渲染边界切分**
3. **Data Cache / Full Route Cache / Router Cache 负责多层缓存**
4. **Server Actions / Route Handlers 负责服务端写操作与接口能力**
5. **Streaming / Suspense 负责把等待时间拆碎，而不是整块阻塞**

如果你还把 Next.js 理解为“SSR 框架”，很多问题会越写越乱。

更准确的理解应该是：

> Next.js 的核心任务，是把页面渲染、数据获取、缓存更新和客户端交互，组织成一条可控的链路。

后面的所有进阶技巧，其实都围绕这条链路展开。

---

## 二、渲染边界：先决定谁在服务端，谁在客户端

很多项目性能差，不是因为算法差，而是**边界切错了**。

### 1. 默认优先使用 Server Component

在 App Router 下，组件默认运行在服务端。只有在真正需要这些能力时，才加 `'use client'`：

- 浏览器事件：点击、输入、拖拽
- 本地状态：`useState`、`useReducer`
- 浏览器 API：`localStorage`、`IntersectionObserver`
- 只能在客户端运行的第三方库

典型错误是把整页都写成 Client Component：

```tsx
'use client'

import { useEffect, useState } from 'react'

export default function DashboardPage() {
  const [stats, setStats] = useState(null)

  useEffect(() => {
    fetch('/api/stats')
      .then((res) => res.json())
      .then(setStats)
  }, [])

  return <div>{stats ? JSON.stringify(stats) : 'loading...'}</div>
}
```

这个写法的问题是：

- 首屏 HTML 信息量低
- 需要额外下载客户端 JS 才能开始拉数据
- 接口链路变成“浏览器 -> API -> 服务端 -> 数据源”
- 更难利用服务端缓存和流式渲染

更合理的方式是把数据读取放到 Server Component：

```tsx
async function getStats() {
  const res = await fetch('https://api.example.com/stats', {
    next: { revalidate: 300 },
  })

  if (!res.ok) {
    throw new Error('Failed to fetch stats')
  }

  return res.json()
}

export default async function DashboardPage() {
  const stats = await getStats()

  return <div>{JSON.stringify(stats)}</div>
}
```

这时链路变成：

- 服务端直接拿数据
- 首屏直接生成带内容的 HTML / RSC Payload
- 缓存策略可以集中在服务端控制

### 2. Client Component 应该像“岛屿”而不是“大陆”

一个成熟项目里，Client Component 更适合做这些事：

- 搜索框
- 筛选面板
- 图表交互
- 富文本编辑器
- 动画与手势

也就是说：**把交互做成局部岛屿，把数据和结构尽可能留在服务端。**

例如：

```tsx
import SearchBox from './SearchBox'
import ProductTable from './ProductTable'

export default async function ProductsPage({
  searchParams,
}: {
  searchParams: Promise<{ keyword?: string }>
}) {
  const { keyword = '' } = await searchParams
  const products = await getProducts(keyword)

  return (
    <>
      <SearchBox initialKeyword={keyword} />
      <ProductTable products={products} />
    </>
  )
}
```

这里 `SearchBox` 负责交互，`ProductTable` 和页面结构仍然由服务端输出。

这类分层，往往比一味做 CSR 更稳。

## 三、缓存分层：Next.js 真正难的不是渲染，而是“什么时候该更新”

很多人第一次碰 App Router 会觉得“玄学”，本质上是没有把缓存层次分清。

你至少要知道三层：

### 1. Data Cache：`fetch` 结果缓存

这是最常见的一层。

```tsx
await fetch('https://api.example.com/posts', {
  next: { revalidate: 600 },
})
```

这表示：

- 请求结果会被缓存
- 在 600 秒内复用缓存
- 过期后由下一次请求触发重新验证

适合：

- CMS 内容
- 商品列表
- 文章详情
- 不要求每次都绝对实时的数据

### 2. Full Route Cache：整个路由结果缓存

如果页面是静态可缓存的，Next.js 会缓存整个路由渲染结果。

这意味着不只是接口数据，连页面产物本身都可能被复用。

所以你需要清楚：

- `revalidate` 不只影响一次 `fetch`
- 它会影响整个页面段的静态化与更新时机

例如：

```tsx
export const revalidate = 300

export default async function BlogPage() {
  const posts = await getPosts()
  return <PostList posts={posts} />
}
```

这是路由级别的 ISR 思维，而不是单接口思维。

### 3. Router Cache：客户端路由缓存

用户在前端跳转时，Next.js 还会缓存部分 RSC 结果，提升返回上一级或二次访问的速度。

这层缓存经常导致一个错觉：

> “我明明服务端数据更新了，为什么前端还没看到？”

这时你就要联想到：

- 是不是客户端路由缓存还在
- 是否需要 `router.refresh()`
- 是否应该在写操作后触发 `revalidatePath()` 或 `revalidateTag()`

## 四、不要只会 `revalidatePath`，要学会标签化失效

中大型项目里，如果你每次写入后都简单粗暴 `revalidatePath('/dashboard')`，很快会遇到两个问题：

- 刷新范围太大
- 失效逻辑和业务实体耦合得太死

更可维护的方式是：**给数据打标签，用标签驱动缓存失效。**

### 1. 读取时打标签

```tsx
async function getPost(id: string) {
  const res = await fetch(`https://api.example.com/posts/${id}`, {
    next: {
      tags: [`post:${id}`, 'posts'],
      revalidate: 3600,
    },
  })

  if (!res.ok) {
    throw new Error('Failed to fetch post')
  }

  return res.json()
}
```

### 2. 写入后按标签失效

```tsx
'use server'

import { revalidateTag } from 'next/cache'

export async function updatePost(id: string, input: FormData) {
  await fetch(`https://api.example.com/posts/${id}`, {
    method: 'PATCH',
    body: JSON.stringify({
      title: input.get('title'),
    }),
    headers: {
      'Content-Type': 'application/json',
    },
  })

  revalidateTag(`post:${id}`)
  revalidateTag('posts')
}
```

这种设计的好处是：

- 列表和详情可以独立控制
- 页面路径变化时，不用大面积改失效代码
- 更符合“按资源建模”，而不是“按页面建模”

当项目变复杂时，`tag` 比 `path` 更像一套长期可维护的缓存协议。

## 五、Server Actions 的价值，不只是“少写一个接口”

很多人理解 Server Actions，只停留在：

> “哦，就是表单可以直接调服务端函数。”

这太浅了。

它更大的价值在于：**把 UI 提交、服务端写入、缓存失效和重定向，压缩到一个闭环里。**

### 1. 一个典型闭环

```tsx
'use server'

import { redirect } from 'next/navigation'
import { revalidateTag } from 'next/cache'

export async function createPost(formData: FormData) {
  const title = String(formData.get('title') || '').trim()

  if (!title) {
    throw new Error('Title is required')
  }

  const res = await fetch('https://api.example.com/posts', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
    },
    body: JSON.stringify({ title }),
  })

  if (!res.ok) {
    throw new Error('Failed to create post')
  }

  const post = await res.json()

  revalidateTag('posts')
  redirect(`/posts/${post.id}`)
}
```

这个流程里已经包含了：

- 输入接收
- 服务端校验
- 数据落库
- 缓存失效
- 页面跳转

过去这些动作通常要拆在：前端提交函数、API Route、service 层、页面刷新逻辑里。

### 2. 但它也带来了新的工程要求

使用 Server Actions 时，必须注意：

- 不要把它当成“无成本 RPC”
- 参数必须显式校验，不能直接信任 `FormData`
- 权限校验必须在服务端内部做，而不是依赖前端按钮隐藏
- 不要在 Action 里混入过多领域逻辑，复杂逻辑仍应下沉到 service 层

一个更稳的结构是：

```tsx
'use server'

import { createPostService } from '@/lib/services/post-service'
import { revalidateTag } from 'next/cache'

export async function createPostAction(formData: FormData) {
  const result = await createPostService({
    title: String(formData.get('title') || ''),
  })

  revalidateTag('posts')

  return result
}
```

也就是说：

- **Action 负责接入层**
- **Service 负责业务层**

这和后端分层思维并不冲突，反而更重要。

## 六、Streaming 和 Suspense：不要等整页准备完才输出

传统 SSR 的问题是“整页阻塞”。

比如一个页面要等：

- 用户信息 80ms
- 推荐列表 300ms
- 图表数据 1200ms

如果你把它们串成一个大 `await`，用户会一直等到最慢的那个请求结束。

### 1. 用 Suspense 拆等待时间

```tsx
import { Suspense } from 'react'

export default function DashboardPage() {
  return (
    <main>
      <UserSummary />

      <Suspense fallback={<div>Loading chart...</div>}>
        <SalesChart />
      </Suspense>

      <Suspense fallback={<div>Loading recommendations...</div>}>
        <Recommendations />
      </Suspense>
    </main>
  )
}
```

如果 `SalesChart` 很慢，页面仍然可以先把：

- 页面骨架
- 用户摘要
- 其它较快模块

提前流式输出给浏览器。

### 2. `loading.tsx` 是路由级的第一层体验兜底

在 segment 下定义 `loading.tsx`，可以让路由切换时立即显示过渡 UI。

适合：

- 页面级 skeleton
- 大块布局壳子
- 首次切换反馈

而 `Suspense` 更适合做页面内部的细粒度拆分。

经验上可以这样分工：

- `loading.tsx` 负责“这个页面正在来”
- `Suspense` 负责“这个局部内容还在来”

## 七、错误处理：不要让异常一路炸到最外层

真实项目里，比“请求失败”更重要的是**失败后用户看到什么**。

App Router 提供了天然的分段错误边界：

- `error.tsx`：当前 segment 的错误边界
- `not-found.tsx`：资源不存在时的专用出口

### 1. 对业务错误和系统错误分开处理

例如文章详情：

```tsx
import { notFound } from 'next/navigation'

export default async function PostDetailPage({
  params,
}: {
  params: Promise<{ id: string }>
}) {
  const { id } = await params
  const post = await getPost(id)

  if (!post) {
    notFound()
  }

  return <article>{post.title}</article>
}
```

这里：

- “没有这篇文章” 是业务意义上的不存在，应该走 `notFound()`
- “数据库连接失败” 是系统错误，应该让 `error.tsx` 接住

这两个不要混。

### 2. `error.tsx` 不只是展示报错文案

一个合格的 `error.tsx` 至少应该支持：

- 用户可理解的错误提示
- 重试按钮
- 开发环境详细信息 / 生产环境收敛信息
- 与日志系统对接

否则它只是把“白屏”换成了“另一种白屏”。

## 八、性能治理：不要只看包体积，要看链路总成本

前端项目常见误区是只盯着 JS bundle 大小，但 Next.js 项目的真实性能成本至少包括：

- 服务端数据等待
- RSC 负载大小
- 客户端 hydration 成本
- 第三方脚本阻塞
- 图片、字体和样式资源体积
- 路由切换时的重新获取与重新渲染

### 1. 先减少不必要的客户端 JS

最有效的方法通常不是 `memo`，而是：

- 能放服务端的别放客户端
- 能局部 `use client` 的别整页 `use client`
- 交互组件按需下沉，不要把父层也拖成客户端

这是 Next.js 里性价比最高的优化。

### 2. 重型组件做动态加载

例如图表、编辑器、地图：

```tsx
import dynamic from 'next/dynamic'

const Editor = dynamic(() => import('./Editor'), {
  ssr: false,
  loading: () => <div>Loading editor...</div>,
})
```

适合：

- 明确依赖浏览器 API
- 首屏不需要出现
- 包体积明显偏大的模块

但不要滥用。对于首屏核心内容，强行 dynamic 只会把问题从“首屏下载”变成“首屏空白等待”。

### 3. 图片优化要服务于 LCP

首屏主视觉图、文章头图、商品主图，应该围绕 LCP 设计：

- 明确尺寸，避免布局抖动
- 对核心图使用更积极的加载策略
- 非首屏图延迟加载
- 避免一上来塞满大图轮播

优化图片的目标不是“工具分数高”，而是让用户更快看见核心内容。

### 4. 第三方脚本要分级管理

埋点、客服、AB 实验、热图工具，经常是 Next.js 项目真实线上性能劣化的元凶。

要建立最基础的分级规则：

- 首屏必须用到的脚本，才考虑尽早执行
- 统计类脚本尽量延后
- 可选功能尽量懒加载
- 定期审查是否仍然需要

你优化了 20KB 业务代码，却引入 300KB 第三方脚本，基本等于白做。

## 九、Route Handlers、Server Actions、外部 BFF，怎么选？

这是进阶项目里经常争论的问题。

我的经验是按职责选，而不是按潮流选。

### 1. 用 Server Actions 的场景

适合：

- 与页面强绑定的表单提交
- 单步写操作
- 提交后立刻刷新当前数据或跳转
- 希望减少样板代码

例如：创建文章、更新昵称、提交评论。

### 2. 用 Route Handlers 的场景

适合：

- 需要标准 HTTP API 能力
- Webhook
- 文件上传
- 对外提供接口
- 需要被移动端、第三方系统或独立前端消费

例如：`app/api/upload/route.ts`、支付回调、机器人回调。

### 3. 用外部 BFF / 独立后端的场景

适合：

- 领域逻辑复杂
- 多端共享服务
- 权限和审计要求高
- 团队前后端边界明确
- 有独立部署、扩容、观测要求

不要为了“全栈一体化”把所有业务硬塞进 Next.js。

Next.js 很强，但它不是所有后端架构问题的唯一答案。

## 十、一个推荐的工程组织方式

进阶项目中，我更推荐下面这种分层：

```text
app/
  dashboard/
    page.tsx
    loading.tsx
    error.tsx
    actions.ts

components/
  dashboard/
    SearchBox.tsx
    StatsPanel.tsx

lib/
  services/
    dashboard-service.ts
  repositories/
    dashboard-repository.ts
  validations/
    dashboard.ts
```

职责大致如下：

- `app/**/page.tsx`：路由入口、组合页面结构
- `app/**/actions.ts`：Server Actions 接入层
- `components/**`：UI 组件
- `lib/services/**`：业务编排
- `lib/repositories/**`：数据访问
- `lib/validations/**`：输入校验

这个结构的重点不是“目录长得漂亮”，而是让你在规模变大后仍然知道：

- 哪些代码依赖运行时
- 哪些代码属于业务核心
- 哪些代码只是页面装配

## 十一、几个常见误区

### 误区 1：把所有请求都放进客户端 `useEffect`

后果通常是：

- 首屏慢
- SEO 弱
- 重复请求多
- 缓存难统一

### 误区 2：把所有组件都写成 Client Component

这会让 App Router 最大的性能优势直接蒸发。

### 误区 3：写操作后只会 `router.refresh()`

`router.refresh()` 能用，但很多时候太粗。
更好的做法是结合 `revalidateTag()` 建立可维护的失效模型。

### 误区 4：Server Actions 里直接塞所有业务逻辑

短期省事，长期难测、难复用、难维护。

### 误区 5：只看 Lighthouse，不看真实用户体验

实验室数据重要，但真实线上更重要。你最终要关心的是：

- 首屏核心内容多久可见
- 交互是否及时响应
- 弱网和中低端设备是否可用
- 数据更新是否稳定、可预期

---

## 十二、总结：真正的 Next.js 进阶，是“控制复杂度”

当你从入门走向进阶，会发现 Next.js 难的地方从来不是 API 数量，而是这些控制能力：

1. **控制渲染边界**：服务端和客户端各做什么
2. **控制缓存边界**：数据什么时候复用，什么时候失效
3. **控制写入链路**：提交、校验、落库、刷新如何闭环
4. **控制等待体验**：哪些内容先出来，哪些内容后出来
5. **控制工程复杂度**：页面代码、业务逻辑、数据访问如何分层

如果你把这五件事想清楚，Next.js 就不再只是“一个能写 React 的全栈框架”，而会变成一套非常强的 Web 应用交付系统。

下一次你再审视自己的项目时，可以先问四个问题：

- 这个组件真的必须在客户端吗？
- 这个数据到底应该缓存多久？
- 这次写操作触发的失效范围是不是过大？
- 这个页面的等待时间，能不能被流式拆开？

当你开始用这四个问题审查代码，你就已经进入 Next.js 的进阶阶段了。

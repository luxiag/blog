# HTTP 与 RESTful API 基础：ASP.NET Core 开发前置知识

ASP.NET Core Web API 处理的是 HTTP 请求。如果不理解 HTTP，就很容易把 API 设计成“能跑但不清晰”的远程方法调用。

这篇文章先不讲 ASP.NET Core API，而是讲 Web API 开发必须知道的 HTTP 和 RESTful 基础。

## HTTP 请求由什么组成

一个 HTTP 请求通常包含：

- Method：请求方法，例如 `GET`、`POST`
- URL：请求地址，例如 `/api/products/1`
- Query String：查询字符串，例如 `?page=1&pageSize=20`
- Headers：请求头，例如 `Content-Type`、`Authorization`
- Body：请求体，常见是 JSON

示例请求：

```http
POST /api/products HTTP/1.1
Host: example.com
Content-Type: application/json
Authorization: Bearer <token>

{
  "name": "Keyboard",
  "price": 199
}
```

ASP.NET Core 的参数绑定，就是把这些位置的数据绑定到 Action 参数或 DTO 上。

## HTTP 响应由什么组成

HTTP 响应通常包含：

- Status Code：状态码，例如 `200`、`404`
- Headers：响应头，例如 `Content-Type`
- Body：响应体，常见是 JSON

示例响应：

```http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/products/1

{
  "id": 1,
  "name": "Keyboard",
  "price": 199
}
```

状态码是 API 设计的一部分，不要所有结果都返回 `200`。

## 常用 HTTP 方法

| 方法 | 语义 | 示例 |
|---|---|---|
| `GET` | 查询资源 | `GET /api/products` |
| `POST` | 创建资源或提交动作 | `POST /api/products` |
| `PUT` | 整体更新资源 | `PUT /api/products/1` |
| `PATCH` | 局部更新资源 | `PATCH /api/products/1` |
| `DELETE` | 删除资源 | `DELETE /api/products/1` |

建议按资源语义设计 API，而不是把动词都塞进 URL。

```text
推荐：GET /api/products/1
不推荐：GET /api/getProductById?id=1

推荐：POST /api/products
不推荐：POST /api/createProduct
```

## 常用状态码

| 状态码 | 含义 | 常见场景 |
|---|---|---|
| `200 OK` | 请求成功 | 查询成功、更新成功并返回内容 |
| `201 Created` | 创建成功 | 创建资源成功 |
| `204 No Content` | 成功但无响应体 | 删除成功、更新成功不返回内容 |
| `400 Bad Request` | 请求不合法 | 参数格式错误、模型验证失败 |
| `401 Unauthorized` | 未认证 | 没有登录或 Token 无效 |
| `403 Forbidden` | 无权限 | 已登录但权限不足 |
| `404 Not Found` | 资源不存在 | 商品 ID 不存在 |
| `409 Conflict` | 状态冲突 | 重复提交、并发冲突 |
| `500 Internal Server Error` | 服务器错误 | 未处理异常 |

ASP.NET Core Controller 中可以直接返回这些语义：

```csharp
return Ok(product);
return CreatedAtAction(nameof(GetById), new { id = product.Id }, product);
return NoContent();
return BadRequest();
return NotFound();
return Conflict();
```

## Header 的作用

Header 用来描述请求或响应的元信息。

常见请求头：

| Header | 作用 |
|---|---|
| `Content-Type` | 请求体格式，例如 `application/json` |
| `Accept` | 客户端期望的响应格式 |
| `Authorization` | 认证信息，例如 Bearer Token |
| `User-Agent` | 客户端信息 |
| `Origin` | 跨域请求来源 |

常见响应头：

| Header | 作用 |
|---|---|
| `Content-Type` | 响应体格式 |
| `Location` | 新资源地址，常配合 `201 Created` |
| `Cache-Control` | 缓存策略 |
| `Set-Cookie` | 设置 Cookie |

## Cookie

Cookie 是浏览器自动携带的小块数据，常用于认证和会话管理。

服务端通过 `Set-Cookie` 响应头设置 Cookie：

```http
HTTP/1.1 200 OK
Set-Cookie: session_id=abc123; Path=/; HttpOnly; Secure; SameSite=Strict
```

浏览器之后对同一域的请求会自动带上：

```http
GET /api/orders HTTP/1.1
Cookie: session_id=abc123
```

Cookie 关键属性：

| 属性 | 作用 |
|---|---|
| `HttpOnly` | JavaScript 无法读取，防止 XSS 窃取 |
| `Secure` | 只在 HTTPS 下传输 |
| `SameSite` | 控制跨站请求是否携带，防止 CSRF |
| `Path` | Cookie 生效的路径范围 |
| `Expires / Max-Age` | 过期时间 |

Web API 认证中，Cookie 和 JWT 是两种常见方案。Cookie 由浏览器自动管理，JWT 需要前端手动存储和携带。

## CORS

前后端分离时，前端（`https://app.example.com`）和后端 API（`https://api.example.com`）不同源，浏览器会阻止跨域请求。这叫同源策略。

CORS（Cross-Origin Resource Sharing）是浏览器和服务器协商跨域访问的机制。

### 同源策略判定规则

浏览器判定两个 URL 是否同源，比较三个部分：**协议**、**域名**、**端口**。三者完全一致才算同源。

| URL A | URL B | 是否同源 | 原因 |
|---|---|---|---|
| `https://example.com/api` | `https://example.com/users` | 同源 | 协议、域名、端口一致 |
| `https://example.com` | `http://example.com` | 不同源 | 协议不同 |
| `https://example.com` | `https://api.example.com` | 不同源 | 域名不同 |
| `https://example.com` | `https://example.com:8080` | 不同源 | 端口不同（默认 443 vs 8080） |

不同源的请求默认会被浏览器拦截（响应被丢弃，请求根本到不了 JS），不是服务端拒绝。

### 简单请求与预检请求

浏览器对跨域请求分两种处理方式：

**简单请求**满足以下所有条件：

- Method 是 `GET`、`HEAD`、`POST` 之一
- Content-Type 只能是 `application/x-www-form-urlencoded`、`multipart/form-data`、`text/plain`
- 不携带自定义 Header（如 `Authorization`、`X-Custom-Header`）

简单请求直接发送，浏览器在响应中检查 `Access-Control-Allow-Origin`：

```http
GET /api/products HTTP/1.1
Origin: https://app.example.com
```

```http
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://app.example.com
Content-Type: application/json
```

如果响应缺少 `Access-Control-Allow-Origin` 或值不匹配，浏览器会丢弃响应。

**预检请求**（Preflight）：不满足简单请求条件时，浏览器先发 `OPTIONS` 请求询问服务器是否允许跨域：

```http
OPTIONS /api/products HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: GET
```

服务器响应允许：

```http
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Authorization, Content-Type
Access-Control-Allow-Credentials: true
```

ASP.NET Core 中配置 CORS：

```csharp
builder.Services.AddCors(options =>
{
    options.AddPolicy("AllowApp", policy =>
    {
        policy.WithOrigins("https://app.example.com")
              .AllowAnyHeader()
              .AllowAnyMethod()
              .AllowCredentials();
    });
});

app.UseCors("AllowApp");
```

注意：

- 不要用 `AllowAnyOrigin()` + `AllowCredentials()`，浏览器不允许。
- `UseCors()` 要放在 `UseRouting()` 之后、`UseAuthentication()` 之前。
- 生产环境必须明确指定允许的源。

## HTTPS

HTTPS = HTTP + TLS 加密。生产环境必须使用 HTTPS：

- 防止请求和响应被窃听。
- 防止请求被篡改（中间人攻击）。
- Cookie 和 JWT 在 HTTPS 下才安全传输。
- 很多浏览器 API（如 Service Worker、Geolocation）只允许 HTTPS 环境。

ASP.NET Core 默认启用 HTTPS 重定向：

```csharp
app.UseHttpsRedirection();
```

生产环境还应启用 HSTS，告诉浏览器始终使用 HTTPS：

```csharp
if (!app.Environment.IsDevelopment())
{
    app.UseHsts();
}
```

## RESTful API 的核心思想

### REST 的核心约束

REST（Representational State Transfer）定义了一组架构约束：

| 约束 | 含义 |
|---|---|
| **客户端-服务端分离** | 前端和后端独立演进，通过统一接口通信 |
| **无状态** | 每个请求必须包含所有必要信息，服务端不保存客户端上下文 |
| **统一接口** | 用相同的语义操作不同资源：GET 查询、POST 创建、PUT 更新、DELETE 删除 |
| **分层系统** | 客户端不知道它连的是终端服务器还是中间代理 |
| **按需代码**（可选） | 服务端可以返回可执行代码（如 JavaScript） |

其中**无状态**和**统一接口**对 API 设计影响最大：

- **无状态**意味着请求不能依赖之前的请求状态。JWT 放在每次请求的 Header 里，而不是靠服务端 Session 记住客户端，就是无状态设计的体现。
- **统一接口**意味着用 HTTP Method 表达操作语义，用 URL 标识资源，而不是在 URL 里写动词。

### REST 与 RPC 风格对比

| 风格 | 设计思路 | 示例 |
|---|---|---|
| **RPC** | 围绕动作设计，URL 是方法名 | `POST /api/createProduct`、`POST /api/getProductById` |
| **REST** | 围绕资源设计，Method 是动作 | `POST /api/products`、`GET /api/products/1` |

RPC 风格的问题：

```text
POST /api/createProduct
POST /api/updateProduct
POST /api/deleteProduct
POST /api/getProductById
POST /api/searchProducts
```

所有操作都是 POST，丢失了 HTTP Method 的语义。客户端只能从 URL 路径判断意图，缓存、幂等性等 HTTP 特性无法利用。

REST 风格对同一资源的所有操作：

```text
POST   /api/products       → 创建
GET    /api/products        → 列表
GET    /api/products/1      → 详情
PUT    /api/products/1      → 更新
DELETE /api/products/1      → 删除
```

Method 本身就表达了意图，URL 只标识资源。GET 请求天然可缓存，PUT 和 DELETE 天然幂等，这些是 RPC 风格无法获得的。

并非所有场景都适合 REST。执行远程命令、触发复杂业务流程（如 `POST /api/orders/1/cancel`）时，RPC 风格的 URL 更清晰。实际项目中 REST 和 RPC 混合使用是常见做法。

RESTful API 的重点不是“URL 好看”，而是围绕资源设计接口。

资源示例：

- 商品：`/api/products`
- 订单：`/api/orders`
- 用户：`/api/users`

针对商品资源的 API：

| 方法 | 路径 | 含义 |
|---|---|---|
| `GET` | `/api/products` | 商品列表 |
| `GET` | `/api/products/1` | 商品详情 |
| `POST` | `/api/products` | 创建商品 |
| `PUT` | `/api/products/1` | 更新商品 |
| `DELETE` | `/api/products/1` | 删除商品 |

## Query、Route、Body 怎么选

| 位置 | 适合放什么 | 示例 |
|---|---|---|
| Route | 资源身份 | `/api/products/1` |
| Query | 筛选、排序、分页 | `?page=1&pageSize=20` |
| Body | 复杂输入数据 | JSON 创建商品请求 |
| Header | 元信息、认证信息 | `Authorization` |

示例：

```http
GET /api/products?keyword=keyboard&page=1&pageSize=20
```

```http
POST /api/products
Content-Type: application/json

{
  "name": "Keyboard",
  "price": 199
}
```

## 一个标准商品 API 设计

```text
GET    /api/products?keyword=keyboard&page=1&pageSize=20
GET    /api/products/{id}
POST   /api/products
PUT    /api/products/{id}
DELETE /api/products/{id}
```

创建商品请求：

```json
{
  "name": "Keyboard",
  "price": 199,
  "stock": 50
}
```

商品响应：

```json
{
  "id": 1,
  "name": "Keyboard",
  "price": 199,
  "stock": 50
}
```

## 总结

ASP.NET Core Web API 的所有高级能力，最终都会落到 HTTP 请求和响应上。先掌握 Method、URL、Header、Body、Status Code、REST 核心约束与 RPC 对比、同源策略与 CORS 机制，再学习 Controller、参数绑定、认证授权和异常处理，会更清晰。

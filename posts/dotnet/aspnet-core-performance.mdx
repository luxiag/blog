# ASP.NET Core 性能优化：异步、连接池、压缩、缓存与诊断工具

性能优化不是看到哪里慢就随手加缓存。正确路径应该是：先测量，再定位瓶颈，最后选择合适手段优化。

ASP.NET Core 常见性能瓶颈包括数据库查询、外部 HTTP 调用、同步阻塞、过度序列化、缓存缺失、线程池耗尽和资源限制。

:::tip 阶段四阅读顺序
建议先掌握 [EF Core](/posts/dotnet/aspnet-core-ef-core)、[缓存](/posts/dotnet/aspnet-core-caching)、[HttpClientFactory](/posts/dotnet/aspnet-core-httpclient-factory) 和 [可观测性](/posts/dotnet/aspnet-core-observability)。
:::

## 先测量再优化

优化前先回答：

- 哪个接口慢？
- P50、P95、P99 延迟是多少？
- 慢在数据库、外部 HTTP、CPU 还是锁等待？
- 错误率是否升高？
- 是否只有高峰期慢？

没有指标的优化通常只是猜测。

## 异步 I/O

Web API 中数据库、HTTP、文件、队列调用都应该使用异步 API。

推荐：

```csharp
var products = await dbContext.Products
    .AsNoTracking()
    .ToListAsync(cancellationToken);
```

不推荐：

```csharp
var products = dbContext.Products.ToList();
```

更不要在异步代码里使用 `.Result` 或 `.Wait()` 阻塞。

## EF Core 查询优化

常见建议：

- 只读查询使用 `AsNoTracking()`。
- 列表接口必须分页。
- 使用 `Select` 投影 DTO。
- 避免过度 `Include`。
- 避免 N+1 查询。
- 给常用查询条件建立数据库索引。

示例：

```csharp
var result = await dbContext.Products
    .AsNoTracking()
    .Where(p => p.CategoryId == categoryId)
    .OrderBy(p => p.Id)
    .Skip((page - 1) * pageSize)
    .Take(pageSize)
    .Select(p => new ProductDto(p.Id, p.Name, p.Price))
    .ToListAsync(cancellationToken);
```

## HttpClientFactory

外部 HTTP 调用要设置超时和取消。

```csharp
builder.Services.AddHttpClient<IWeatherClient, WeatherClient>(client =>
{
    client.BaseAddress = new Uri("https://api.example.com");
    client.Timeout = TimeSpan.FromSeconds(5);
});
```

慢接口经常不是自己慢，而是下游服务慢。必须记录外部调用耗时。

## 缓存

缓存适合读多写少的数据：

- 商品详情
- 字典数据
- 权限列表
- 外部接口响应

不要缓存强一致性要求很高的数据。缓存必须设计 Key、过期时间和失效策略。

## 响应压缩

启用响应压缩：

```csharp
builder.Services.AddResponseCompression();

app.UseResponseCompression();
```

响应压缩适合文本类响应，例如 JSON、HTML、CSS、JS。对小响应或已经压缩的图片、视频收益不大。

## 限流保护

限流不是性能优化本身，但能保护系统不被突发流量打垮。

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.AddFixedWindowLimiter("fixed", limiterOptions =>
    {
        limiterOptions.PermitLimit = 100;
        limiterOptions.Window = TimeSpan.FromMinutes(1);
    });
});

app.UseRateLimiter();
```

## dotnet-counters

`dotnet-counters` 可以查看运行时指标。

```bash
dotnet-counters monitor --process-id <pid>
```

关注：

- CPU Usage
- GC Heap Size
- Gen 0/1/2 GC Count
- ThreadPool Queue Length
- Exception Count

## dotnet-trace

采集 Trace：

```bash
dotnet-trace collect --process-id <pid>
```

适合进一步分析 CPU、锁等待、运行时事件。

## 数据库连接池

ADO.NET 和 EF Core 底层使用连接池，默认配置通常够用，但高并发场景需要调优。

关键配置（连接字符串中）：

| 参数 | 默认值 | 说明 |
|---|---|---|
| `Max Pool Size` | 100 | 最大连接数 |
| `Min Pool Size` | 0 | 最小保持连接数 |
| `Connection Timeout` | 15s | 获取连接超时 |
| `Connection Lifetime` | 0 | 连接最大存活时间（0 为无限） |

```text
Server=db;Database=AppDb;User Id=app;Password=***;Max Pool Size=200;Min Pool Size=5
```

连接耗尽的典型表现：

- 请求超时，错误日志出现 `Timeout expired`
- 连接池等待队列增长
- `dotnet-counters` 中 `ThreadPool Queue Length` 升高

EF Core 还需要注意：

- `DbContext` 默认不是连接池，每个请求一个实例（Scoped）
- `DbContextPool` 可以复用 `DbContext` 实例，减少初始化开销

```csharp
builder.Services.AddDbContextPool<AppDbContext>(options =>
    options.UseSqlServer(connectionString), poolSize: 128);
```

`AddDbContextPool` 比 `AddDbContext` 在高频请求场景下性能更好。

## BenchmarkDotNet

性能优化不能靠感觉。BenchmarkDotNet 是 .NET 基准测试标准工具，能消除 JIT、GC 等运行时干扰，给出稳定的测量结果。

安装：

```bash
dotnet add package BenchmarkDotNet
```

示例 — 对比字符串拼接方式：

```csharp
[MemoryDiagnoser]
public class StringConcatBenchmark
{
    private const int Count = 100;

    [Benchmark(Baseline = true)]
    public string StringConcat()
    {
        string result = "";
        for (int i = 0; i < Count; i++)
        {
            result += i.ToString();
        }
        return result;
    }

    [Benchmark]
    public string StringBuilder()
    {
        var sb = new StringBuilder();
        for (int i = 0; i < Count; i++)
        {
            sb.Append(i.ToString());
        }
        return sb.ToString();
    }
}
```

运行：

```bash
dotnet run -c Release
```

必须在 Release 模式运行，Debug 模式结果不可信。

输出示例：

```text
| Method         | Mean     | Allocated |
|--------------- |---------:|----------:|
| StringConcat   | 3.450 us |  12.5 KB  |
| StringBuilder  | 0.820 us |   0.5 KB  |
```

常见使用场景：

- 对比多种实现方式的性能和内存分配
- 验证缓存是否真的有效
- 评估序列化库选型
- 测试新版本升级后的性能回归

## 性能优化清单

- 先通过指标定位瓶颈。
- 数据库查询先看 SQL 和索引。
- 外部 HTTP 调用必须有超时。
- 不要同步阻塞异步调用。
- 只读查询加 `AsNoTracking()`。
- 列表接口分页。
- 热点读使用缓存。
- 大响应考虑压缩。
- 高流量接口考虑限流。
- 用 OpenTelemetry 记录链路和耗时。

## 总结

ASP.NET Core 性能优化的核心是测量、定位、验证。不要先入为主地加缓存或改代码。先通过日志、指标、链路追踪和诊断工具找到瓶颈，再针对数据库、HTTP、缓存、序列化、线程池等方向优化。

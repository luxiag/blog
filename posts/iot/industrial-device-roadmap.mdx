# .NET 对接工业设备路线图：地磅、摄像头、门禁

"智慧园区""无人值守称重""一卡通"这类项目，技术上都属于同一件事：**用 .NET 对接厂区内网里的工业现场设备**。

这个方向的中文资料质量普遍不高，大多是"能跑但不能维护"的 Demo：串口直接在 `DataReceived` 里解析、厂商 SDK 调用散落在按钮点击事件里、没有断线重连、没有原始报文留存。真上了现场，一次断电、一次网络抖动、一次电磁干扰，系统就开始出玄学问题，而你连排查的证据都没有。

这个系列想解决的就是这件事：**不只是"跑通"，而是能扛住现场、能长期维护。**

## 这类项目和其他方向的区别

如果你之前做的是 Web 后端或云端 IoT，要先调整几个预期：

| 维度 | 云端 IoT / Web 后端 | 工业设备对接 |
|---|---|---|
| 部署位置 | 云服务器 | 厂区内网的一台工控机 |
| 设备接口 | MQTT、HTTP、REST | 厂商 C/C++ SDK、串口、私有 TCP 协议 |
| 主要难点 | 高并发、海量连接 | 设备互操作、流程状态机、现场可靠性 |
| 网络环境 | 稳定，可假设联网 | 会断，断了业务也得继续 |
| 调试方式 | 本地随便跑 | 现场机会极少，必须靠模拟器 |
| 出错代价 | 重启一下 | 过磅涉及钱、门禁涉及责任，要留证据 |

最需要转变的一点：**在这里，"能连上设备"只是起点，"设备不可靠时系统还正确"才是工程量所在。**

:::note 如果你要做的是云端 IoT
上表右列（MQTT 接入、海量设备、时序数据）那条线在 [云端 IoT 平台路线图](/posts/iot/cloud-iot-roadmap)，技术栈和本系列几乎不重叠。

实际项目里两条线经常同时出现：边缘侧用本系列的方式对接现场设备，再通过 MQTT 把数据送上云。
:::

## 读完这个系列你应该能回答

- 串口的波特率、数据位、停止位、校验位分别影响什么，配错会出现什么现象
- 为什么串口和 TCP 都必须自己拆帧，三种定界方式各自适用什么协议
- Modbus 手册上写的 40001，为什么报文里要填 0
- 为什么 RS485 总线上不能并发请求，几十台设备该怎么轮询调度
- 称重仪表的示数为什么不能直接用，"判稳"到底在判什么
- 厂商只给 C++ DLL 时，怎么用 P/Invoke 正确映射结构体和回调，为什么回调会随机崩溃
- 为什么厂商 SDK 经常报 `BadImageFormatException`
- 摄像头需求分几类，什么时候用 RTSP、什么时候用 ISAPI、什么时候才值得写 SDK 互操作
- 门禁对接的真正难点为什么是"数据下发同步"而不是"开门"
- 设备适配层怎么分，才能在换品牌时不重写业务代码
- 没有现场设备时，怎么在本地把整套流程调通

## 前置知识

这个系列假设你已经掌握 C# 基础和 ASP.NET Core 的宿主模型。下面这几篇如果没读过，建议先补，因为后面会反复用到：

- [C# async/await 异步编程](/posts/dotnet/csharp-async-await) —— 设备通信全是 IO 等待，同步阻塞写法会把线程池打死
- [依赖注入](/posts/dotnet/aspnet-core-dependency-injection) —— 设备适配层靠 DI 做品牌切换，`BackgroundService` 里取 Scoped 服务是必修的坑
- [后台服务 BackgroundService](/posts/dotnet/aspnet-core-background-service) —— 所有设备采集循环的载体
- [日志](/posts/dotnet/aspnet-core-logging) —— 现场排查唯一的抓手
- [配置与 Options](/posts/dotnet/aspnet-core-options) —— 设备参数（端口、IP、品牌）必须外置

## 阅读顺序

系列分成四段：先打通信地基，再打互操作地基，然后是三类设备的实战，最后收成可交付的工程结构。全部八篇已完成。

### 第一段：通信地基

**1. [串口通信与设备协议拆帧](/posts/iot/serial-port-communication)**

从 `SerialPort` 开始，讲清 RS232/RS485 的物理层参数、`DataReceived` 事件为什么不能直接用来解析、字节流为什么必须拆帧，并给出固定长度、分隔符、长度前缀三种拆帧器的完整实现。最后把串口和 TCP 抽象成同一个通道接口——因为现场经常用串口服务器把 RS232 转成网口，上层解析逻辑不应该被这件事影响。

这是整个系列最重要的一篇。地磅、老式读卡器、显示屏、称重打印机，全都在这一层。

**2. [私有 TCP 协议与二进制解析](/posts/iot/tcp-protocol-binary-parsing)**

厂商只给一份《通信协议文档》时怎么落地：帧结构建模要确认的七件事、`SpanReader` 游标式二进制读取、BCD 码与定点小数、CRC16 的三种常见变体和算不对时的排查顺序。

后半篇是长连接的生命周期管理——请求应答关联（半双工用信号量串行化，带序号的用等待表）、心跳保活与半开连接、断线重连的退避与"清场"、以及设备主动连你时的服务端实现。**这部分占实际工作量的七成，比协议解析本身重要。**

**3. [Modbus 协议实战](/posts/iot/modbus-protocol)**

前两篇处理的是私有协议，这一篇是工业现场最普及的**标准**协议。电表、水表、传感器、变频器、IO 模块、部分 PLC 都用它。

四类数据区与功能码、**地址偏移这个百分百会踩的坑**（手册的 40001 在报文里是 0）、RTU 的静默间隔分帧为什么在通用操作系统上要改成按预期长度读取、TCP 的 MBAP 头与事务标识、**32 位数值的字序不在标准内**所以必须可配置，以及轮询系统的三要素：批量读取合并、按周期分组、故障设备退避。

### 第二段：互操作地基

**4. [P/Invoke 对接厂商 SDK](/posts/iot/pinvoke-vendor-sdk)**

海康、大华、中控的 SDK 都是原生 DLL。这一篇按"七关"组织：位数匹配与 `BadImageFormatException`、DLL 依赖加载、函数声明与调用约定、结构体映射与对齐（用 `Marshal.SizeOf` 验证）、GBK 中文编码、**回调委托必须保活否则随机崩溃**、句柄与内存生命周期，最后是三层封装让业务代码完全看不见 `Marshal`。

这一篇是分水岭。过了 P/Invoke 这关，任何厂商的 SDK 对你都是一样的，剩下的只是查文档。

### 第三段：三类设备实战

**5. [地磅称重对接](/posts/iot/weighbridge-integration)**

从业务开始讲：毛重/皮重/净重、二次过磅为什么决定了数据模型。技术核心是两个——**判稳算法**（滑动窗口 + 极差阈值 + 持续时长三重判定，为什么不能只信仪表的稳定标志位）和**过磅状态机**（每个状态都必须有超时兜底，这是无人值守能不能用的分界线）。

另外覆盖防作弊的七种手法与对策、单据跨天的一致性要求、道闸与语音的外设抽象、以及断网时的本地优先降级。

**6. [摄像头对接](/posts/iot/camera-integration)**

核心是**动手之前先按需求选路线**，选错成本差十倍：抓图用 ISAPI（一个 HTTP GET）、预览用 LibVLCSharp、逐帧处理用 OpenCvSharp、跨品牌用 ONVIF、只有实时取流和云台精细控制才值得写 SDK。录像交给 NVR，识别交给一体机。

重点讲**车牌识别一体机**的接入——设备自己识别完推给你，是地磅和停车场性价比最高的方案，同时说明这个推送端点为什么必须做来源控制。另有图片存储策略和现场部署（带宽计算、VLAN、NTP、密码管理）。

**7. [门禁对接](/posts/iot/access-control-integration)**

门禁的难点不在开门，而在"设备必须离线可用"这个约束推导出的一切：人员、卡号、人脸、权限、时间段规则**必须提前下发到设备本地**，于是它变成了一个分布式数据同步问题。

覆盖期望状态与设备状态的对账模型、下发任务表与退避重试、同设备串行与依赖排序、**全量校准的自动删除防护**、人脸下发的前置校验、**事件推送 + 游标拉取双管道补漏**、消防联动的硬件兜底，以及撤销权限必须确认生效。

### 第四段：工程化

**8. [设备适配层设计与现场可靠性](/posts/iot/device-layer-and-reliability)**

把前七篇收成一套能长期维护的工程结构：四层架构与每层的**禁令**、领域接口如何不泄漏 SDK 概念、配置驱动的键控服务工厂、设备状态与健康检查分级。

重点是**模拟器的三个层次**（Fake 实现、会故意作恶的协议级模拟器、按原始时序的录制回放），以及现场可靠性的成套做法：报文留存的独立通道、三层看门狗、Windows Service 部署的六个坑、本地优先的降级链路，最后附一份可逐条打勾的上线清单。

## 一条贯穿全系列的架构线

从第一篇开始就会按这个分层写代码，不是最后才重构：

```text
业务层（过磅流程、通行规则、报表）
    ↑  只依赖领域事件和领域接口
设备适配层（IWeighingIndicator / ICamera / IAccessController）
    ↑  每个品牌一个实现，配置文件决定加载哪个
通信层（IDeviceChannel：串口 / TCP 统一抽象）
    ↑
厂商 SDK 与私有协议（P/Invoke、SerialPort、Socket）
```

守住这条线的收益很直接：三年后甲方要换品牌，你只加一个适配器实现；开发期没有真机，你注入一个模拟实现照样能把业务跑通。

:::tip 学到哪一步就能接项目
第 1 篇 + 第 5 篇（串口 + 地磅）足够独立完成一套有人值守的称重系统。
再加第 4 篇 + 第 6 篇（P/Invoke + 摄像头），就能做无人值守。
只做数据采集类项目（电表、传感器、能耗监测）的话，第 1 篇 + 第 3 篇（串口 + Modbus）就够用。
第 7 篇门禁是另一条相对独立的业务线，可以按需跳读。
:::

## 一个现实的提醒

这类项目里，**你会有相当比例的时间花在"厂商文档和实际行为不一致"上**。手册写着返回 0 表示成功，实际返回 1；说是 GBK 编码，实际混着 UTF-8；文档里的结构体字段顺序和 SDK 头文件不一样。

应对办法只有两条，这个系列会反复强调：

1. **所有原始报文落盘**。不猜，看真实字节。
2. **先写模拟器再写业务**。你需要一个完全受你控制的"设备"，才能分清是你的代码错了还是设备行为变了。

准备好了就从 [串口通信与设备协议拆帧](/posts/iot/serial-port-communication) 开始。

# 云端 IoT 平台路线图：MQTT 接入到数据落库

这是和 [工业设备对接系列](/posts/iot/industrial-device-roadmap) 并行的另一条线。两条线的技术重心几乎不重叠，先说清区别，避免走错方向。

| 维度 | 工业设备对接 | 云端 IoT 平台 |
|---|---|---|
| 部署位置 | 厂区内网的一台工控机 | 云服务器 / K8s |
| 设备数量 | 几台到几十台 | 几千到几十万 |
| 设备接口 | 厂商 SDK、串口、私有 TCP | **MQTT**、HTTP |
| 主要难点 | 设备互操作、流程状态机 | **海量长连接、数据吞吐、设备管理** |
| 数据特征 | 单条数据很重要（一次过磅） | 单条不重要，趋势重要 |
| 网络假设 | 会断，断了业务也要继续 | 相对稳定，但设备会大量掉线 |

一句话区分：**工业侧的难点是"连得上"，云端的难点是"扛得住"。**

两条线不是替代关系。实际项目里经常是"边缘用工业侧那套对接设备，再通过 MQTT 把数据送上云"，这时两条线都要会。

如果你的项目是厂区内的几台设备，去看工业系列。如果是几千台设备上报数据到云端，这条线才对。

## 读完这个系列你应该能回答

- MQTT 凭什么取代 HTTP 成为 IoT 的事实标准
- QoS 0/1/2 到底保证什么，为什么 QoS 2 在实践中很少用
- 遗嘱消息（LWT）如何实现设备掉线检测
- Topic 怎么设计才能同时满足业务查询和权限隔离
- 一机一密和一型一密的区别，为什么后者是安全隐患
- 什么是物模型，为什么它能让新增设备品类不用改代码
- 一万台设备每秒上报，数据库扛不住时该怎么削峰
- 为什么 IoT 数据不该用关系库长期存储
- 设备离线时 App 怎么显示状态，"期望值"和"上报值"为什么要分开
- 指令下发是异步的，怎么把响应和请求对上

## 阅读顺序

### 第一段：接入地基

**1. [MQTT 与 MQTTnet：从模拟设备到服务端接入](/posts/iot/mqtt-mqttnet-basics)**

MQTT 的全部核心概念：发布订阅模型、Topic 层级与通配符、QoS 三个等级的确切语义、保留消息、遗嘱消息、心跳与会话。然后用 MQTTnet 写一个模拟设备和一个服务端订阅服务，跑通"设备上报 → 服务端接收 → 入队"的最小闭环。

**2. [MQTT Topic 设计、设备认证与 ACL](/posts/iot/mqtt-topic-auth-acl)**

两件"改起来最贵"的决策。Topic 的六条设计原则与完整规范表（为什么设备标识必须在路径里、为什么业务属性绝不能入 Topic、第一层放版本号的价值）、通配符订阅的性能取舍与 MQTT 5 共享订阅。

后半篇是安全：一机一密 vs 一型一密的取舍、**HMAC 签名让密钥不上网**、EMQX 的 HTTP 认证与 ACL 端点实现、**`{deny, all}` 兜底为什么是整套 ACL 的核心**，以及设备时钟导致 TLS 校验失败这个经典现场坑。附一份可逐条确认的安全清单。

### 第二段：数据抽象

**3. [物模型：属性、事件、服务三要素](/posts/iot/thing-model)**

整个平台最重要的抽象。先算清不用物模型的代价（六个横向功能 × 二十个品类 = 一百二十份重复工作），再讲三要素的划分标准（属性与事件怎么分、服务与可写属性怎么分）、类型系统与约束的实际用途、一份完整的物模型 JSON。

然后是落地：**上报数据校验必须做**且要区分处理（超范围报设备健康告警、未定义属性留档、类型错拒绝、部分接受）、属性值存储的三种方案对比与"快照 JSON 列 + 历史时序库"的组合、三个具体红利（前端动态渲染、规则引擎通用化、生态映射一次到位），以及物模型自身的兼容性演进。

### 第三段：数据链路

**4. [削峰、背压与批量入库](/posts/iot/ingest-backpressure-batching)**

从算账开始（三行公式 + 三档场景表），然后是三层结构：`Channel` 缓冲（为什么绝不能用 Unbounded、容量按可缓冲时长定）、批量写入（双触发攒批、数据库原生批量接口、`COPY` 与唯一约束的冲突）、背压策略（**为什么 `Wait` 会引发级联故障**、遥测与事件的分级队列、落盘兜底）。

另有消息队列的引入判断标准（看信号不看设备数）、五个必须有的队列指标与解读表、削峰的边界（缓冲只解决突发峰值），以及从源头减少数据量的四种手段。

**5. [时序数据库：为什么关系库扛不住 IoT 数据](/posts/iot/timeseries-database)**

先讲清 IoT 数据的四个特征如何逐条击穿关系库的假设（尤其"表变大导致写入变慢"这个自我恶化的问题），再讲时序库的三项核心优化：列存 + 类型化压缩、按时间分区、预聚合。

选型给了 TimescaleDB / InfluxDB / TDengine 的对比与明确建议（**已用 PostgreSQL 就上 TimescaleDB**，迁移成本近乎为零还保留 JOIN）。实践部分覆盖 **tag 基数这个头号陷阱**、`device_id` 数字化与属性名字典化、为什么不能用 JSON 列存历史数据、分层保留与连续聚合、按查询跨度自动选粒度，以及双库并存的一致性原则。

### 第四段：设备管理

**6. [设备影子与在线状态](/posts/iot/device-shadow-online-state)**

先讲清"在线"这个词的歧义——TCP 连着不等于设备在工作，最可信的信号是"最近收到业务消息"。然后是三信号组合判定、按产品配置的超时阈值、**离线去抖而上线立即生效**这个有意的不对称、抖动设备识别，以及上线风暴的三层应对。

后半篇是设备影子的 reported / desired / delta 三段模型：它如何让离线设备也能"接受"指令、**reported 追上就必须移除 desired 项**否则会重复下发、**desired 必须有时效**（周五设的指令周一执行是安全问题）、以及"用户开灯系统关灯"这类冲突的策略选择。

**7. [指令下发与响应关联](/posts/iot/command-dispatch-reply)**

下发的全部困难来自一个错配：调用方期望同步，现实是异步。核心认知是**分清四层"成功"**（已受理/已投递/已送达/已执行），绝大多数 bug 来自混淆它们。

覆盖多实例部署下"响应被别的实例收到"的三种解法、MQTT 5 的原生请求响应属性、**超时不等于失败而是"未知"**、幂等设计优于重试控制（把"切换"改成"设置为 X"）、离线设备的三种策略、批量下发的限流与灰度熔断，以及 OTA 为什么必须单独设计。

## 一个前置提醒

这条线上有个常见的过度设计陷阱：**一上来就搭 Kafka + 时序库 + K8s。**

如果你的设备数在**一千台以内、每台每分钟上报一次**，那就是每秒不到 20 条消息——一个 EMQX 加一个 PostgreSQL 就能轻松扛住，引入消息队列只是增加运维负担。

先把量算清楚：

```text
消息速率 = 设备数 × 每台每秒上报次数
日增数据量 = 消息速率 × 单条大小 × 86400
```

**按算出来的量选方案，不要按"以后可能会有多少设备"选。** 架构可以演进，过早的复杂度是实打实的成本。

## 1. InnoDB 的 B+Tree 索引：和通用模型有什么不同

### 1.1 聚簇索引 vs 二级索引

通用 B-Tree 索引原理已在 [SQL 进阶](/posts/sql/sql-advanced-performance) 中讲过。InnoDB 的独特之处在于**聚簇索引**：

- **聚簇索引**：主键就是数据的物理组织方式，叶子节点存储完整行数据
- **二级索引**：按索引列排序，叶子节点只存储**索引列 + 主键**

这意味着 InnoDB 的二级索引查询通常需要**回表**：先从二级索引查到主键，再到聚簇索引查完整行。

对比 PostgreSQL：PG 的索引叶子存的是堆指针（ctid），数据和索引分离。

### 1.2 页结构：InnoDB 怎么组织数据

- 数据页之间通过**双向链表**关联
- 页内记录按主键顺序组成**单向链表**
- 通过**页目录**实现二分法快速定位
- 每页默认 16KB

### 1.3 索引的代价

| 代价类型 | 说明 |
|---------|------|
| 空间代价 | 每建一个索引就要建立一棵 B+树，占用存储空间 |
| 时间代价 | 增删改时需维护 B+树结构，产生页面分裂、记录移位 |
| 回表代价 | InnoDB 二级索引特有：查到主键后还要再查聚簇索引 |

## 2. InnoDB 索引使用条件

### 2.1 适用场景

| 场景 | 说明 |
|-----|------|
| **全值匹配** | 查询条件包含索引的全部列 |
| **匹配左边的列** | 必须从最左边连续使用索引列（最左前缀原则） |
| **匹配列前缀** | 如 `LIKE 'As%'`，不支持 `LIKE '%As%'` |
| **匹配范围值** | 索引列进行范围查询 |
| **精确匹配+范围匹配** | 左边列精确匹配，右边列范围匹配 |
| **用于排序/分组** | ORDER BY/GROUP BY 使用索引列 |

### 2.2 联合索引注意事项

```sql
-- 联合索引 idx_name_birthday_phone_number (name, birthday, phone_number)
-- 可用于：
SELECT * FROM person_info WHERE name = 'Ashburn';
SELECT * FROM person_info WHERE name = 'Ashburn' AND birthday = '1990-09-27';

-- 不可用于：
SELECT * FROM person_info WHERE birthday = '1990-09-27';
SELECT * FROM person_info WHERE name = 'Ashburn' AND phone_number = '...';
```

### 2.3 回表的代价与覆盖索引

InnoDB 二级索引查到主键后，需要到聚簇索引中查找完整记录（**回表**）。回表是随机 IO，代价很高。

**覆盖索引**：如果查询需要的列全部在二级索引中，MySQL 可以直接从索引返回结果，避免回表。

```sql
SELECT name, birthday, phone_number
FROM person_info WHERE name > 'Asa' AND name < 'Barlow';
```

如果 `(name, birthday, phone_number)` 是联合索引，这个查询可以用覆盖索引。

### 2.4 索引下推（ICP）：MySQL 5.6+ 的优化

在没有 ICP 时：存储引擎根据最左前缀从索引中找到行，回表后交给 Server 层判断其他 WHERE 条件。

有了 ICP：存储引擎在索引遍历时就判断 WHERE 中**能用到索引列的条件**，不满足的不回表，减少回表次数。

```sql
-- 联合索引 (zipcode, lastname, firstname)
SELECT * FROM people
WHERE zipcode = '95054' AND lastname LIKE '%etnia%';
```

ICP 可以在索引遍历时就跳过 `lastname` 不满足的记录，不必回表。

## 3. 单表访问方法：type 字段详解

MySQL EXPLAIN 的 `type` 字段表示访问方法，从好到差：

| 类型 | 说明 | 适用场景 |
|-----|------|---------|
| `system` | 表中只有一行（const 的特例） | 系统表 |
| `const` | 主键/唯一索引等值查询 | `WHERE id = 1` |
| `eq_ref` | JOIN 时被驱动表用主键/唯一键匹配 | JOIN 场景 |
| `ref` | 普通二级索引等值查询 | `WHERE key1 = 'abc'` |
| `ref_or_null` | 索引列等值或 NULL | `WHERE key1 = 'a' OR key1 IS NULL` |
| `range` | 索引列范围查询 | `WHERE key2 > 10 AND key2 < 1000` |
| `index` | 遍历全部索引（不回表） | 查询列都在索引中 |
| `ALL` | 全表扫描 | 最慢，尽量避免 |

### 3.1 索引合并（Index Merge）

某些情况下可使用多个索引：

| 类型 | 条件 | 说明 |
|-----|------|------|
| **Intersection** | 多索引等值匹配 | 取多个索引结果的交集 |
| **Union** | 多索引条件用 OR 连接 | 取多个索引结果的并集 |
| **Sort-Union** | 非等值但可排序 | 先排序再 Union |

索引合并在 EXPLAIN 中 `type` 显示为 `index_merge`。

## 4. 基于成本的优化：MySQL 优化器怎么选执行计划

### 4.1 成本构成

```
总成本 = I/O成本 + CPU成本
```

- **I/O成本**：页面从磁盘加载到内存
- **CPU成本**：读取记录、检测搜索条件、排序

### 4.2 优化步骤

1. 根据搜索条件，找出所有可能使用的索引（`possible_keys`）
2. 计算全表扫描的代价
3. 计算使用不同索引执行查询的代价
4. 对比各种执行方案的代价，选择最低的

### 4.3 影响成本的因素

| 因素 | 影响 |
|-----|------|
| **范围区间数量** | IN 子句参数多则成本高 |
| **需要回表的记录数** | 回表记录越多，成本越高 |
| **统计数据准确性** | InnoDB 统计数据是估计值 |

### 4.4 统计信息刷新

InnoDB 的统计信息不是实时精确的，而是基于采样估算：

```sql
-- 查看表的统计信息
SHOW TABLE STATUS LIKE 'orders';

-- 手动刷新统计信息
ANALYZE TABLE orders;
```

MySQL 8.0 还支持直方图来提高非索引列的估算精度：

```sql
ANALYZE TABLE orders UPDATE HISTOGRAM ON status WITH 100 BUCKETS;
```

## 5. EXPLAIN 逐字段详解

通用执行计划解读方法见 [SQL 进阶](/posts/sql/sql-advanced-performance)。这里逐字段讲 MySQL 的 EXPLAIN 输出。

### 5.1 关键输出列

| 列名 | 说明 |
|-----|------|
| `id` | 查询编号，子查询/UNION 会多行 |
| `select_type` | 查询类型：SIMPLE / PRIMARY / SUBQUERY / DERIVED 等 |
| `table` | 访问哪张表 |
| `partitions` | 匹配的分区（未分区为 NULL） |
| `type` | 访问方法（见第 3 节） |
| `possible_keys` | 可能使用的索引 |
| `key` | 实际使用的索引 |
| `key_len` | 索引使用长度（判断复合索引用了几列） |
| `ref` | 与索引比较的列或常量 |
| `rows` | 预估读取的记录数 |
| `filtered` | 存储引擎返回后 Server 层再过滤的百分比 |
| `Extra` | 额外信息 |

### 5.2 Extra 常见值

| 值 | 含义 | 优化建议 |
|---|-----|---------|
| `Using index` | 覆盖索引，无需回表 | 最佳 |
| `Using index condition` | 索引下推（ICP） | 良好 |
| `Using where` | 回表后 Server 层过滤 | 可能需优化 |
| `Using filesort` | 需要额外排序（不在索引中） | 考虑添加索引 |
| `Using temporary` | 使用临时表 | 考虑优化查询 |
| `Using join buffer` | JOIN 被驱动表没走索引 | 检查 JOIN 条件 |
| `Using MRR` | Multi-Range Read 优化 | 一般良好 |
| `FirstMatch` | 半连接优化 | 子查询优化结果 |
| `LooseScan` | 半连接优化 | 子查询优化结果 |

### 5.3 优化示例

```sql
EXPLAIN SELECT * FROM orders WHERE status = 'pending';
-- 如果 type=ALL, key=NULL: 全表扫描

ALTER TABLE orders ADD INDEX idx_status (status);
EXPLAIN SELECT * FROM orders WHERE status = 'pending';
-- 期望 type=ref, key=idx_status
```

## 6. 基于规则的优化：MySQL 优化器做了哪些自动改写

### 6.1 条件化简

| 优化 | 示例 |
|-----|------|
| 移除括号 | `((a=5))` → `a=5` |
| 常量传递 | `a=5 AND b>a` → `a=5 AND b>5` |
| 表达式计算 | `a=5+1` → `a=6` |

### 6.2 外连接消除

当 WHERE 子句包含被驱动表列的**非 NULL 条件**时，MySQL 会将外连接自动转为内连接：

```sql
SELECT * FROM t1 LEFT JOIN t2 ON t1.id = t2.id
WHERE t2.name IS NOT NULL;
-- 优化器自动等价于
SELECT * FROM t1 INNER JOIN t2 ON t1.id = t2.id WHERE t2.name IS NOT NULL;
```

### 6.3 子查询优化

**物化表**：将不相关子查询结果存入临时表，避免重复执行子查询。

**半连接（Semi-join）**：将子查询转为连接，只关心匹配是否存在。MySQL 的半连接策略包括 FirstMatch、LooseScan、Duplicate Weedout 等。

## 7. InnoDB 事务与锁实现

通用的事务和锁概念见 [SQL 入门指南](/posts/sql/sql-beginner-guide)。这里讲 InnoDB 的具体实现。

### 7.1 ACID 的 InnoDB 实现机制

| 特性 | 说明 | InnoDB 实现机制 |
|-----|------|---------|
| **A**tomic | 原子性 | Undo Log |
| **C**onsistency | 一致性 | Redo Log + 锁 |
| **I**solation | 隔离性 | MVCC + 锁 |
| **D**urability | 持久性 | Redo Log |

### 7.2 隔离级别与 InnoDB 行为

| 级别 | 脏读 | 不可重复读 | 幻读 | InnoDB 行为 |
|-----|-----|----------|-----|------------|
| READ UNCOMMITTED | 可能 | 可能 | 可能 | 最少加锁 |
| READ COMMITTED | 不可能 | 可能 | 可能 | 记录锁，不加间隙锁 |
| REPEATABLE READ（默认） | 不可能 | 不可能 | 可能（InnoDB 用 Next-Key Lock 防止） | 记录锁 + 间隙锁 |
| SERIALIZABLE | 不可能 | 不可能 | 不可能 | 所有 SELECT 隐式加锁 |

### 7.3 MVCC 原理：InnoDB 的 ReadView

**ReadView** 包含：

- `m_ids`：活跃事务 ID 列表
- `min_trx_id`：最小活跃事务 ID
- `max_trx_id`：创建时最大事务 ID
- `creator_trx_id`：当前事务 ID

**快照读** vs **当前读**：

- 快照读：读取事务开始时的快照（普通 SELECT）
- 当前读：读取最新数据（`SELECT FOR UPDATE` / `INSERT` / `UPDATE` / `DELETE`）

InnoDB 的 MVCC 实现与 PostgreSQL 不同：PG 用堆 + xmin/xmax 标记，InnoDB 用 undo log 链 + ReadView。

## 8. Buffer Pool 优化

### 8.1 作用

Buffer Pool 是 InnoDB 在内存中缓存数据和索引的组件，减少磁盘 IO。

### 8.2 关键参数

| 参数 | 说明 | 建议值 |
|-----|------|-------|
| `innodb_buffer_pool_size` | 缓冲池大小 | 物理内存的 50%-80% |
| `innodb_buffer_pool_instances` | 缓冲池实例数 | CPU 核心数（最多 8 个） |
| `innodb_old_blocks_pct` | 旧区域比例 | 默认 37% |
| `innodb_flush_neighbor_pages` | 刷邻接页 | 机械盘建议 always，SSD 建议 none |

### 8.3 优化建议

```sql
SET GLOBAL innodb_buffer_pool_size = 8589934592;

SELECT @@innodb_buffer_pool_read_requests / (@@innodb_buffer_pool_read_requests + @@innodb_buffer_pool_reads) AS hit_rate;
```

## 9. 索引设计最佳实践

### 9.1 创建原则

1. **只为用于搜索、排序、分组的列创建索引**
2. **选择高基数的列**（重复值少）
3. **索引列类型尽量小**（减少存储空间和 IO）
4. **字符串前缀索引**（对长字符串效果好）

```sql
ALTER TABLE orders ADD INDEX idx_email (email(10));
ALTER TABLE orders ADD INDEX idx_status_created (status, created_at);
```

### 9.2 避免的索引

| 问题 | 说明 | 解决方案 |
|-----|------|---------|
| **冗余索引** | 联合索引已包含单列索引 | 删除冗余索引 |
| **重复索引** | 主键+唯一索引+普通索引 | 避免重复 |
| **过长的索引** | 占用大量空间 | 使用前缀索引 |

### 9.3 主键设计

**建议**：使用自增主键或趋势主键，避免随机主键导致页分裂。

```sql
CREATE TABLE orders (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    ...
) ENGINE=InnoDB;
```

## 10. 慢查询排查方法

### 10.1 开启慢查询日志

```sql
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;
SET GLOBAL slow_query_log_file = '/var/log/mysql/slow.log';
SET GLOBAL log_queries_not_using_indexes = ON;
```

### 10.2 使用 EXPLAIN 分析

```sql
EXPLAIN SELECT * FROM orders
WHERE customer_id = 100 AND status = 'pending';
```

### 10.3 使用 optimizer_trace

```sql
SET optimizer_trace = "enabled=on";
SET optimizer_trace_max_mem_size = 1000000;

SELECT * FROM orders WHERE ...;

SELECT * FROM information_schema.OPTIMIZER_TRACE;
```

## 总结：MySQL 优化检查清单

### 索引优化
- [ ] 为 WHERE、JOIN、ORDER BY、GROUP BY 的列建立索引
- [ ] 遵循最左前缀原则设计联合索引
- [ ] 避免冗余和重复索引
- [ ] 使用覆盖索引减少回表
- [ ] 对长字符串列使用前缀索引

### 查询优化
- [ ] 避免 SELECT *，只查询需要的列
- [ ] 避免在索引列上使用函数或运算
- [ ] 使用 EXPLAIN 分析执行计划
- [ ] 避免隐式类型转换
- [ ] 优化子查询，使用 JOIN 替代

### 架构优化
- [ ] 合理设置 Buffer Pool 大小
- [ ] 使用合适的数据类型
- [ ] 避免大事务
- [ ] 定期分析表更新统计数据
- [ ] 使用连接池复用连接

# MySQL 分库分表迁移实战：不停机双写、回填、校验与切流

分库分表最难的不是设计分片算法，而是迁移上线。

真实项目常见翻车点：

1. 全量迁移时锁表导致业务抖动。
2. 双写阶段新老数据不一致。
3. 切流后读写路由命中错误。
4. 没有回滚预案，出问题只能硬扛。

这篇文章给你一套“可回滚、可观测、可灰度”的迁移流程。

---

## 一、迁移目标与原则

目标：

1. 业务不停机。
2. 数据不丢、不乱。
3. 可灰度切流。
4. 异常可快速回退。

原则：

1. 先建新路，再切旧路。
2. 先双写，再切读，再切写。
3. 每一步都可验证、可回滚。

---

## 二、迁移前准备

至少完成这些准备：

1. 明确分片键（如 `user_id`）。
2. 明确分片规则（取模/一致性哈希）。
3. 上线路由层（应用内或中间件）。
4. 新分片库建表和索引完成。
5. 增加迁移开关（双写开关、读路由开关、回退开关）。

建议先在预发全链路演练一遍。

---

## 三、总体迁移流程（7 步）

```text
1. 新库准备
2. 发布双写代码（默认只写旧库）
3. 开启双写（旧+新）
4. 历史数据回填
5. 增量追平与一致性校验
6. 灰度切读 -> 切写
7. 稳定后下线旧路径
```

---

## 四、双写策略（不停机核心）

### 1. 推荐策略

1. 主写旧库（事实来源）。
2. 异步或同步写新分片库。
3. 双写失败要可观测和可补偿。

### 2. Node.js 伪代码示例

```ts
async function createOrder(input: OrderInput) {
  // 1) 先写旧库（主路径）
  const order = await oldDb.createOrder(input)

  // 2) 双写开关开启时写新库
  if (featureFlags.dualWriteEnabled) {
    try {
      const shard = calcShard(input.userId)
      await newShardDbs[shard].createOrder(order)
    } catch (err) {
      // 记录失败事件，交给补偿任务
      await migrationErrorLog.save({
        bizType: 'ORDER_CREATE',
        bizId: order.orderNo,
        payload: order,
        reason: String(err),
      })
    }
  }

  return order
}
```

重点：

1. 不要让新库失败直接影响主链路（迁移阶段）。
2. 失败必须可追踪、可补偿。

---

## 五、历史数据回填

### 1. 回填方式

1. 按主键范围分批。
2. 每批固定大小（如 1000/5000）。
3. 限速执行，避免打爆线上库。

### 2. 批处理示例

```sql
SELECT * FROM orders
WHERE id > ?
ORDER BY id
LIMIT 1000;
```

回填时建议“幂等 upsert”写入新库。

### 3. 回填顺序建议

1. 主表先回填。
2. 明细表、日志表跟进。
3. 最后校验关联完整性。

---

## 六、增量追平（CDC）

历史回填只覆盖过去数据，迁移期间新变更要靠增量同步。

常见做法：

1. 订阅 binlog（Debezium/Canal）。
2. 将增量变更写入新分片库。
3. 与双写并行，保证追平。

目标是：

> 在切流前让“旧库数据状态”和“新库数据状态”尽可能一致。

---

## 七、一致性校验（必须做）

至少做三类校验：

### 1. 总量校验

```sql
SELECT COUNT(*) FROM orders;
```

对比旧库总量与新分片汇总总量。

### 2. 分片维度校验

```sql
SELECT user_id % 8 AS shard_key, COUNT(*)
FROM orders
GROUP BY shard_key;
```

检查分布是否符合预期。

### 3. 抽样字段校验

按 `order_no` 抽样比对金额、状态、时间字段。

建议自动化输出差异报表。

---

## 八、灰度切流策略

### 1. 先切读

按小流量用户（1%）切到新库读：

1. 查询接口先切。
2. 核对延迟和结果一致性。

### 2. 再切写

切写要更谨慎：

1. 1% 写流量 -> 10% -> 50% -> 100%。
2. 每阶段观察业务成功率、错误率、慢 SQL。

### 3. 切流期间保留双写

先保持一段时间“新主写 + 旧库兜底写”，稳定后再下线旧写。

---

## 九、回滚预案（必须提前准备）

回滚触发条件示例：

1. 新库关键接口错误率 > 1%。
2. 查询结果差异超阈值。
3. 状态流转异常增多。

回滚动作：

1. 读路由切回旧库。
2. 写路由切回旧库。
3. 保留新库写入日志用于问题分析。
4. 启动数据修复任务。

没有回滚预案，就不算可上线方案。

---

## 十、迁移期监控指标

重点监控：

1. 双写失败率。
2. 回填进度与速率。
3. 增量积压（CDC lag）。
4. 新旧库数据差异数。
5. 分片热点（QPS/CPU/锁等待）。

迁移期建议单独仪表盘，不和常规业务混在一起。

---

## 十一、常见坑与规避

1. 分片键选错导致热点。
2. 双写无幂等导致重复数据。
3. 只做总量校验，不做字段校验。
4. 切流过快，问题放大。
5. 迁移脚本无限速，拖垮线上。

---

## 十二、最小可执行清单

1. 新库与路由层就绪。
2. 双写代码上线并可开关控制。
3. 回填任务支持断点续传。
4. CDC 增量同步可观测。
5. 校验脚本自动化。
6. 灰度切流与回滚脚本演练通过。

---

## 总结

分库分表迁移的本质不是“搬数据”，而是“控制风险”。

你只要把这四件事做好：

1. 双写可控。
2. 回填可追。
3. 校验可证。
4. 切流可回。

迁移就会从高风险工程变成可管理工程。

# MySQL 分片键设计与热点治理实战：方法、案例与避坑

分库分表能不能成功，80% 看分片键。

分片键选得好：

1. 流量均匀
2. 查询高效
3. 扩容平滑

分片键选得差：

1. 热点分片爆炸
2. 跨分片查询激增
3. 扩容迁移困难

---

## 一、分片键到底在决定什么

分片键同时决定三件事：

1. 数据落在哪个分片
2. 查询是否命中单分片
3. 流量是否均衡

所以它不是“一个字段”，而是整个分片系统的路由核心。

---

## 二、分片键选择的 5 条原则

1. **高频查询可命中**：常用查询应带分片键。
2. **分布尽量均匀**：避免少数分片过热。
3. **值稳定**：不要用经常变化的字段。
4. **可扩展**：后续扩容迁移成本可控。
5. **业务语义清晰**：排障和治理易理解。

---

## 三、常见候选分片键对比

### 1. `user_id`

优点：

1. 用户维度查询命中率高
2. 数据通常分布较均匀

缺点：

1. 按订单号查单可能跨路由

### 2. `order_id`

优点：

1. 唯一性强，路由简单

缺点：

1. 按用户维度查订单易跨分片

### 3. 时间字段（如 `created_date`）

优点：

1. 归档方便

缺点：

1. 极易形成时间热点，不建议单独使用

实战中订单系统常优先 `user_id`。

---

## 四、分片算法怎么选

### 1. 取模（`key % N`）

优点：简单、快。
缺点：扩容时迁移量大。

### 2. 一致性哈希

优点：扩容迁移更平滑。
缺点：实现复杂度更高。

### 3. 范围分片

优点：按时间管理方便。
缺点：热点明显，需要配套冷热拆分。

默认建议：

1. 早期可用取模。
2. 预留扩容迁移方案。

---

## 五、热点分片如何识别

不要只看全局 QPS，必须按分片看。

至少监控：

1. 每分片 QPS
2. 每分片 CPU/IO
3. 每分片慢 SQL
4. 每分片连接数
5. 每分片锁等待

热点判定常见阈值：

1. 某分片流量 > 平均值 2-3 倍
2. 某分片延迟长期高于其他分片

---

## 六、热点成因（常见）

1. 大客户/大卖家集中在同一分片。
2. 活动流量命中同一批 key。
3. 时间分片导致当前分片过热。
4. 分片键低基数（可选值太少）。

---

## 七、热点治理策略

## 1. 路由打散（最常用）

在分片键上增加“打散因子”，例如：

```text
logicalShard = hash(user_id + order_type + salt) % N
```

适合新系统，老系统改造成本较高。

## 2. 热点分片再拆分

对热点分片做二次拆分：

1. 只迁热点租户/用户
2. 非热点数据保持不动

这是最常见的增量治理方法。

## 3. 缓存吸收热点读

1. 热门查询前置 Redis
2. 本地缓存 + 短 TTL
3. 防击穿和雪崩

## 4. 写入削峰

1. 异步化非核心写
2. 批量写合并
3. 限流与队列缓冲

---

## 八、热点迁移实战流程

当某分片长期过热，推荐流程：

1. 识别热点对象（租户/用户/商品）。
2. 给热点对象分配新分片路由。
3. 上线双写（旧分片 + 新分片）。
4. 回填历史数据。
5. 校验一致性。
6. 切读路由。
7. 停旧写并下线旧路由。

全程需要开关控制和回滚能力。

---

## 九、Node.js 路由示例（伪代码）

```ts
const SHARD_COUNT = 16

function calcShard(userId: number): number {
  return userId % SHARD_COUNT
}

// 热点覆盖表（可存在配置中心/Redis）
const hotShardOverride = new Map<number, number>()

function routeShard(userId: number): number {
  const override = hotShardOverride.get(userId)
  if (override !== undefined) return override
  return calcShard(userId)
}
```

这个模式可以做“定向迁移”：

1. 默认走老规则。
2. 热点用户走新分片。

## 十、SQL 与索引注意点

热点分片治理时，别忽略索引。

建议：

1. 分片内索引结构同构。
2. 热点查询走覆盖索引。
3. 避免热点分片上深分页。

示例索引：

```sql
KEY idx_user_created_id (user_id, created_at DESC, id DESC)
KEY idx_status_created (status, created_at)
```

---

## 十一、常见误区

1. 只看“分布均匀”，忽略查询命中。
2. 分片键选时间字段导致天然热点。
3. 扩容只扩机器，不迁热点数据。
4. 热点治理没有可观测指标。
5. 一次性大迁移，缺少灰度。

---

## 十二、一套可执行检查清单

上线前确认：

1. 分片键是否命中核心查询。
2. 是否有每分片监控看板。
3. 是否有热点识别阈值。
4. 是否有热点迁移开关。
5. 是否有回滚方案。

---

## 总结

分片系统长期稳定运行，关键不是“先分出去”，而是“能持续治理热点”。

你可以记住这三步：

1. 选对分片键。
2. 盯住分片级指标。
3. 热点增量迁移。

把这三步做扎实，分库分表才会真正变成可持续的扩展能力。

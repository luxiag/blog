# MySQL 入门：安装、特性与实战要点

:::tip 前置知识
本文不讲解 SQL 语法基础（SELECT / WHERE / JOIN / GROUP BY / 子查询等）。如果你还不熟悉通用 SQL，请先阅读 [SQL 入门指南](/posts/sql/sql-beginner-guide) 和 [SQL 实战练习](/posts/sql/sql-exercises)。
:::

MySQL 是最常用的关系型数据库之一，很多 Web 应用（电商、内容站、后台系统）都离不开它。通用 SQL 是它的"普通话"，但 MySQL 有自己的"口音"——存储引擎、字符集、特有函数、特有 DDL 语法、8.0 新特性等。

本文聚焦** MySQL 和通用 SQL 的差异点**，帮你把"会写 SQL"变成"会用 MySQL"。

> 默认以 **MySQL 8.0** 为参考版本。MySQL 5.7 仍常见，但部分特性（例如窗口函数、CTE、默认字符集、权限细节）会有差异。

---

## 1. MySQL 是什么？和 SQL 是什么关系？

- **SQL**：一门"操作关系型数据"的语言（查、改、建表、事务）。
- **MySQL**：一种具体的关系型数据库产品，用 SQL 作为主要接口。

同一句 SQL，在不同数据库里可能有一些"口音差异"——函数、分页、类型、行为细节。本文就是讲这些差异。

## 2. 安装与配置

### 2.1 Linux（Ubuntu/Debian）

```bash
sudo apt update
sudo apt install mysql-server
sudo systemctl start mysql
sudo mysql_secure_installation
```

### 2.2 macOS

```bash
brew install mysql
brew services start mysql
```

### 2.3 Docker（推荐开发环境）

```bash
docker run -d \
  --name mysql8 \
  -p 3306:3306 \
  -e MYSQL_ROOT_PASSWORD=your_password \
  mysql:8.0
```

### 2.4 关键配置参数（my.cnf）

```ini
[mysqld]
character-set-server = utf8mb4
collation-server = utf8mb4_0900_ai_ci
default-authentication-plugin = caching_sha2_password
max_connections = 200
innodb_buffer_pool_size = 1G
slow_query_log = 1
long_query_time = 1
```

配置文件位置：

- Linux：`/etc/mysql/my.cnf` 或 `/etc/my.cnf`
- macOS（Homebrew）：`/opt/homebrew/etc/my.cnf`
- Docker：挂载自定义配置文件

修改后需要重启：`sudo systemctl restart mysql`

## 3. MySQL 核心概念

### 3.1 服务器、库、表、行、列

- **MySQL Server**：数据库服务进程，负责存储、查询、权限、事务等。
- **Database（库）**：表的集合，通常按业务拆分。
- **Table（表）**：数据的结构化存储。
- **Row（行）**：一条记录。
- **Column（列）**：字段（类型、约束）。

### 3.2 存储引擎（非常重要）

MySQL 的表背后有不同的"存储引擎"。最常见的是：

- **InnoDB**（默认）：支持事务、行级锁、外键、崩溃恢复，适合绝大多数业务。
- **MyISAM**（老引擎）：不支持事务，锁粒度粗，更多历史遗留。

结论：**新项目几乎都选 InnoDB**。

建表时指定引擎：

```sql
CREATE TABLE users (
  id BIGINT PRIMARY KEY,
  name VARCHAR(50) NOT NULL
) ENGINE=InnoDB;
```

### 3.3 字符集与排序规则（charset/collation）

实际业务里最容易踩坑的是"乱码"和"大小写/比较规则不一致"。

建议：

- 字符集统一使用 `utf8mb4`（不要用 `utf8`，MySQL 的 `utf8` 最多 3 字节，存不了 emoji）
- 排序规则（collation）按业务选择：
  - 想更贴近语言规则、对大小写更友好：`utf8mb4_0900_ai_ci`（8.0 常用）
  - 想严格区分大小写：选择 `*_bin` 或明确的区分大小写规则

建表时指定：

```sql
CREATE TABLE users (
  id BIGINT PRIMARY KEY,
  name VARCHAR(50) NOT NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

## 5. MySQL 特有的数据类型与 DDL

通用 SQL 的数据类型（INT、VARCHAR、DATE 等）在 [SQL 入门指南](/posts/sql/sql-beginner-guide) 中已讲过。这里只补充 MySQL 特有的。

### 5.1 MySQL 独有或差异的类型

| 类型 | 说明 |
|------|------|
| `TINYINT` | 1 字节整数，MySQL 独有（通用 SQL 一般只有 SMALLINT 起） |
| `MEDIUMINT` | 3 字节整数，MySQL 独有 |
| `ENUM` | 枚举类型，MySQL 特有 |
| `SET` | 集合类型，MySQL 特有 |
| `TIMESTAMP` | MySQL 的 TIMESTAMP 有自动更新行为（`ON UPDATE CURRENT_TIMESTAMP`），与 DATETIME 行为不同 |
| `JSON` | MySQL 8.0 原生支持，可配合 `->>` 操作符查询 |
| `YEAR` | 年份类型，MySQL 特有 |

### 5.2 TIMESTAMP vs DATETIME

这是 MySQL 初学者最常见的困惑之一：

| 对比项 | `DATETIME` | `TIMESTAMP` |
|--------|-----------|-------------|
| 存储 | 不做时区转换 | 存 UTC，读时转当前时区 |
| 范围 | `1000-01-01` ~ `9999-12-31` | `1970-01-01` ~ `2038-01-19`（4 字节限制） |
| 自动更新 | 需手动设 `DEFAULT` | 支持 `ON UPDATE CURRENT_TIMESTAMP` |
| 空间 | 8 字节 | 4 字节 |

建议：

- 需要自动更新时间戳用 `TIMESTAMP`
- 需要存历史/未来远期日期用 `DATETIME`
- 团队统一一种策略，不要混用

### 5.3 MySQL 的 AUTO_INCREMENT

MySQL 用 `AUTO_INCREMENT` 实现自增主键：

```sql
CREATE TABLE orders (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  user_id BIGINT NOT NULL,
  status VARCHAR(20) NOT NULL
) ENGINE=InnoDB;
```

注意：`AUTO_INCREMENT` 只能在 InnoDB 的主键或唯一键上使用。

### 5.4 MySQL 特有的建表选项

```sql
CREATE TABLE orders (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  user_id BIGINT NOT NULL,
  status ENUM('pending', 'paid', 'shipped', 'cancelled') DEFAULT 'pending',
  remark TEXT,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
  AUTO_INCREMENT=1000
  ROW_FORMAT=DYNAMIC;
```

- `ENGINE`：指定存储引擎
- `DEFAULT CHARSET / COLLATE`：字符集和排序规则
- `AUTO_INCREMENT`：起始值
- `ROW_FORMAT`：行格式（COMPACT / DYNAMIC / COMPRESSED）

## 6. MySQL 8.0 的两件利器：CTE 与窗口函数

MySQL 8.0 之前没有 CTE 和窗口函数，这让很多复杂查询只能用子查询或应用层拼接。8.0 终于支持了。

### 6.1 CTE（WITH）

```sql
WITH paid_orders AS (
  SELECT id, user_id, created_at
  FROM orders
  WHERE status = 'PAID'
)
SELECT user_id, COUNT(*) AS paid_count
FROM paid_orders
GROUP BY user_id;
```

### 6.2 窗口函数

```sql
WITH ranked AS (
  SELECT
    o.*, ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rn
  FROM orders o
)
SELECT id, user_id, status, created_at
FROM ranked
WHERE rn = 1;
```

更详细的窗口函数用法见 [SQL 入门指南](/posts/sql/sql-beginner-guide)。

## 7. MySQL 特有的函数

通用 SQL 的标准函数（`COALESCE`、`CASE WHEN`、`CAST` 等）在 [SQL 入门指南](/posts/sql/sql-beginner-guide) 中已讲过。MySQL 有自己的"方言函数"——功能等价，但语法不同。了解它们可以帮你读懂别人的代码，但新代码建议优先用标准写法。

### 7.1 IF() —— MySQL 的三元表达式

标准 SQL 用 `CASE WHEN ... THEN ... ELSE ... END`，MySQL 提供了简写：

```sql
SELECT name, IF(age >= 18, '成年', '未成年') AS age_group
FROM users;
```

等价标准写法：

```sql
SELECT name, CASE WHEN age >= 18 THEN '成年' ELSE '未成年' END AS age_group
FROM users;
```

建议：**新代码用 `CASE WHEN`**，跨数据库可移植。

### 7.2 IFNULL() —— MySQL 的空值替换

```sql
SELECT name, IFNULL(phone, '未填写') AS phone_display
FROM users;
```

等价标准写法：

```sql
SELECT name, COALESCE(phone, '未填写') AS phone_display
FROM users;
```

区别：`IFNULL` 只支持两个参数，`COALESCE` 支持多个。建议**优先 `COALESCE`**。

### 7.3 GROUP_CONCAT() —— 分组拼接字符串

MySQL 特有的聚合函数，把分组内的值拼成一个字符串：

```sql
SELECT
  department,
  GROUP_CONCAT(name ORDER BY name SEPARATOR ', ') AS members
FROM employees
GROUP BY department;
```

结果示例：

| department | members |
|-----------|---------|
| 工程部 | Alice, Bob, Carol |
| 市场部 | Dave, Eve |

其他数据库的等价写法：

- PostgreSQL：`STRING_AGG(name, ', ')`
- SQL Server：`STRING_AGG(name, ', ')`
- Oracle：`LISTAGG(name, ', ')`

注意：

- `GROUP_CONCAT` 默认最大长度 1024 字节，超长会被截断。可通过 `SET group_concat_max_len = 1000000;` 调大
- 结果长度不确定，不要用来做业务逻辑判断

### 7.4 其他常用 MySQL 方言函数速查

| MySQL 函数 | 标准等价 | 说明 |
|-----------|---------|------|
| `IF(cond, a, b)` | `CASE WHEN cond THEN a ELSE b END` | 三元表达式 |
| `IFNULL(a, b)` | `COALESCE(a, b)` | 空值替换 |
| `GROUP_CONCAT(col)` | `STRING_AGG` (PG/SS) | 分组拼接 |
| `DATE_FORMAT(date, fmt)` | `TO_CHAR` (PG/Oracle) | 日期格式化 |
| `FIND_IN_SET(str, strlist)` | 无标准等价 | 在逗号分隔字符串中查找位置 |
| `INET_ATON / INET_NTOA` | 无标准等价 | IP 地址与整数互转 |

## 8. MySQL JSON 操作（8.0+）

MySQL 8.0 对 JSON 的支持是它区别于很多传统关系数据库的亮点。如果你有半结构化数据（配置、标签、动态属性），JSON 类型比额外建表或用 EAV 模式更方便。

### 8.1 JSON 列定义与插入

```sql
CREATE TABLE products (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  name VARCHAR(100) NOT NULL,
  attrs JSON,
  tags JSON
);

INSERT INTO products (name, attrs, tags) VALUES
  ('iPhone 15', '{"color": "蓝色", "storage": 256}', '["5G", "旗舰"]'),
  ('Pixel 8', '{"color": "黑色", "storage": 128}', '["5G", "中端"]');
```

MySQL 会自动校验 JSON 格式，非法 JSON 会报错。

### 8.2 提取值：->> 和 JSON_EXTRACT

```sql
SELECT
  name,
  attrs->>'$.color' AS color,
  attrs->>'$.storage' AS storage
FROM products;
```

`->>` 是 MySQL 5.7.13+ 引入的内联路径操作符，等价于 `JSON_UNQUOTE(JSON_EXTRACT(...))`：

- `attrs->'$.color'` → 返回带引号的 JSON 值（如 `"蓝色"`）
- `attrs->>'$.color'` → 返回去掉引号的纯字符串（如 `蓝色`）

**日常查询建议用 `->>`**，结果更干净。

### 8.3 条件查询

```sql
SELECT name
FROM products
WHERE attrs->>'$.color' = '蓝色';
```

```sql
SELECT name
FROM products
WHERE JSON_CONTAINS(tags, '"5G"');
```

`JSON_CONTAINS(target, candidate)` 判断 target JSON 是否包含 candidate 指定的值。

### 8.4 修改 JSON 值

```sql
UPDATE products
SET attrs = JSON_SET(attrs, '$.storage', 512)
WHERE id = 1;
```

常用 JSON 修改函数：

| 函数 | 说明 |
|------|------|
| `JSON_SET(doc, path, val)` | 存在则更新，不存在则新增 |
| `JSON_REPLACE(doc, path, val)` | 只更新已存在的路径 |
| `JSON_REMOVE(doc, path)` | 删除指定路径 |
| `JSON_INSERT(doc, path, val)` | 只在不存在的路径插入 |

### 8.5 JSON 数组操作

```sql
SELECT name
FROM products
WHERE JSON_LENGTH(tags) > 1;

SELECT name, JSON_EXTRACT(tags, '$[0]') AS first_tag
FROM products;
```

### 8.6 虚拟列与索引

JSON 列本身不能直接建普通索引，但可以提取为虚拟列再索引：

```sql
ALTER TABLE products
ADD COLUMN color VARCHAR(50)
  GENERATED ALWAYS AS (JSON_UNQUOTE(JSON_EXTRACT(attrs, '$.color'))) STORED,
ADD INDEX idx_color (color);
```

`STORED` 表示实际存储，`VIRTUAL` 表示查询时计算。索引需要 `STORED` 列。

### 8.7 JSON 使用的边界建议

1. **不要把所有数据都塞进 JSON**——频繁查询/排序的字段还是用普通列
2. JSON 列适合"可选的、动态的、不常单独查询"的属性
3. JSON 内部的值不会参与统计信息优化，查询性能不如普通列
4. JSON 文档不宜过大（建议 1MB 以内），否则更新代价高

## 9. MySQL 特有的 DML：UPSERT

MySQL 的 `ON DUPLICATE KEY UPDATE` 是其独有的"插入或更新"语法：

```sql
INSERT INTO users (id, name, email, created_at)
VALUES (1, 'Alice', 'alice@example.com', NOW())
ON DUPLICATE KEY UPDATE
  name = VALUES(name),
  email = VALUES(email);
```

> MySQL 8.0.20+ 开始不推荐依赖 `VALUES(col)` 的旧行为，建议用别名写法：
>
> ```sql
> INSERT INTO users (id, name, email, created_at)
> VALUES (1, 'Alice', 'alice@example.com', NOW()) AS new_val
> ON DUPLICATE KEY UPDATE
>   name = new_val.name,
>   email = new_val.email;
> ```

对比其他数据库：PostgreSQL 用 `ON CONFLICT`，SQLite 用 `INSERT OR REPLACE`。

## 10. MySQL 特有的分页：LIMIT / OFFSET

MySQL 用 `LIMIT offset, count` 或 `LIMIT count OFFSET offset` 做分页：

```sql
SELECT * FROM orders
ORDER BY created_at DESC
LIMIT 10 OFFSET 20;
```

对比其他数据库：PostgreSQL 也用 `LIMIT/OFFSET`，SQL Server 用 `OFFSET ... FETCH`，Oracle 用 `ROWNUM`。

深分页优化（游标分页）在 [SQL 进阶：执行计划与查询优化](/posts/sql/sql-advanced-performance) 中有通用讲解，MySQL 的具体实践在 [MySQL 进阶](/posts/mysql/mysql-advanced-guide) 中展开。

## 11. 索引与 EXPLAIN：MySQL 的实现细节

索引的通用原理（B-Tree、最左前缀、覆盖索引）已在 [SQL 进阶：执行计划与查询优化](/posts/sql/sql-advanced-performance) 中讲过。这里补充 MySQL 特有的实现细节。

### 11.1 InnoDB 的聚簇索引

与 PostgreSQL 的堆存储不同，**InnoDB 的主键就是聚簇索引**——数据按主键顺序存在 B+Tree 里：

- 二级索引叶子节点存的是**主键值**（不是物理指针）
- 二级索引查询通常需要**回表**：先查到主键，再到聚簇索引查完整行

这意味着：

- 主键选择影响写入性能（随机主键导致频繁页分裂）
- 覆盖索引对 InnoDB 尤其重要（避免回表）

### 11.2 MySQL 的 EXPLAIN 输出

```sql
EXPLAIN
SELECT id, user_id, created_at
FROM orders
WHERE user_id = 1
ORDER BY created_at DESC
LIMIT 20;
```

MySQL EXPLAIN 的关键字段：

| 字段 | 说明 |
|------|------|
| `type` | 访问类型：`const` > `eq_ref` > `ref` > `range` > `index` > `ALL` |
| `key` | 实际使用的索引 |
| `key_len` | 索引使用长度（判断复合索引用了几列） |
| `rows` | 预估扫描行数 |
| `Extra` | `Using index`（覆盖索引）、`Using filesort`、`Using temporary` 等 |

注意：`type` 字段中 `eq_ref` 是 MySQL 特有的，表示 JOIN 时被驱动表用主键/唯一键匹配。

更详细的 EXPLAIN 分析见 [MySQL 性能优化指南](/posts/mysql/mysql-optimization-guide)。

## 12. 事务与锁：MySQL InnoDB 特有行为

事务的通用概念（ACID、隔离级别）在 [SQL 入门指南](/posts/sql/sql-beginner-guide) 中已有介绍。这里讲 MySQL 的实现差异。

### 12.1 InnoDB 的默认隔离级别

MySQL InnoDB 默认是 `REPEATABLE READ`，而 PostgreSQL 和 Oracle 默认是 `READ COMMITTED`。

### 12.2 InnoDB 在 REPEATABLE READ 下的 Next-Key Lock

InnoDB 在 `REPEATABLE READ` 下使用 **Next-Key Lock**（记录锁 + 间隙锁）来防止幻读，这是 MySQL 特有的实现：

```sql
START TRANSACTION;
UPDATE orders
SET status = 'CLOSED'
WHERE user_id = 1 AND created_at >= '2026-01-01';
```

如果条件不够精准、索引不匹配，锁的范围可能扩大，导致大量阻塞。

- PostgreSQL 用 `SERIALIZABLE` 隔离级别 + SSI 来防幻读，不使用间隙锁
- Oracle 用多版本读一致性，也不使用间隙锁

### 12.3 锁观察命令

```sql
SHOW PROCESSLIST;
SHOW ENGINE INNODB STATUS;
```

## 15. 监控与排障

建议至少掌握这些：

- 慢查询日志（Slow Query Log）
- `EXPLAIN` / `EXPLAIN ANALYZE`（8.0.18+）
- `SHOW PROCESSLIST`（看当前连接与执行状态）
- 关注长事务与锁等待

当你遇到"突然变慢"，优先按顺序排查：

- 是否全表扫描（索引/SQL 改写）
- 是否锁等待（长事务/条件不走索引）
- 是否 IO/CPU 瓶颈（硬件/并发/缓存命中）

## 16. 常见坑合集

- 字符集没统一导致乱码：全链路统一 `utf8mb4`，不要用 `utf8`
- `utf8` 不是真 UTF-8：MySQL 的 `utf8` 最多 3 字节，emoji 存不了，必须用 `utf8mb4`
- 时间处理混乱：明确时区策略与字段类型（TIMESTAMP vs DATETIME）
- `NOT IN` 遇到 `NULL` 行为诡异：优先 `NOT EXISTS`
- 事务开太久导致锁等待：减少事务范围、避免在事务里做慢操作
- 隐式类型转换导致索引失效：参数类型与列类型保持一致
- JSON 列不做索引就做条件查询：性能会很差，需要虚拟列 + 索引
- `GROUP_CONCAT` 结果被截断：默认 1024 字节，长结果需调 `group_concat_max_len`

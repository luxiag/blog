## 1. 先建立一张"性能全景图"

一次查询从客户端到结果，中间会经过：

1. 连接与权限（连接数、线程、认证）
2. 解析与优化（SQL 解析、选择执行计划）
3. 执行与访问（走不走索引、扫描多少行、是否回表）
4. 存储与 IO（Buffer Pool 命中率、磁盘读写、redo/undo）
5. 并发与锁（行锁、间隙锁、死锁、长事务）

进阶的关键不是"背参数"，而是：**能把慢/抖/卡住映射到上面的某一层，再用工具验证**。

## 2. InnoDB 存储引擎：数据到底怎么放？

### 2.1 聚簇索引：主键就是数据的"物理组织方式"

通用 B-Tree 索引原理在 [SQL 进阶](/posts/sql/sql-advanced-performance) 中已讲。这里讲 InnoDB 的独特实现。

在 InnoDB 里：

- 表数据按 **主键顺序** 组织在 B+Tree 里（这棵树叫"聚簇索引"）
- 二级索引（普通索引）叶子节点存：**索引列 + 主键值**

对比 PostgreSQL：PG 用堆存储，数据和索引是分离的；InnoDB 的聚簇索引意味着**数据即索引，索引即数据**。

这会带来两个非常实用的结论：

- 二级索引查到主键后，通常还要"回表"拿其它列
- 主键如果很乱（完全随机），写入会频繁页分裂，性能与空间都会变差

### 2.2 页（Page）与局部性：为什么顺序写更快

InnoDB 以页为基本单位管理数据（常见 16KB）。

- 顺序插入：新数据通常落在相邻页，IO 与缓存命中更好
- 随机插入：更容易触发页分裂与离散写，放大 IO

这就是为什么很多团队偏好：

- 主键自增（或趋势递增的分布式 ID）
- 时间字段配合索引用于范围查询

### 2.3 Buffer Pool：MySQL 的"内存数据库"部分

真实线上性能往往取决于：**热数据是否在 Buffer Pool**。

- 命中：内存读，快
- 不命中：磁盘 IO，慢且容易抖

最常见的进阶调优思路：

- 机器内存足够时，把 `innodb_buffer_pool_size` 作为第一优先级（专用数据库机通常给到大部分内存）
- 观察 Buffer Pool 命中率、脏页刷新、IO 等指标后再细调

## 3. redo / undo / binlog：持久化与恢复的三件套

MVCC 和 WAL 的通用原理在 [SQL 进阶](/posts/sql/sql-advanced-performance) 中已讲。这里讲 MySQL 的具体实现。

你可以用一句话理解它们：

- **undo log**：用于回滚与 MVCC（读一致性）
- **redo log**：用于崩溃恢复（保证已提交的数据不丢）
- **binlog**：用于复制与审计（MySQL Server 层的逻辑日志）

### 3.1 redo log 与 binlog 的两阶段提交

MySQL 有两层日志（redo 是 InnoDB 引擎层，binlog 是 Server 层），为保证两者一致，使用**两阶段提交**：

```
1. 写 redo log（prepare 状态）
2. 写 binlog
3. 写 redo log（commit 状态）
```

如果中途崩溃，恢复时根据两阶段状态决定提交还是回滚，保证主从数据一致。

### 3.2 为什么会出现"长事务拖垮数据库"？

长事务不提交/不结束会导致：

- undo 不能及时清理，历史版本堆积
- 一致性读需要追溯更老的版本
- purge 压力变大，整体性能下降

进阶经验：**线上尽量避免长事务**，尤其别把网络调用、慢业务逻辑放在事务里。

## 4. MVCC 与隔离级别：InnoDB 的实现

### 4.1 一致性读 vs 锁定读

- 一致性读：普通 `SELECT`（在默认隔离级别下读到一个一致快照）
- 锁定读：会加锁、参与并发控制
  - `SELECT ... FOR UPDATE`
  - `SELECT ... LOCK IN SHARE MODE`（8.0 更推荐 `FOR SHARE`）

### 4.2 为什么默认 REPEATABLE READ 有时"锁很大"？

InnoDB 在 `REPEATABLE READ` 下使用 **Next-Key Lock（记录锁 + 间隙锁）**来防止幻读。这是 MySQL 特有的实现——PostgreSQL 用 SSI（Serializable Snapshot Isolation），不使用间隙锁。

直觉理解：

- 你锁的不仅是"已存在的行"，还可能锁住"行之间的空隙"，避免别人插入符合你条件的新行

这在"范围更新/范围删除"里尤其明显：

```sql
START TRANSACTION;
UPDATE orders
SET status = 'CLOSED'
WHERE user_id = 1 AND created_at >= '2026-01-01';
```

如果条件不够精准、索引不匹配，锁的范围可能扩大，导致大量阻塞。

进阶经验：

- 范围写操作尽量确保命中合适的索引
- 能用主键/唯一键精确命中的，尽量精确命中

### 4.3 READ COMMITTED 下的锁行为

如果业务对并发要求高，且能接受"不可重复读"，可以考虑把隔离级别改为 `READ COMMITTED`：

- Next-Key Lock 退化为记录锁（不锁间隙）
- 并发更好，但丧失了防幻读保证

## 5. 锁、死锁与"卡住"：真正的排障套路

### 5.1 什么时候会出现锁等待？

典型情景：

- A 事务更新某行未提交
- B 事务也更新同一行（或同一范围）
- B 只能等 A 提交/回滚

### 5.2 死锁是什么？为什么 MySQL 会"主动杀掉一个事务"？

死锁：两个事务互相等待对方释放锁，永远等不到。

InnoDB 会检测死锁并回滚其中一个事务（让系统继续前进）。

减少死锁的常见策略：

- 多表/多行更新时，统一访问顺序（例如总是先更新 `orders` 再更新 `order_items`）
- 缩小事务范围，减少持锁时间
- 尽量用索引精确命中，避免范围锁扩大

### 5.3 必会的观察手段

```sql
SHOW PROCESSLIST;

SHOW ENGINE INNODB STATUS;
```

`SHOW ENGINE INNODB STATUS` 里通常能看到最近一次死锁信息（谁锁了谁、SQL 是什么）。

MySQL 8.0 还可用 `performance_schema.data_locks` 查看锁详情：

```sql
SELECT * FROM performance_schema.data_locks
WHERE OBJECT_NAME = 'orders';
```

## 6. 优化器与执行计划：MySQL 特有细节

### 6.1 EXPLAIN 的 MySQL 特有字段

通用执行计划原理见 [SQL 进阶](/posts/sql/sql-advanced-performance)。这里补充 MySQL EXPLAIN 的特有细节：

| 字段 | 说明 |
|------|------|
| `type` | MySQL 特有的访问类型枚举：`system` > `const` > `eq_ref` > `ref` > `range` > `index` > `ALL` |
| `key_len` | 索引使用长度，可判断复合索引用了几列 |
| `Extra: Using index condition` | 索引下推（ICP），MySQL 5.6+ 特有优化 |
| `Extra: Using MRR` | Multi-Range Read 优化 |
| `Extra: Using join buffer` | JOIN 时被驱动表没走索引，用了连接缓冲 |

### 6.2 为什么"建了索引还是慢"？

常见原因：

- 选择性差：过滤不掉多少行，走索引不一定更划算
- 回表成本高：二级索引查到一堆主键，回表随机 IO 很贵
- 条件写法导致索引失效：函数、隐式转换、前导通配符等

典型例子（函数导致索引难用）：

```sql
WHERE DATE(created_at) = '2026-01-01'
```

更推荐：

```sql
WHERE created_at >= '2026-01-01'
  AND created_at <  '2026-01-02'
```

### 6.3 执行计划不稳定：统计信息与直方图

优化器依赖统计信息估算行数。

- 数据分布变化大时可能选错索引
- MySQL 8.0 支持 **直方图（histogram）** 来提高估算精度（适合某些非均匀分布列）

```sql
ANALYZE TABLE orders UPDATE HISTOGRAM ON status WITH 100 BUCKETS;
```

你不必一开始就手动维护直方图，但要知道：计划"突然变差"往往和统计信息相关。

### 6.4 optimizer_trace：看优化器怎么决策

```sql
SET optimizer_trace = "enabled=on";
SELECT * FROM orders WHERE user_id = 1;
SELECT * FROM information_schema.OPTIMIZER_TRACE;
SET optimizer_trace = "enabled=off";
```

## 7. 索引设计：InnoDB 的实战要点

通用索引设计原则见 [SQL 进阶](/posts/sql/sql-advanced-performance)。这里只讲 InnoDB 特有的实战要点。

### 7.1 覆盖索引：InnoDB 里回表的代价尤其大

因为 InnoDB 二级索引叶子存的是主键，回表意味着再查一次聚簇索引 B+Tree（随机 IO）。

如果一个查询需要的列都包含在二级索引里，MySQL 可以用覆盖索引避免回表：

```sql
SELECT user_id, created_at
FROM orders
WHERE user_id = 1
ORDER BY created_at DESC
LIMIT 20;
```

`(user_id, created_at)` 复合索引即可覆盖，不需要回表。

### 7.2 字符串索引与前缀索引

对很长的 `VARCHAR/TEXT`：

- 全字段索引可能太大
- 可以考虑前缀索引（例如只索引前 20 个字符）

```sql
ALTER TABLE users ADD INDEX idx_email (email(20));
```

代价：前缀索引可能降低唯一性与过滤能力，不能用覆盖索引，要用数据分布验证。

### 7.3 隐式类型转换

```sql
-- 假设 user_id 是 BIGINT
WHERE user_id = '1'
```

MySQL 可能对字符串做隐式转换，导致索引失效。进阶习惯：**参数类型与列类型保持一致**。

## 8. 慢查询治理：从发现到解决的闭环

### 8.1 发现：慢查询日志

```sql
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;
SET GLOBAL log_queries_not_using_indexes = ON;
```

### 8.2 定位：EXPLAIN + 样本数据

同一条 SQL，数据量与分布不同，表现可能完全不一样。

进阶习惯：

- 用接近真实的数据规模验证
- 优化前后对比执行计划与扫描行数

### 8.3 解决：三板斧

1. 改写 SQL（先过滤再 JOIN、避免函数、缩小结果集）
2. 设计索引（复合索引、覆盖索引）
3. 结构调整（冗余字段、汇总表、分区/分库分表，按需）

## 9. 参数调优：只抓最关键的那几个

参数非常多，但对绝大多数业务，优先级通常是：

### 9.1 `innodb_buffer_pool_size`

决定"热数据能不能装下"。这是最影响性能的参数之一。

### 9.2 `innodb_log_file_size` / redo 相关

影响写入与检查点行为。过小会导致频繁 checkpoint，写入更抖；过大恢复时间可能变长。

### 9.3 `max_connections` 与连接池

连接并不是越多越好：

- 过多连接会导致线程调度与内存消耗上升
- 应用层应使用连接池，并控制并发

### 9.4 其他重要参数速查

| 参数 | 说明 | 常见建议 |
|------|------|----------|
| `innodb_flush_log_at_trx_commit` | redo 落盘策略 | `1`（最安全）/ `2`（性能与安全折中） |
| `sync_binlog` | binlog 落盘策略 | `1`（最安全）/ `0` 或 `N`（性能优先） |
| `innodb_io_capacity` | InnoDB 后台 IO 能力 | SSD 建议 2000+，HDD 建议 200-400 |
| `innodb_flush_method` | 刷盘方式 | Linux 建议 `O_DIRECT` |

## 10. 分区（Partitioning）：它解决的是"管理与扫描范围"

分区常用于：

- 按时间切分历史大表（便于归档/删除）
- 让某些查询只扫相关分区

```sql
CREATE TABLE orders (
  id BIGINT AUTO_INCREMENT,
  created_at DATE NOT NULL,
  PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (YEAR(created_at)) (
  PARTITION p2024 VALUES LESS THAN (2025),
  PARTITION p2025 VALUES LESS THAN (2026),
  PARTITION p2026 VALUES LESS THAN (2027),
  PARTITION pmax VALUES LESS THAN MAXVALUE
);
```

但要注意：

- 分区不是银弹：索引、查询写法、分区裁剪是否生效都很关键
- 业务层面常见的"按月删历史"用分区会很爽（`DROP PARTITION`）

## 11. 复制与高可用：线上必备的工程能力

### 11.1 binlog 三种格式

- `STATEMENT`：记录 SQL
- `ROW`：记录行变更（更准确、更常用）
- `MIXED`：混合

很多线上环境偏好 `ROW`，因为复制一致性更好（代价是日志更大）。

### 11.2 GTID：让复制拓扑更可控

GTID 能让"谁执行过哪些事务"更明确，减少人工对齐。

### 11.3 高可用的常见形态

- 主从复制 + 故障切换（配合 MHA、Orchestrator 等工具体系）
- 半同步复制（降低主挂时丢事务的概率）
- 组复制 / InnoDB Cluster（更系统的方案，但复杂度更高）

进阶建议：

- 先把"备份恢复"练熟，再上"自动切换"
- 明确你的 RPO/RTO（能丢多少数据、允许多久不可用）

复制原理与搭建见 [MySQL 复制与高可用](/posts/mysql/mysql-replication-guide)，分片设计与迁移见 [MySQL 分片实战指南](/posts/mysql/mysql-sharding-guide)。

## 12. 备份恢复进阶：可演练、可验证

### 12.1 你至少要掌握两类能力

- **全量备份**：任何时候都能恢复到某个全量点
- **增量/时间点恢复（PITR）**：能恢复到某个具体时间

通常做法：

- 物理全量备份（例如 xtrabackup）
- 持续保留 binlog
- 需要时：全量恢复 + 回放 binlog 到目标时间

进阶经验：

- 备份不是"做了就行"，要定期做恢复演练
- 演练结果要可量化：耗时、数据校验、业务启动流程

## 13. 在线变更（Online DDL）：别在白天锁表改结构

MySQL 8.0 对很多 DDL 支持在线能力，但仍需谨慎：

- 有些变更会重建表
- 大表重建会产生大量 IO、影响线上

```sql
ALTER TABLE orders ADD INDEX idx_status (status), ALGORITHM=INPLACE, LOCK=NONE;
```

- `ALGORITHM=INPLACE`：尽量原地执行，不拷贝全表
- `LOCK=NONE`：不锁表，允许并发 DML

进阶实践常见选择：

- 能在线就在线，但要先在测试环境验证"是否真正在线"
- 更保守的方案：使用成熟的在线变更工具体系（按团队标准）
- 无论哪种：都要有回滚与灰度策略

## 14. 实战清单：遇到问题怎么下手

### 14.1 查询慢

- 看慢日志：是哪条 SQL、频率如何
- 用 `EXPLAIN`：是否全表扫、扫描行数是否离谱
- 看索引：能否覆盖、复合索引是否匹配 WHERE/ORDER
- 改写 SQL：先过滤、避免函数、减少返回列

### 14.2 写入慢或抖

- 看是否有大事务/批量更新
- 看是否有热点行/热点索引
- 看 redo/刷盘行为与 IO
- 检查是否过多二级索引影响写入

### 14.3 卡住/大量超时

- 看 `SHOW PROCESSLIST` 是否大量 waiting
- 看 `SHOW ENGINE INNODB STATUS` 是否锁等待/死锁
- 找长事务并处理
- 检查更新条件是否命中索引，避免锁范围扩大

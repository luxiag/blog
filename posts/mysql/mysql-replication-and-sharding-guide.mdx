# MySQL 复制与分片全面指南：原理、方案与实战避坑

复制和分片是数据库扩展的两条主线：

- 复制：一份数据变多份，主要解决读压力和高可用。
- 分片：一份数据拆多份，主要解决写压力和容量上限。

一句话记住：

> 复制是“横向复制同样的数据”，分片是“横向拆分不同的数据”。

---

## 一、先解决“为什么要做”

### 1. 什么时候考虑复制

1. 查询太多，主库读压力高。
2. 希望有从库做备份、报表、离线分析。
3. 想提升可用性，主库故障能切换。

### 2. 什么时候考虑分片

1. 单表数据量过大（亿级甚至更高）。
2. 单库写入瓶颈明显（CPU、IO、锁冲突）。
3. 单机容量和连接数快到上限。

优先顺序建议：

1. SQL 和索引优化。
2. 缓存优化。
3. 复制 + 读写分离。
4. 最后再分片。

---

## 二、复制（Replication）详细讲解

## 1. 复制的基本原理

MySQL 复制常见流程：

1. 主库把变更写入 Binlog。
2. 从库 I/O 线程拉取 Binlog 到 Relay Log。
3. 从库 SQL 线程回放 Relay Log。

核心特点：

- 默认是异步复制。
- 主从会有延迟（秒级到分钟级，异常时更高）。

## 2. 常见复制模式

1. 异步复制：性能好，主库提交不等从库确认。
2. 半同步复制：主库至少等一个从库确认再返回，可靠性更强。
3. 组复制/多主集群：复杂度更高，适合特定场景。

## 3. 复制拓扑

1. 一主一从：简单，容灾能力有限。
2. 一主多从：最常见，读扩展好。
3. 级联复制：跨地域降低主库压力。

## 4. 读写分离

典型规则：

- 写请求走主库。
- 读请求走从库。
- 强一致读（刚写后立即读）走主库。

“刚写就读”不一致问题常见解决方案：

1. 关键读强制走主库。
2. 写后短时间内读主库（会话级策略）。
3. 业务接受短暂最终一致。

## 5. 复制的常见坑

1. 主从延迟导致脏读。
2. 大事务回放慢。
3. DDL 导致复制阻塞。
4. 主从切换后路由未及时更新。

建议监控：

1. `Seconds_Behind_Master`。
2. Binlog/Relay Log 积压。
3. 从库 SQL 线程状态。

## 三、分片（Sharding）详细讲解

## 1. 分片有两种

1. 垂直拆分：按业务域拆库（用户库、订单库、库存库）。
2. 水平拆分：同一张表按规则拆到多个库表。

实战里通常先垂直，再水平。

## 2. 水平分片的分片键

分片键是最关键设计。

常见选择：

1. `user_id`：按用户维度查询多，均衡较好。
2. `order_id`：唯一性强，但按用户查单可能跨分片。
3. 组合键：更灵活但路由更复杂。

好分片键标准：

1. 分布均匀。
2. 高频查询可命中单分片。
3. 不易形成热点。

## 3. 分片算法

1. 取模：`shard = key % N`，简单但扩容迁移成本高。
2. 范围：按 ID/时间段，利于归档但易热点。
3. 一致性哈希：扩容迁移更平滑，复杂度高一些。

## 4. 路由层怎么做

需要一层路由中间件或应用内路由逻辑：

1. 根据分片键算目标库表。
2. 执行 SQL。
3. 聚合结果（跨分片时）。

常见方案：

1. 应用层自己路由（灵活但开发成本高）。
2. 中间件路由（ShardingSphere、MyCat 等）。

## 5. 分片后的常见难题

1. 跨分片 `JOIN` 困难。
2. 跨分片分页困难。
3. 全局排序困难。
4. 分布式事务复杂。
5. 全局唯一 ID 需要额外方案。

应对思路：

1. 避免跨分片 JOIN，改冗余字段。
2. 分页用游标，不做深分页。
3. 强依赖聚合的查询放搜索/OLAP。
4. 事务用最终一致 + 补偿。

---

## 四、复制和分片怎么组合

最常见组合是：

1. 每个分片内部再做主从复制。
2. 写进分片主库，读走分片从库。

结构类似：

```text
Shard-0: master + replicas
Shard-1: master + replicas
Shard-2: master + replicas
```

这样可以同时拿到：

- 分片的写扩展能力。
- 复制的读扩展和高可用能力。

---

## 五、迁移与扩容（最容易翻车的环节）

## 1. 从单库迁移到分片的步骤

1. 设计分片规则和路由层。
2. 新老双写（短期）。
3. 历史数据回填。
4. 校验一致性。
5. 切读流量。
6. 切写流量。
7. 下线旧路径。

## 2. 在线扩容要点

1. 预留扩容策略（避免纯取模硬绑定）。
2. 做数据迁移工具和限速。
3. 迁移期间双写或变更捕获（CDC）。
4. 全程可观测、可回滚。

---

## 六、全局 ID 设计

分片后不能依赖单表自增主键做全局唯一。

常见方案：

1. 雪花算法（时间 + 机器 + 序列）。
2. 号段模式（批量取号）。
3. UUID（简单但索引局部性差）。

业务上通常更推荐雪花或号段。

---

## 七、事务与一致性怎么做

分片后跨库事务成本高，不建议重度依赖 2PC。

实用方案：

1. 单分片内强事务。
2. 跨分片用消息最终一致。
3. 配套幂等 + 补偿任务 + 对账。

核心原则：

> 把强一致范围缩到最小，把最终一致链路补齐。

---

## 八、监控与告警指标

复制和分片至少监控这些：

1. 主从延迟。
2. 分片 QPS/延迟分布。
3. 热点分片占比。
4. 慢 SQL 数量。
5. 连接池使用率。
6. 锁等待和死锁数。

如果只看总指标，不看“分片维度”，你会漏掉热点问题。

---

## 九、实战选型建议

### 小中型系统

1. 单库 + 主从复制。
2. 读写分离。
3. 重点做索引和缓存。

### 中大型系统

1. 业务垂直拆分。
2. 关键大表水平分片。
3. 每分片内部主从。
4. 建立数据迁移与对账能力。

---

## 十、常见误区

1. 过早分片，复杂度爆炸。
2. 只做分片，不做运维自动化。
3. 忽视主从延迟对业务读一致性的影响。
4. 分片键选错导致热点。
5. 没有迁移回滚预案。

---

## 总结

复制和分片不是“高级功能”，而是数据库扩展的必经之路。

你可以把落地顺序记成一句话：

1. 先优化。
2. 再复制。
3. 后分片。
4. 最后把迁移、监控、补偿体系补齐。

这样做，系统扩展会稳得多，也更可控。

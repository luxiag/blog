SQL（Structured Query Language）是**关系型数据库**的通用语言。你可以用它：

- 管数据（建表、加约束）
- 改数据（插入、更新、删除）
- 查数据（查询、筛选、排序、统计）

本文目标：让你在读完后能把 SQL 当成一门"表达数据问题"的语言，写出**正确、可读、可维护、可优化**的查询。这是整个系列的地基——后面的练习、性能优化、数据库专精，都建立在这里讲清楚的概念之上。

## 1. 先建立 SQL 的整体认知

### 1.1 关系型数据库在解决什么问题？

关系型数据库（RDBMS）把数据组织成"表（Table）"，表由"行（Row）"和"列（Column）"组成。

- 列：字段含义与类型（例如 `price` 是数值）
- 行：一条记录（例如一笔订单）
- 主键：唯一标识一行（例如 `id`）
- 外键：建立表与表之间关系（例如 `orders.user_id -> users.id`）

SQL 的核心是：**用集合（set）的方式处理数据**。

### 1.2 SQL 的两大类工作

- **DDL**（定义结构）：`CREATE` / `ALTER` / `DROP`
- **DML**（写入/修改/删除）：`INSERT` / `UPDATE` / `DELETE`
- **DQL**（查询）：`SELECT`
- **DCL**（权限控制）：`GRANT` / `REVOKE`
- **TCL**（事务控制）：`BEGIN` / `COMMIT` / `ROLLBACK`

### 1.3 SQL 语法约定

写 SQL 之前，先了解几条基本规则：

- **分号结尾**：每条 SQL 语句以 `;` 结束。一次可以发送多条语句。
- **不区分大小写**：`SELECT`、`select`、`Select` 效果相同，但**关键字大写、表名/列名小写**是广泛推荐的风格。
- **三种注释**：
  ```sql
  -- 单行注释（推荐）
  # 单行注释（MySQL 特有，其他数据库不支持）
  /* 多行
     注释 */
  ```
- **缩进与换行**：SQL 可以单行也可以多行书写，用空格和缩进来提高可读性。

## 2. 数据类型：表里能存什么

选对数据类型能节省存储空间、提升查询性能、避免隐式转换的坑。

### 2.1 数值类型

| 类型 | 大小 | 范围 | 适用场景 |
|------|------|------|----------|
| `TINYINT` | 1 字节 | -128 ~ 127 | 枚举值、小标志位 |
| `SMALLINT` | 2 字节 | -32768 ~ 32767 | 较小的计数 |
| `INT` / `INTEGER` | 4 字节 | -21 亿 ~ 21 亿 | 最常用的整数主键、数量 |
| `BIGINT` | 8 字节 | 极大 | 大表主键、分布式 ID |
| `DECIMAL(p, s)` | 可变 | 精确小数 | **金额必须用这个**，不能用浮点 |
| `REAL` / `DOUBLE` | 4/8 字节 | 浮点数 | 科学计算，有精度损失 |

:::warning 金额字段用 DECIMAL，绝不用 FLOAT/DOUBLE
`0.1 + 0.2` 在浮点类型中不等于 `0.3`，这在金融场景中不可接受。`DECIMAL(10,2)` 表示最多 10 位数、2 位小数。
:::

### 2.2 字符串类型

| 类型 | 说明 | 适用场景 |
|------|------|----------|
| `CHAR(n)` | 固定 n 个字符，不足补空格 | 固定长度（如身份证号、国家代码） |
| `VARCHAR(n)` | 变长，最多 n 个字符 | **最常用**，用户名、邮箱等 |
| `TEXT` | 无限长度字符串 | 文章正文、长描述 |
| `BLOB` | 二进制大对象 | 图片、文件（通常不推荐存数据库） |

### 2.3 日期时间类型

| 类型 | 格式 | 说明 |
|------|------|------|
| `DATE` | `YYYY-MM-DD` | 仅日期 |
| `TIME` | `HH:MM:SS` | 仅时间 |
| `DATETIME` | `YYYY-MM-DD HH:MM:SS` | 日期+时间，不含时区 |
| `TIMESTAMP` | `YYYY-MM-DD HH:MM:SS` | 日期+时间，含时区（转为 UTC 存储） |

:::tip 时间字段推荐用 TIMESTAMP
`TIMESTAMP` 会自动转为 UTC 存储、读取时根据会话时区转换。`DATETIME` 不做时区转换，在多时区应用中容易出 bug。
:::

### 2.4 其他类型

| 类型 | 说明 |
|------|------|
| `BOOLEAN` | 逻辑值，大部分数据库实现为 `0/1` |
| `JSON` / `JSONB` | 结构化数据（PostgreSQL 的 `jsonb` 支持索引，性能远优于 `json`） |
| `ENUM` | 枚举值，只能取预定义的值（MySQL 原生支持） |

## 3. 示例数据

为方便演示，假设你有以下表：

```sql
CREATE TABLE users (
  id        BIGINT PRIMARY KEY,
  name      VARCHAR(50) NOT NULL,
  email     VARCHAR(200) NOT NULL,
  created_at TIMESTAMP NOT NULL
);

CREATE TABLE products (
  id    BIGINT PRIMARY KEY,
  name  VARCHAR(100) NOT NULL,
  price DECIMAL(10,2) NOT NULL
);

CREATE TABLE orders (
  id         BIGINT PRIMARY KEY,
  user_id    BIGINT NOT NULL,
  status     VARCHAR(20) NOT NULL,
  created_at TIMESTAMP NOT NULL
);

CREATE TABLE order_items (
  order_id   BIGINT NOT NULL,
  product_id BIGINT NOT NULL,
  quantity   INT NOT NULL,
  unit_price DECIMAL(10,2) NOT NULL,
  PRIMARY KEY (order_id, product_id)
);
```

你不需要立刻跑起来，先理解结构：

- `users` 一对多 `orders`
- `orders` 一对多 `order_items`
- `products` 一对多 `order_items`

## 4. 建表与约束：把规则写进数据库

### 4.1 DDL：创建与修改表

**创建数据库**

```sql
CREATE DATABASE mydb;
-- 安全写法：已存在则跳过
CREATE DATABASE IF NOT EXISTS mydb;
```

**创建表**

```sql
CREATE TABLE users (
  id         BIGINT PRIMARY KEY,
  name       VARCHAR(50) NOT NULL,
  email      VARCHAR(200) NOT NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

**修改表结构（ALTER TABLE）**

```sql
-- 添加列
ALTER TABLE users ADD phone VARCHAR(20);

-- 修改列类型
ALTER TABLE users MODIFY email VARCHAR(300);

-- 删除列
ALTER TABLE users DROP COLUMN phone;

-- 重命名列（标准 SQL，MySQL 用 CHANGE）
ALTER TABLE users RENAME COLUMN name TO username;
```

**删除表 / 清空表**

```sql
DROP TABLE users;              -- 删除表结构和数据
DROP TABLE IF EXISTS users;    -- 安全写法
TRUNCATE TABLE users;          -- 保留表结构，只清空数据（比 DELETE 快）
```

### 4.2 约束：确保数据正确

**NOT NULL：不允许为空**

```sql
CREATE TABLE users (
  id   INT NOT NULL,
  name VARCHAR(100) NOT NULL,
  email VARCHAR(100)  -- 允许为空
);
```

**UNIQUE：列值不能重复**

```sql
CREATE TABLE users (
  id       INT PRIMARY KEY,
  username VARCHAR(50) UNIQUE,
  email    VARCHAR(100) UNIQUE
);
```

**PRIMARY KEY：唯一且不为空**

一个表只能有一个主键，它隐式包含 NOT NULL + UNIQUE：

```sql
CREATE TABLE users (
  id   INT AUTO_INCREMENT,  -- MySQL 用 AUTO_INCREMENT，PG 用 SERIAL
  name VARCHAR(50),
  PRIMARY KEY (id)
);
```

**FOREIGN KEY：引用完整性**

确保子表的值必须在父表中存在：

```sql
CREATE TABLE orders (
  id      BIGINT PRIMARY KEY,
  user_id BIGINT NOT NULL,
  FOREIGN KEY (user_id) REFERENCES users(id)
);
```

**CHECK：检查值的合法性**

```sql
CREATE TABLE products (
  id    INT PRIMARY KEY,
  name  VARCHAR(100),
  price DECIMAL(10,2) CHECK (price > 0)
);
```

**DEFAULT：设置默认值**

```sql
CREATE TABLE users (
  id    INT PRIMARY KEY,
  name  VARCHAR(50),
  age   INT DEFAULT 18
);
```

把规则写在数据库里，比在应用层校验更可靠——即使有人绕过了你的应用，数据库也会拒绝不合法的数据。

## 5. 写数据：INSERT / UPDATE / DELETE

### 5.1 INSERT

```sql
-- 插入单条
INSERT INTO users (id, name, email, created_at)
VALUES (1, 'Alice', 'alice@example.com', '2026-01-01');

-- 一次插入多条（所有数据库通用）
INSERT INTO users (id, name, email, created_at) VALUES
  (2, 'Bob', 'bob@example.com', '2026-01-02'),
  (3, 'Charlie', 'charlie@example.com', '2026-01-03');
```

**INSERT ... SELECT：从查询结果批量插入**

把一张表的数据"搬"到另一张表，或者把查询结果作为新数据插入：

```sql
-- 把旧表的数据搬到新表
INSERT INTO users_backup (id, name, email)
SELECT id, name, email
FROM users
WHERE created_at < '2025-01-01';

-- 创建表时顺便灌数据（部分数据库支持）
CREATE TABLE active_users AS
SELECT * FROM users WHERE is_active = true;
```

这在数据迁移、备份、创建汇总表时非常常用。

### 5.2 UPDATE

```sql
UPDATE orders
SET status = 'SHIPPED'
WHERE id = 1001;
```

强烈建议：写 `UPDATE/DELETE` 之前先把 `WHERE` 拿去跑一遍 `SELECT`，确认影响范围。

**UPDATE ... JOIN：跨表更新**

用另一张表的值来更新当前表，非常实用：

```sql
-- MySQL 写法：根据 users 表的最新邮箱更新 orders 表的冗余字段
UPDATE orders o
JOIN users u ON u.id = o.user_id
SET o.user_name = u.name
WHERE o.user_name IS NULL;

-- PostgreSQL / SQL Server 写法（FROM 子句）
UPDATE orders
SET user_name = u.name
FROM users u
WHERE orders.user_id = u.id AND orders.user_name IS NULL;
```

:::tip MySQL vs PG 的 UPDATE JOIN 语法不同
MySQL 用 `UPDATE ... JOIN ... SET`，PG 用 `UPDATE ... SET ... FROM ...`。跨数据库开发时要注意这个差异。
:::

批量更新不同值可以用 `CASE WHEN`：

```sql
-- 根据不同 ID 设置不同的名字
UPDATE users
SET name = CASE id
  WHEN 1 THEN 'new_name1'
  WHEN 2 THEN 'new_name2'
  WHEN 3 THEN 'new_name3'
END
WHERE id IN (1, 2, 3);
```

### 5.3 DELETE

```sql
DELETE FROM orders
WHERE id = 1001;
```

### 5.4 UPSERT（插入或更新）

- PostgreSQL：`INSERT ... ON CONFLICT ... DO UPDATE`
- MySQL：`INSERT ... ON DUPLICATE KEY UPDATE`
- SQL Server：常用 `MERGE`（需谨慎）

这是典型的"方言差异"，写文章/做项目时要确认你的数据库。

## 6. 查询基础：SELECT / WHERE / ORDER BY

### 6.1 SELECT 的基本结构

```sql
SELECT 列1, 列2
FROM 表
WHERE 条件
ORDER BY 排序列
LIMIT n;
```

一个常见的顺序认知：

- 你写的时候通常是 `SELECT -> FROM -> WHERE ...`
- 数据库执行时的逻辑顺序更像 `FROM -> WHERE -> GROUP BY -> HAVING -> SELECT -> ORDER BY -> LIMIT`

理解逻辑顺序可以帮你解释很多"为什么不能在 WHERE 里用别名"等问题。

### 6.2 选择列、别名与去重

**选择列**：不是每次都需要 `SELECT *`，明确指定你需要的列：

```sql
-- ❌ 查所有列，浪费带宽，还可能拿到不需要的敏感字段
SELECT * FROM users;

-- ✅ 只取需要的列
SELECT name, email FROM users;
```

**别名（AS）**：给列或表起一个临时名字，让结果更可读，或者简化后续引用：

```sql
-- 给列起别名：让输出标题更清晰
SELECT
  name AS 用户名,
  email AS 邮箱
FROM users;

-- 给表起别名：让 JOIN 写起来更短
SELECT u.name, o.status
FROM users u              -- u 是 users 的别名
JOIN orders o ON o.user_id = u.id;  -- o 是 orders 的别名
```

起别名后，后续的 `WHERE`、`ORDER BY` 等子句**不能用列别名**（因为逻辑执行顺序中 `SELECT` 比 `WHERE` 晚），但 `ORDER BY` 例外（大部分数据库支持）：

```sql
-- ❌ 报错：WHERE 里不能用列别名
SELECT name, age AS user_age FROM users WHERE user_age > 25;

-- ✅ 正确写法：WHERE 用原始列名
SELECT name, age AS user_age FROM users WHERE age > 25;

-- ✅ ORDER BY 可以用别名（大部分数据库）
SELECT name, age AS user_age FROM users ORDER BY user_age DESC;
```

**去重（DISTINCT）**：查询结果可能有重复行，用 `DISTINCT` 去掉：

```sql
-- orders 表里 status 可能有多个 'PAID'
SELECT status FROM orders;
-- 结果：PAID, PAID, PENDING, SHIPPED  ← PAID 出现两次

-- 加 DISTINCT 去重
SELECT DISTINCT status FROM orders;
-- 结果：PAID, PENDING, SHIPPED  ← 每个值只出现一次

-- 多列去重：组合不重复才保留
SELECT DISTINCT user_id, status FROM orders;
```

### 7.2 分组拼接：GROUP_CONCAT / STRING_AGG

有时你需要把分组内的多个值拼成一个字符串——比如"查出每个用户的标签列表"。

```sql
-- MySQL：GROUP_CONCAT
SELECT user_id, GROUP_CONCAT(tag SEPARATOR ', ') AS tags
FROM user_tags
GROUP BY user_id;

-- PostgreSQL / SQL Server：STRING_AGG
SELECT user_id, STRING_AGG(tag, ', ') AS tags
FROM user_tags
GROUP BY user_id;
```

结果可能像：

| user_id | tags |
|---------|------|
| 1 | vip, new, active |
| 2 | vip |

也可以配合 `DISTINCT` 去重、`ORDER BY` 排序：

```sql
-- MySQL：去重 + 排序
SELECT user_id, GROUP_CONCAT(DISTINCT tag ORDER BY tag SEPARATOR ', ') AS tags
FROM user_tags
GROUP BY user_id;

-- PostgreSQL：去重 + 排序
SELECT user_id, STRING_AGG(tag, ', ' ORDER BY tag) AS tags
FROM user_tags
GROUP BY user_id;
```

:::tip 为什么不在 SELECT 里直接拼？
`GROUP_CONCAT` / `STRING_AGG` 是**聚合函数**，必须配合 `GROUP BY` 使用。它把一个分组内的多行"压缩"成一个字符串，和 `COUNT`、`SUM` 本质一样——都是对分组结果的加工。
:::

区别：

- `WHERE` 过滤"行"
- `HAVING` 过滤"分组后的结果"

## 8. 常用函数

SQL 内置了大量函数，下面列出日常开发中最常用的。注意：不同数据库的函数名可能有差异，这里以通用写法为准。

### 8.1 数学函数

| 函数 | 作用 | 示例 |
|------|------|------|
| `ABS(x)` | 绝对值 | `ABS(-10)` → `10` |
| `ROUND(x, d)` | 四舍五入到 d 位小数 | `ROUND(3.14159, 2)` → `3.14` |
| `CEIL(x)` / `CEILING(x)` | 向上取整 | `CEIL(3.1)` → `4` |
| `FLOOR(x)` | 向下取整 | `FLOOR(3.9)` → `3` |
| `MOD(a, b)` | 取余 | `MOD(10, 3)` → `1` |
| `POWER(x, y)` | 幂运算 | `POWER(2, 3)` → `8` |
| `SQRT(x)` | 平方根 | `SQRT(9)` → `3` |

### 8.2 字符串函数

| 函数 | 作用 | 示例 |
|------|------|------|
| `LENGTH(s)` | 字符串长度 | `LENGTH('hello')` → `5` |
| `CONCAT(s1, s2, ...)` | 拼接字符串 | `CONCAT('Hello', ' ', 'World')` → `'Hello World'` |
| `SUBSTRING(s, start, len)` | 截取子串 | `SUBSTRING('Hello', 1, 3)` → `'Hel'` |
| `UPPER(s)` / `LOWER(s)` | 大小写转换 | `UPPER('hello')` → `'HELLO'` |
| `TRIM(s)` | 去除首尾空格 | `TRIM('  hi  ')` → `'hi'` |
| `REPLACE(s, from, to)` | 替换子串 | `REPLACE('aabb', 'a', 'x')` → `'xxbb'` |
| `LEFT(s, n)` / `RIGHT(s, n)` | 取左边/右边 n 个字符 | `LEFT('Hello', 3)` → `'Hel'` |
| `CHAR_LENGTH(s)` | 字符数（多字节安全） | `CHAR_LENGTH('你好')` → `2` |

### 8.3 日期时间函数

| 函数 | 作用 | 说明 |
|------|------|------|
| `NOW()` / `CURRENT_TIMESTAMP` | 当前日期时间 | 大多数数据库都支持 |
| `CURRENT_DATE` | 当前日期 | 只有日期部分 |
| `YEAR(d)` / `MONTH(d)` / `DAY(d)` | 提取年/月/日 | `YEAR('2026-05-11')` → `2026` |
| `DATE_TRUNC('month', d)` | 截断到指定精度 | PG/MySQL 8+：`DATE_TRUNC('month', NOW())` 月初 |
| `EXTRACT(part FROM d)` | 提取日期部分 | `EXTRACT(DOW FROM NOW())` 星期几（标准 SQL） |
| `INTERVAL 'n unit'` | 时间间隔 | `NOW() - INTERVAL '30 DAY'` 30 天前 |

不同数据库的日期函数差异较大，这是方言差异最集中的地方之一（参见 Section 19）。

### 8.4 流程控制函数

```sql
-- IF：二选一
SELECT name, IF(age >= 18, '成年', '未成年') AS status FROM users;

-- CASE WHEN：多选一（标准 SQL，所有数据库通用）
SELECT name,
  CASE
    WHEN score >= 90 THEN '优秀'
    WHEN score >= 70 THEN '良好'
    WHEN score >= 60 THEN '及格'
    ELSE '不及格'
  END AS grade
FROM students;

-- COALESCE：返回第一个非 NULL 值
SELECT COALESCE(nickname, username, 'Anonymous') AS display_name FROM users;

-- NULLIF：两个值相等时返回 NULL
SELECT NULLIF(a, b);  -- 如果 a = b 则返回 NULL，否则返回 a
```

`CASE WHEN` 是 SQL 中最强大的条件表达式，在 SELECT、WHERE、ORDER BY 中都能用。窗口函数里的条件聚合（`SUM(CASE WHEN ... THEN ... END)`）也依赖它。

### 8.5 类型转换：CAST 与隐式转换

SQL 中经常需要在不同类型之间转换，比如把字符串转成数字、把日期转成字符串。

**显式转换（推荐）**

```sql
-- 标准 SQL 写法
CAST(expression AS type)

-- PostgreSQL 简写
expression::type
```

```sql
-- 把字符串转成数字
SELECT CAST('123' AS INTEGER);          -- 123
SELECT '456'::INTEGER;                  -- 456（PG 简写）

-- 把数字转成字符串
SELECT CAST(price AS CHAR) FROM products;  -- MySQL
SELECT price::TEXT FROM products;           -- PG

-- 把字符串转成日期
SELECT CAST('2026-05-11' AS DATE);      -- 2026-05-11
SELECT '2026-05-11'::DATE;              -- PG 简写

-- 用 TRY_CAST 避免转换失败报错（SQL Server / PG 16+）
SELECT TRY_CAST('abc' AS INTEGER);      -- 返回 NULL，不报错
```

**隐式转换（要警惕）**

数据库在某些场景会自动做类型转换，但这**非常危险**：

```sql
-- 假设 phone 是 VARCHAR 类型
-- ❌ 传入数字，数据库把每行的 phone 转成数字再比，索引失效
SELECT * FROM users WHERE phone = 13800138000;

-- ✅ 类型对齐
SELECT * FROM users WHERE phone = '13800138000';

-- ❌ 字符串和数字混用，可能导致全表扫描
SELECT * FROM orders WHERE id = '1001';  -- id 是 INT
```

:::warning 隐式转换是索引失效的常见原因
当查询条件的类型和列的类型不匹配时，数据库会对**每行**做类型转换再比较，等于对列做了函数，索引就废了。养成习惯：**字符串值加引号，数字值不加引号，类型对齐再比较。**
:::

## 9. 多表查询：JOIN 连接

JOIN 是 SQL 的核心能力之一：把分散在不同表的数据拼成你需要的结果。

**为什么需要 JOIN？** 数据库为了减少冗余，会把数据拆到不同的表里（这就是"规范化"）。但查询时你经常需要把它们拼回来——比如"用户名 + 他的订单"，就需要把 `users` 表和 `orders` 表连起来。

**JOIN 的本质**：根据一个关联键（通常是 `id` 和 `xxx_id`），把两张表的行"配对"。

```sql
-- 概念模型：把 users 的每一行，和 orders 中 user_id 匹配的行拼在一起
SELECT 用户列, 订单列
FROM users
JOIN orders ON users.id = orders.user_id;
```

### 9.3 RIGHT JOIN（右表全保留）

RIGHT JOIN 和 LEFT JOIN 方向相反：保留**右表**的所有行，左表无匹配则补 NULL。

```sql
-- 查出所有订单及对应下单人（哪怕有些订单找不到用户也列出来）
SELECT o.id AS order_id, u.name AS user_name
FROM users u
RIGHT JOIN orders o ON o.user_id = u.id;
```

:::tip 实际使用中 RIGHT JOIN 较少
绝大多数场景下，你只需要 LEFT JOIN——把主要的表放在 FROM 后面（左表），用 LEFT JOIN 关联其他表。RIGHT JOIN 在逻辑上等价于交换两张表的位置再用 LEFT JOIN，所以实际写 SQL 时 LEFT JOIN 用得更多。
:::

### 9.4 SELF JOIN（自连接）

一张表和自己做 JOIN，适合处理层级关系（如员工-上级、评论-父评论）。

```sql
-- 查询员工及其上级的名字
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;
```

自连接的关键是**给同一张表起两个别名**，让数据库把它当作两张"不同的表"来处理。

### 9.5 JOIN 常见坑：把条件写错位置

如果，你想查"所有用户及其已支付订单（没有也要出现）"，这两句不等价：

```sql
SELECT u.id, u.name, o.id AS order_id
FROM users u
LEFT JOIN orders o
  ON o.user_id = u.id
 AND o.status = 'PAID';
```

```sql
SELECT u.id, u.name, o.id AS order_id
FROM users u
LEFT JOIN orders o
  ON o.user_id = u.id
WHERE o.status = 'PAID';
```

第二句会把 `LEFT JOIN` 变得更像 `INNER JOIN`（因为 `WHERE o.status='PAID'` 会过滤掉 `NULL` 行）。

## 10. 子查询：把一个查询当成条件或表

子查询就是**嵌套在另一个查询里的查询**。把它想象成"先算一个小问题，再用小问题的结果去算大问题"。

```sql
-- 外层查询
SELECT name FROM users
WHERE id IN (
  -- 这是子查询：先算出"下过单的用户 ID 列表"
  SELECT DISTINCT user_id FROM orders
);
```

**子查询可以放在哪些位置？**
- `WHERE` 里：作为过滤条件（如 `IN`、`EXISTS`、比较运算符旁边）
- `FROM` 里：当作一张"临时表"（叫派生表）
- `SELECT` 里：返回单个值（标量子查询）

查"下过单的用户"：


经验法则：

- `IN` 更像"把一堆值拿来比对"
- `EXISTS` 更像"对每个外层行判断是否存在匹配"

数据库优化器会做很多优化，但 `EXISTS` 常更稳健。

### 10.3 标量子查询：返回单个值

子查询返回一个值（一行一列），用在比较运算符旁边：

```sql
-- 查出比平均价格贵的商品
SELECT name, price
FROM products
WHERE price > (SELECT AVG(price) FROM products);
```

### 10.4 IN 与 ANY / ALL：返回一列值

子查询返回一列值时，除了 `IN`，还可以用 `ANY`（任一）和 `ALL`（全部）：

```sql
-- 比"IT 部门"任意一个人年龄大的员工
SELECT name, age FROM employees
WHERE age > ANY (SELECT age FROM employees WHERE department = 'IT');

-- 比"IT 部门"所有人年龄都大的员工
SELECT name, age FROM employees
WHERE age > ALL (SELECT age FROM employees WHERE department = 'IT');
```

### 10.5 派生表（FROM 子查询）：把子查询当表用

子查询放在 `FROM` 后面时，必须起别名，它会作为一个临时结果集参与查询：

```sql
-- 先算出每个用户的总消费，再从中筛选
SELECT user_id, total_spent
FROM (
  SELECT user_id, SUM(amount) AS total_spent
  FROM orders
  GROUP BY user_id
) AS user_totals
WHERE total_spent > 500;
```

> 当查询变复杂时，用 CTE（Section 12）替代派生表通常更可读。

## 11. 集合运算：UNION / INTERSECT / EXCEPT

把两个查询结果"拼接/取交集/取差集"。

**生活类比**：你有两个购物清单 A 和 B——
- `UNION`：把两个清单合并成一个（去重）
- `UNION ALL`：把两个清单合并（保留重复项，更快）
- `INTERSECT`：找出两个清单里**都有**的东西
- `EXCEPT`：找出 A 有但 B 没有的东西

```sql
-- UNION：合并两个查询的结果，自动去重
SELECT name FROM employees
UNION
SELECT name FROM contractors;

-- UNION ALL：不去重，性能更好（推荐在确定无重复或不需要去重时用）
SELECT name FROM employees
UNION ALL
SELECT name FROM contractors;

-- INTERSECT：取交集（两个查询都有的行）
SELECT name FROM employees
INTERSECT
SELECT name FROM contractors;

-- EXCEPT：取差集（第一个查询有、第二个没有的行）
SELECT name FROM employees
EXCEPT
SELECT name FROM contractors;
```

:::tip UNION 的列数和类型要匹配
两个 `SELECT` 语句的列数必须相同，对应列的数据类型要兼容（比如不能一列是字符串、另一列是数字）。
:::

## 12. CTE：WITH 让复杂 SQL 更可读

CTE（Common Table Expression）可以把查询拆成"可命名的步骤"，就像给中间结果起个名字，后面可以直接用。

**没有 CTE 时**，子查询嵌套很深，难以阅读：

```sql
-- 嵌套子查询：难以理解
SELECT user_id, COUNT(*) FROM (
  SELECT user_id FROM orders WHERE status = 'PAID'
) AS paid_orders GROUP BY user_id;
```

**有 CTE 后**，每一步都有名字，逻辑清晰：

```sql
-- CTE：先定义"已支付订单"，再对它统计
WITH paid_orders AS (
  SELECT user_id FROM orders WHERE status = 'PAID'
)
SELECT user_id, COUNT(*) FROM paid_orders GROUP BY user_id;
```

**核心语法**：

```sql
WITH cte名称 AS (
  -- 先执行这个查询，结果命名为 cte名称
  SELECT ...
)
-- 再用 cte名称 作为"临时表"
SELECT ... FROM cte名称;
```

可以定义多个 CTE，用逗号分隔：

```sql
WITH
active_users AS (SELECT * FROM users WHERE is_active = true),
paid_orders AS (SELECT * FROM orders WHERE status = 'PAID')
SELECT u.name, COUNT(o.id)
FROM active_users u
JOIN paid_orders o ON o.user_id = u.id
GROUP BY u.name;
```

CREATE TABLE orders (id INT, user_id INT, status TEXT);
INSERT INTO orders VALUES (101, 1, 'PAID'), (102, 1, 'PAID'), (103, 2, 'PENDING'), (104, 3, 'SHIPPED');
`;

  title="练习：CTE 公共表表达式"
  description="使用 WITH 语句将复杂查询拆分为可命名的步骤"
/>

很多场景下 CTE 主要提升可读性；不同数据库对 CTE 的优化策略不同。

### 12.1 递归 CTE：处理树形和层级数据

普通 CTE 只执行一次，但**递归 CTE** 可以引用自身，反复执行直到满足终止条件。它专门用来处理**层级/树形结构**——组织架构、评论楼中楼、物料清单、省市区三级联动等。

**核心语法**：

```sql
WITH RECURSIVE cte名称 AS (
  -- 1) 锚定部分：初始查询（非递归，只执行一次）
  SELECT ...
  UNION ALL
  -- 2) 递归部分：引用自身的查询（反复执行，直到没有新行产生）
  SELECT ... FROM cte名称 WHERE ...
)
SELECT * FROM cte名称;
```

递归 CTE 的执行过程：

1. 执行锚定查询，得到初始行集
2. 用上一步的结果执行递归查询，得到新行
3. 把新行追加到结果集，再用新行执行递归查询
4. 重复步骤 2~3，直到递归查询不再产生新行
5. 返回所有步骤累积的最终结果

**示例 1：员工层级——查出某员工及其所有下属**

假设 `employees` 表有 `id, name, manager_id`（`manager_id` 指向上级的 `id`，顶级上司的 `manager_id` 为 `NULL`）：

```sql
WITH RECURSIVE emp_chain AS (
  -- 锚定：从 CEO 开始
  SELECT id, name, manager_id, 1 AS level
  FROM employees
  WHERE id = 1  -- CEO 的 id

  UNION ALL

  -- 递归：找当前层每个人的下属
  SELECT e.id, e.name, e.manager_id, ec.level + 1
  FROM employees e
  JOIN emp_chain ec ON e.manager_id = ec.id
)
SELECT id, name, level
FROM emp_chain
ORDER BY level, id;
```

结果示例：

| id | name | level |
|----|------|-------|
| 1  | CEO  | 1     |
| 2  | VP Engineering | 2 |
| 3  | VP Sales | 2    |
| 5  | Alice | 3     |
| 6  | Bob   | 3     |

`level` 列是递归过程中累加的，让你知道每个人在第几层。

**示例 2：评论楼中楼——查出某条评论及其所有回复**

```sql
WITH RECURSIVE comment_tree AS (
  -- 锚定：根评论
  SELECT id, parent_id, content, 0 AS depth
  FROM comments
  WHERE id = 1001

  UNION ALL

  -- 递归：找当前层评论的所有回复
  SELECT c.id, c.parent_id, c.content, ct.depth + 1
  FROM comments c
  JOIN comment_tree ct ON c.parent_id = ct.id
)
SELECT id, content, depth
FROM comment_tree
ORDER BY depth, id;
```

**示例 3：生成序列——1 到 100 的数字**

递归 CTE 不一定要查表，也可以用来生成数据：

```sql
WITH RECURSIVE nums AS (
  SELECT 1 AS n
  UNION ALL
  SELECT n + 1 FROM nums WHERE n < 100
)
SELECT n FROM nums;
```

:::warning 递归 CTE 的安全限制
如果递归逻辑写错（比如终止条件永远不满足），理论上会无限循环。数据库都有保护机制：

- PostgreSQL：默认递归上限 100 次（`max_recursion` 参数）
- MySQL 8.0：默认上限 1000 次（`cte_max_recursion_depth` 参数）
- SQL Server：默认上限 100 次（`MAXRECURSION` 提示）

如果确实需要更深的递归，需要显式调大参数。但更多时候，递归超限说明你的数据或逻辑有问题。
:::

:::tip MySQL 的语法细节
MySQL 8.0+ 才支持递归 CTE，且必须写 `WITH RECURSIVE`。PostgreSQL 和 SQL Server 也要求 `WITH RECURSIVE`（SQL Server 用 `OPTION (MAXRECURSION n)` 控制深度）。SQLite 3.8.3+ 支持。
:::

export const recursiveCteInitSql = `

## 13. 窗口函数：统计但不"折叠"行

**普通聚合（GROUP BY）会把多行"折叠"成一行**，丢失了原始行的细节。窗口函数可以在**保留每一行**的同时，做分组统计、排名、累计等计算。

```
原始数据：          GROUP BY 的结果：      窗口函数的结果：
Alice  100    →    Alice  500     →     Alice  100  累计 100
Alice  200         Bob    300          Alice  200  累计 300
Alice  200                              Alice  200  累计 500
Bob    300                              Bob    300  累计 300
```

**核心语法**：

```sql
窗口函数() OVER (
  PARTITION BY 分组列   -- 按什么分组（可省略，表示整个结果集）
  ORDER BY 排序列       -- 组内按什么排序
  ROWS/RANGE ...        -- 窗口框架（可省略，默认是当前行到最前面）
)
```

### 13.1 ROW_NUMBER：在分组内编号

比如：每个用户的最近一笔订单。

`;

### 13.2 SUM OVER：累计求和

窗口函数是从"会写查询"到"写得很强"的分水岭，建议专门练。

### 13.3 窗口框架：ROWS vs RANGE

窗口函数的 `OVER` 子句里，除了 `PARTITION BY` 和 `ORDER BY`，还可以指定**窗口框架**——即"当前行的前后多少行参与计算"。

```sql
-- ROWS 模式：物理行，固定数量
SUM(amount) OVER (
  ORDER BY created_at
  ROWS BETWEEN 2 PRECEDING AND CURRENT ROW  -- 当前行 + 前 2 行
)

-- RANGE 模式：逻辑范围，基于 ORDER BY 列的值
SUM(amount) OVER (
  ORDER BY created_at
  RANGE BETWEEN INTERVAL '7 day' PRECEDING AND CURRENT ROW  -- 7 天内的行
)

-- GROUPS 模式：按分组后的组数（PG 11+、Oracle 支持）
SUM(amount) OVER (
  ORDER BY created_at
  GROUPS BETWEEN 1 PRECEDING AND 1 FOLLOWING  -- 前一组、当前组、后一组
)
```

**三者的核心区别：**

| 模式 | 含义 | 典型场景 |
|------|------|----------|
| `ROWS` | 按物理行计数，固定数量 | "前 3 行的移动平均" |
| `RANGE` | 按 ORDER BY 列的值做范围 | "过去 7 天的累计"、"同月的数据" |
| `GROUPS` | 按 ORDER BY 列值分组后的组数 | "前一个分组到后一个分组" |

```sql
-- 实例：计算 7 天移动平均销售额
SELECT
  order_date,
  amount,
  AVG(amount) OVER (
    ORDER BY order_date
    RANGE BETWEEN INTERVAL '6 day' PRECEDING AND CURRENT ROW
  ) AS moving_avg_7d
FROM daily_sales;

-- 实例：ROWS 模式的移动平均（严格取前 3 行）
SELECT
  order_date,
  amount,
  AVG(amount) OVER (
    ORDER BY order_date
    ROWS BETWEEN 3 PRECEDING AND CURRENT ROW
  ) AS moving_avg_3rows
FROM daily_sales;
```

:::tip 不指定框架时的默认行为
如果 `ORDER BY` 存在但没指定框架，默认是 `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`（从第一行到当前行）。如果连 `ORDER BY` 都没有，默认是 `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`（整个分组）。
:::

## 14. 事务：保证数据一致性的基础

事务让一组操作"要么全部成功，要么全部失败"。

```sql
BEGIN;

UPDATE products
SET price = price * 0.9
WHERE id = 2001;

INSERT INTO orders (id, user_id, status, created_at)
VALUES (3001, 1, 'PAID', '2026-01-10');

COMMIT;
```

如果中途出错，可以：

```sql
ROLLBACK;
```

### 14.1 ACID 四个字母代表什么

- 原子性：一个事务不可分割
- 一致性：事务前后约束不被破坏
- 隔离性：并发事务互不干扰（程度可调）
- 持久性：提交后数据可靠落盘

### 14.2 隔离级别（知道概念即可）

不同隔离级别权衡"性能 vs 一致性"，会影响脏读、不可重复读、幻读等现象。

## 15. 索引：让查询快起来

索引像书的目录：用空间换时间。

### 15.1 什么时候索引有效？

- `WHERE` 过滤列、`JOIN` 连接列、`ORDER BY` 排序列经常是索引候选
- 索引不是越多越好：写入会变慢，维护成本会上升

### 15.2 复合索引与最左前缀（通用规律）

如果有复合索引 `(user_id, created_at)`，那么：

- `WHERE user_id = ?` 常能用到
- `WHERE user_id = ? AND created_at >= ?` 常能用到
- `WHERE created_at >= ?` 通常用不到（因为缺少最左列）

### 15.3 用执行计划定位瓶颈

不同数据库命令不同：

- PostgreSQL：`EXPLAIN (ANALYZE, BUFFERS) ...`
- MySQL：`EXPLAIN ...`

执行计划能告诉你是否走索引、预估行数、连接方式等。

## 16. 从需求到 SQL：手把手教你写查询

前面讲了很多语法，但很多人面对真实需求时还是一脸懵——"我知道 WHERE 是过滤，但到底怎么写？"。这一节用 **5 个由浅入深的真实场景**，带你走一遍"读需求 → 拆解 → 写 SQL"的完整过程。

我们用这套表来练：

```sql
-- 用户表
users (id, name, email, city, created_at)
-- 订单表
orders (id, user_id, status, amount, created_at)
-- 订单明细表
order_items (order_id, product_id, quantity, unit_price)
-- 商品表
products (id, name, category, price)
```

### 场景 1：查某个条件下的数据

> **需求**：查出来自北京的用户

**思考过程**：
1. 数据在哪个表？→ `users`
2. 要哪些列？→ 所有列（先用 `*`，熟练后指定列）
3. 过滤条件？→ `city = 'Beijing'`

```sql
SELECT * FROM users WHERE city = 'Beijing';
```

**进阶**：只要名字和邮箱，按注册时间倒序：

```sql
SELECT name, email, created_at
FROM users
WHERE city = 'Beijing'
ORDER BY created_at DESC;
```

### 场景 2：多条件组合过滤

> **需求**：查出来自北京、且注册时间在 2026 年之后的用户

**思考过程**：
1. 两个条件都要满足 → 用 `AND`
2. 时间范围 → `BETWEEN` 或 `>=` + `<`

```sql
-- 写法 A：BETWEEN（闭区间）
SELECT name, email
FROM users
WHERE city = 'Beijing'
  AND created_at BETWEEN '2026-01-01' AND '2026-12-31';

-- 写法 B：比较运算符（更精确控制边界）
SELECT name, email
FROM users
WHERE city = 'Beijing'
  AND created_at >= '2026-01-01'
  AND created_at < '2027-01-01';
```

**常见错误**：

```sql
-- ❌ 日期比较用了字符串格式的函数，索引失效
WHERE YEAR(created_at) = 2026

-- ✅ 用范围条件，保持列的"裸"形态
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'
```

### 场景 3：聚合统计 + 分组

> **需求**：查每个用户的订单数量和总消费金额，只看已支付订单

**思考过程**：
1. 数据涉及哪些表？→ `users`（用户名）+ `orders`（订单信息）
2. 要按什么分组？→ 每个用户 → `GROUP BY user_id`
3. 统计什么？→ 订单数 `COUNT(*)`，总金额 `SUM(amount)`
4. 过滤条件？→ `status = 'PAID'`（在 JOIN 的 ON 里还是 WHERE 里？→ 这里放在 WHERE 更清晰）

```sql
SELECT
  u.id,
  u.name,
  COUNT(o.id) AS order_count,
  COALESCE(SUM(o.amount), 0) AS total_spent
FROM users u
LEFT JOIN orders o ON o.user_id = u.id AND o.status = 'PAID'
GROUP BY u.id, u.name
ORDER BY total_spent DESC;
```

**为什么用 `LEFT JOIN`？** 因为需求是"每个用户"——没有订单的用户也要显示（金额显示 0）。如果用 `INNER JOIN`，没订单的用户就丢了。

**再加一层过滤**：只要总消费超过 1000 的用户：

```sql
SELECT
  u.id,
  u.name,
  COUNT(o.id) AS order_count,
  COALESCE(SUM(o.amount), 0) AS total_spent
FROM users u
LEFT JOIN orders o ON o.user_id = u.id AND o.status = 'PAID'
GROUP BY u.id, u.name
HAVING total_spent > 1000       -- 对聚合结果过滤，用 HAVING 而非 WHERE
ORDER BY total_spent DESC;
```

### 场景 4：多表关联 + 子查询

> **需求**：查出来买过"数据库"这个分类的商品的用户

**思考过程**：
1. 需要的信息：用户（`users`）→ 通过什么关联到商品？→ `users → orders → order_items → products`
2. 过滤条件：商品分类 = '数据库'
3. 用户可能买了多件，要去重 → `DISTINCT`

```sql
-- 写法 A：多表 JOIN
SELECT DISTINCT u.id, u.name
FROM users u
JOIN orders o ON o.user_id = u.id
JOIN order_items oi ON oi.order_id = o.id
JOIN products p ON p.id = oi.product_id
WHERE p.category = '数据库';

-- 写法 B：EXISTS 子查询（通常更高效）
SELECT u.id, u.name
FROM users u
WHERE EXISTS (
  SELECT 1
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.id
  JOIN products p ON p.id = oi.product_id
  WHERE o.user_id = u.id
    AND p.category = '数据库'
);
```

**EXISTS 的优势**：找到第一条匹配就停止扫描，不需要像 `DISTINCT` 那样处理整个结果集。

### 场景 5：排名与窗口函数

> **需求**：查每个分类中价格最高的 Top 3 商品

**思考过程**：
1. 分组方式：每个分类 → `PARTITION BY category`
2. 排名依据：价格倒序 → `ORDER BY price DESC`
3. 取前 3 → `WHERE rn <= 3`

```sql
WITH ranked_products AS (
  SELECT
    id,
    name,
    category,
    price,
    ROW_NUMBER() OVER (
      PARTITION BY category
      ORDER BY price DESC
    ) AS rn
  FROM products
)
SELECT id, name, category, price
FROM ranked_products
WHERE rn <= 3
ORDER BY category, rn;
```

**ROW_NUMBER vs RANK vs DENSE_RANK**：

```sql
-- 假设价格：100, 90, 90, 80
ROW_NUMBER() → 1, 2, 3, 4   -- 严格唯一编号
RANK()       → 1, 2, 2, 4   -- 并列跳号（90 并列第 2，下一个从第 4 开始）
DENSE_RANK() → 1, 2, 2, 3   -- 并列不跳号（90 并列第 2，下一个从第 3 开始）
```

### 小结：写 SQL 的通用思考路径

遇到任何查询需求，按这 6 步走：

1. **数据在哪些表？** → 确定 `FROM` 和 `JOIN` 关系
2. **要哪些列？** → 写 `SELECT` 的输出
3. **怎么过滤？** → 写 `WHERE` 条件
4. **要分组统计吗？** → 需要就加 `GROUP BY` + 聚合函数
5. **要对分组结果过滤？** → 用 `HAVING`
6. **要排序/分页？** → 加 `ORDER BY` + `LIMIT`

> 建议：先在纸上或脑子里过一遍这 6 步，再动手写 SQL。写完后用 `SELECT COUNT(*)` 验证行数是否符合预期，再看具体数据。

## 18. 视图（VIEW）：把复杂查询存起来复用

视图是一条保存在数据库里的 SQL 查询，用起来像一张"虚拟表"。

### 18.1 创建视图

```sql
CREATE VIEW v_user_order_summary AS
SELECT
  u.id AS user_id,
  u.name,
  COUNT(o.id) AS order_count,
  COALESCE(SUM(o.amount), 0) AS total_spent
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.name;
```

之后你可以像查表一样查它：

```sql
SELECT * FROM v_user_order_summary WHERE total_spent > 500;
```

### 18.2 视图的价值

- **简化复杂查询**：把多表 JOIN + 聚合的结果存成视图，业务代码直接 `SELECT * FROM 视图`
- **权限控制**：给用户开放视图的查询权限，而非底层表的权限（用户看不到敏感列）
- **逻辑独立**：表结构变了，只需修改视图定义，业务代码不用改

### 18.3 修改和删除视图

```sql
-- 修改视图定义
CREATE OR REPLACE VIEW v_user_order_summary AS
SELECT ... ;  -- 新的查询

-- 删除视图
DROP VIEW IF EXISTS v_user_order_summary;
```

:::note 视图不是"物化"的
普通视图不存数据，每次查询时它会重新执行底层 SQL。如果底层查询很重，视图的性能也不会好。需要缓存结果时，用**物化视图**（PostgreSQL 支持）或单独建汇总表。
:::

## 19. 常见错误与排查清单

### 19.1 结果行数"异常多"

通常是 JOIN 条件不完整导致"倍增"。做法：

- 先单表 `SELECT COUNT(*)` 看规模
- 再逐步加入 JOIN，每一步都检查行数变化
- 确认连接键是否唯一/是否应该先聚合再 JOIN

### 19.2 WHERE 条件写了但没命中索引

常见原因：

- 对列做了函数变换（例如 `WHERE DATE(created_at) = ...`）
- 隐式类型转换（字符串和数字混用）
- 条件选择性太差（过滤不掉多少行）

### 19.3 NULL 引发的逻辑问题

- `NOT IN` 遇到 `NULL` 容易出问题，很多场景用 `NOT EXISTS` 更可靠

## 20. 安全：SQL 注入与权限控制

### 20.1 SQL 注入：永远不要拼接字符串

SQL 注入是最常见也最危险的问题之一。

```sql
-- ❌ 危险：直接拼接用户输入
query = "SELECT * FROM users WHERE name = '" + userInput + "'";
-- 如果用户输入 ' OR '1'='1，就会变成：
-- SELECT * FROM users WHERE name = '' OR '1'='1'  → 返回全部数据！

-- ✅ 安全：参数化查询（Prepared Statement）
-- MySQL
PREPARE stmt FROM 'SELECT * FROM users WHERE name = ?';
SET @name = 'Alice';
EXECUTE stmt USING @name;

-- PostgreSQL / 应用层（以 Node.js 为例）
-- db.query('SELECT * FROM users WHERE name = $1', [userInput])
```

原则：
- 应用层使用参数化查询（Prepared Statement）
- 对输入做合理校验，但不要把"校验"当成注入防护的唯一手段

### 20.2 权限控制：GRANT 与 REVOKE

数据库权限控制的原则是**最小权限**：只给用户它真正需要的权限。

```sql
-- 创建一个只读用户
CREATE USER readonly_user WITH PASSWORD 'secure_password';

-- 给它查询特定表的权限
GRANT SELECT ON users TO readonly_user;
GRANT SELECT ON orders TO readonly_user;

-- 给应用用户读写权限
CREATE USER app_user WITH PASSWORD 'app_password';
GRANT SELECT, INSERT, UPDATE ON users TO app_user;
GRANT SELECT, INSERT, UPDATE, DELETE ON orders TO app_user;

-- 撤销权限
REVOKE DELETE ON orders FROM app_user;

-- 查看用户权限
SHOW GRANTS FOR readonly_user;  -- MySQL
\du+ readonly_user               -- PostgreSQL（psql 命令）
```

:::warning 不要用 root 跑应用
生产环境中，应用代码连接数据库的账号应该只有它需要的最小权限。`root` / `superuser` 只留给 DBA 做维护操作。
:::

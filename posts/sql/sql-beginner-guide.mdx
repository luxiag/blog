SQL（Structured Query Language）是**关系型数据库**的通用语言。你可以用它：

- 查数据（查询、筛选、排序、统计）
- 改数据（插入、更新、删除）
- 管数据（建表、加约束、建索引、事务控制、权限）

## 1. 先建立 SQL 的整体认知

### 1.1 关系型数据库在解决什么问题？

关系型数据库（RDBMS）把数据组织成"表（Table）"，表由"行（Row）"和"列（Column）"组成。

- 列：字段含义与类型（例如 `price` 是数值）
- 行：一条记录（例如一笔订单）
- 主键：唯一标识一行（例如 `id`）
- 外键：建立表与表之间关系（例如 `orders.user_id -> users.id`）

SQL 的核心是：**用集合（set）的方式处理数据**。

### 1.2 SQL 的两大类工作

- **DQL**（查询）：`SELECT`
- **DML**（写入/修改/删除）：`INSERT` / `UPDATE` / `DELETE`
- **DDL**（定义结构）：`CREATE` / `ALTER` / `DROP`
- **TCL**（事务控制）：`BEGIN` / `COMMIT` / `ROLLBACK`

## 2. 我们用一套示例数据贯穿全文

为方便演示，假设你有以下表：

```sql
CREATE TABLE users (
  id        BIGINT PRIMARY KEY,
  name      VARCHAR(50) NOT NULL,
  email     VARCHAR(200) NOT NULL,
  created_at TIMESTAMP NOT NULL

CREATE TABLE products (
  id    BIGINT PRIMARY KEY,

CREATE TABLE orders (
  id         BIGINT PRIMARY KEY,
  user_id    BIGINT NOT NULL,
  status     VARCHAR(20) NOT NULL,
  created_at TIMESTAMP NOT NULL
);

CREATE TABLE order_items (
  order_id   BIGINT NOT NULL,
  product_id BIGINT NOT NULL,
  quantity   INT NOT NULL,
  unit_price DECIMAL(10,2) NOT NULL,
  PRIMARY KEY (order_id, product_id)
);
```

你不需要立刻跑起来，先理解结构：

- `users` 一对多 `orders`
- `orders` 一对多 `order_items`
- `products` 一对多 `order_items`

## 3. 最重要的语句：SELECT 查询

### 3.1 SELECT 的基本结构

```sql
SELECT 列1, 列2
FROM 表
WHERE 条件
ORDER BY 排序列
LIMIT n;
```

一个常见的顺序认知：

- 你写的时候通常是 `SELECT -> FROM -> WHERE ...`
- 数据库执行时的逻辑顺序更像 `FROM -> WHERE -> GROUP BY -> HAVING -> SELECT -> ORDER BY -> LIMIT`

理解逻辑顺序可以帮你解释很多"为什么不能在 WHERE 里用别名"等问题。

当你写 `GROUP BY` 时：

- `SELECT` 里的非聚合列必须出现在 `GROUP BY` 里（严格 SQL）
- 某些数据库（如 MySQL 在特定模式）可能"放宽"，但结果不可预测，不建议依赖

### 5.2 LEFT JOIN（主表全保留）

<SqlSimulator

  defaultQuery="SELECT * FROM users u LEFT JOIN orders o ON u.id = o.user_id;"
  answerSql="SELECT u.name, COUNT(o.id) as order_count FROM users u LEFT JOIN orders o ON u.id = o.user_id GROUP BY u.id;"

  description="保留左表所有记录，右表无匹配则为 NULL"

这能查出"没有订单的用户"（`order_id` 会是 `NULL`）。

### 5.3 JOIN 常见坑：把条件写错位置

如果，你想查"所有用户及其已支付订单（没有也要出现）"，这两句不等价：

```sql
SELECT u.id, u.name, o.id AS order_id
FROM users u
LEFT JOIN orders o
  ON o.user_id = u.id
 AND o.status = 'PAID';
```

```sql
SELECT u.id, u.name, o.id AS order_id
FROM users u
LEFT JOIN orders o
  ON o.user_id = u.id
WHERE o.status = 'PAID';
```

第二句会把 `LEFT JOIN` 变得更像 `INNER JOIN`（因为 `WHERE o.status='PAID'` 会过滤掉 `NULL` 行）。

<SqlSimulator

- SQL Server：常用 `MERGE`（需谨慎）

这是典型的"方言差异"，写文章/做项目时要确认你的数据库。

## 11. 建表与约束：把规则写进数据库

### 11.1 常见约束

- `PRIMARY KEY`：唯一且不为空
- `UNIQUE`：唯一（允许多个 `NULL` 的行为因数据库而异）
- `NOT NULL`：不允许为空
- `FOREIGN KEY`：引用完整性
- `CHECK`：检查约束（部分数据库支持程度不同）

示例：

```sql
CREATE TABLE payments (
  id       BIGINT PRIMARY KEY,
  order_id BIGINT NOT NULL,
  amount   DECIMAL(10,2) NOT NULL,
  status   VARCHAR(20) NOT NULL,
  CONSTRAINT fk_payments_order
    FOREIGN KEY (order_id) REFERENCES orders(id),
  CONSTRAINT chk_amount_positive
    CHECK (amount > 0)
);
```

把规则写在数据库里能减少"脏数据"出现的概率。

## 12. 事务：保证数据一致性的基础

事务让一组操作"要么全部成功，要么全部失败"。

```sql
BEGIN;

UPDATE products
SET price = price * 0.9
WHERE id = 2001;

INSERT INTO orders (id, user_id, status, created_at)
VALUES (3001, 1, 'PAID', '2026-01-10');

COMMIT;
```

如果中途出错，可以：

```sql
ROLLBACK;
```

### 12.1 ACID 四个字母代表什么

- 原子性：一个事务不可分割
- 一致性：事务前后约束不被破坏
- 隔离性：并发事务互不干扰（程度可调）
- 持久性：提交后数据可靠落盘

### 12.2 隔离级别（知道概念即可）

不同隔离级别权衡"性能 vs 一致性"，会影响脏读、不可重复读、幻读等现象。

## 13. 索引：让查询快起来

索引像书的目录：用空间换时间。

### 13.1 什么时候索引有效？

- `WHERE` 过滤列、`JOIN` 连接列、`ORDER BY` 排序列经常是索引候选
- 索引不是越多越好：写入会变慢，维护成本会上升

### 13.2 复合索引与最左前缀（通用规律）

如果有复合索引 `(user_id, created_at)`，那么：

- `WHERE user_id = ?` 常能用到
- `WHERE user_id = ? AND created_at >= ?` 常能用到
- `WHERE created_at >= ?` 通常用不到（因为缺少最左列）

### 13.3 用执行计划定位瓶颈

不同数据库命令不同：

- PostgreSQL：`EXPLAIN (ANALYZE, BUFFERS) ...`
- MySQL：`EXPLAIN ...`

执行计划能告诉你是否走索引、预估行数、连接方式等。

## 14. 设计思维：写出更"好用"的表

### 14.1 规范化的直觉（不追概念也能做对）

- 一列只表达一件事（避免把多个值用逗号塞进一列）
- 可变集合用子表表达（例如订单项用 `order_items`）
- 不重复存储能推导的数据（减少一致性风险）

### 14.2 命名与字段建议

- 主键统一用 `id`
- 外键用 `xxx_id`
- 时间用 `created_at/updated_at`
- 状态字段明确枚举范围（配合约束或业务层校验）

---

## 15. 常见错误与排查清单

### 15.1 结果行数"异常多"

通常是 JOIN 条件不完整导致"倍增"。做法：

- 先单表 `SELECT COUNT(*)` 看规模
- 再逐步加入 JOIN，每一步都检查行数变化
- 确认连接键是否唯一/是否应该先聚合再 JOIN

### 15.2 WHERE 条件写了但没命中索引

常见原因：

- 对列做了函数变换（例如 `WHERE DATE(created_at) = ...`）
- 隐式类型转换（字符串和数字混用）
- 条件选择性太差（过滤不掉多少行）

### 15.3 NULL 引发的逻辑问题

- `NOT IN` 遇到 `NULL` 容易出问题，很多场景用 `NOT EXISTS` 更可靠

---

## 16. 安全：永远不要拼接 SQL 字符串

SQL 注入是最常见也最危险的问题之一。

- 应用层使用参数化查询（Prepared Statement）
- 数据库权限最小化（只给必要的读写权限）
- 对输入做合理校验，但不要把"校验"当成注入防护的唯一手段

---

## 17. 方言差异速览（写 SQL 时要有意识）

- 字符串/标识符引用：有的用单引号/双引号/反引号
- 分页语法：`LIMIT/OFFSET` vs `TOP` vs `FETCH`
- 日期函数：`NOW()`、`CURRENT_TIMESTAMP`、`DATEADD` 等
- 布尔类型：有的是真布尔，有的是 `0/1`
- `AUTO_INCREMENT` / `SERIAL` / `IDENTITY`

当你从教程复制 SQL 到项目里跑不通，先问自己：**我用的数据库是哪种？**

---

## 18. 一页速查：从需求到 SQL 的思考路径

- 需求要什么列：先写 `SELECT` 的输出形状
- 数据在哪些表：写 `FROM` 并画关系
- 如何过滤：写 `WHERE`（先行过滤通常更省）
- 是否要汇总：需要就加 `GROUP BY` + 聚合
- 是否要筛选汇总：用 `HAVING`
- 是否要排序分页：`ORDER BY` + 分页
- 性能不行：看执行计划，调整索引/改写查询

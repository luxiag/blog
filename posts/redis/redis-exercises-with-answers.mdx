## 0. 热身：安全地清理练习数据

**题目**：删除所有以 `ex` 开头的 key，且不能阻塞 Redis。

::: details 查看答案
用 `SCAN` 游标式分批扫描，对每批结果再删除，**绝不能用 `KEYS ex*`**（会阻塞单线程的 Redis）：

```redis
SCAN 0 MATCH ex* COUNT 100
```

拿到每批返回的 key 后用 `DEL` 删除，循环直到游标回到 0。生产中通常用脚本封装这个循环。
:::

## 一、String / TTL / 计数器（基础）

### 1.1 验证码与过期

**题目**：写入登录验证码 `ex01:code:alice = 123456`，5 分钟后过期，并查看剩余 TTL。

::: details 查看答案
```redis
SET ex01:code:alice 123456 EX 300
TTL ex01:code:alice
GET ex01:code:alice
```
`EX 300` 表示 300 秒后自动过期。验证码这类临时数据**必须设 TTL**，否则会堆积占内存。
:::

### 1.2 原子计数器

**题目**：统计首页 PV，每访问一次加 1，再一次性加 10。

::: details 查看答案
```redis
INCR ex01:pv:home
INCRBY ex01:pv:home 10
GET ex01:pv:home
```
`INCR` 是原子操作，高并发下也不会算错，这是用 Redis 做计数器的核心优势。
:::

### 1.3 简单库存扣减（体会原子性）

**题目**：商品 `ex01:stock:2001` 初始 5 件，每次下单减 1，库存不足要能识别。

::: details 查看答案
```redis
SET ex01:stock:2001 5
DECR ex01:stock:2001
```
`DECR` 返回扣减后的值。如果返回 `-1`，说明超卖了，需要 `INCR` 回滚并提示售罄。但"判断 + 扣减"两步在高并发下仍有隐患，更稳的做法是用 Lua 把它们合成一个原子操作（见第六章）。
:::

## 二、Hash（对象存储）

### 2.1 存用户资料并局部更新

**题目**：用 Hash 存用户 1001（name=Alice, age=18, city=Shanghai），然后把 age 加 1。

::: details 查看答案
```redis
HSET ex02:user:1001 name Alice age 18 city Shanghai
HINCRBY ex02:user:1001 age 1
HGETALL ex02:user:1001
```
用 Hash 而非 String+JSON 的好处：能单独更新某个字段（如 age），不用读出整个对象再写回。
:::

### 2.2 Hash 字段级过期怎么做

**题目**：Hash 不支持字段级 TTL，如果想让某个字段过期，你会怎么做？

::: details 查看答案
常见三种方案：
- **拆成独立 key**：`ex02:user:1001:token` 单独存并设 TTL。
- **逻辑过期**：字段值里带上 `expiresAt` 时间戳，读取时自己判断是否过期。
- **辅助 ZSet**：用一个 ZSet 存"字段名 → 过期时间戳"，定期扫描清理。

（注：Redis 7.4+ 开始为 Hash 字段提供了原生 TTL 命令 `HEXPIRE`，但低版本仍需用上述方案。）
:::

## 三、List（队列）

### 3.1 FIFO 队列

**题目**：往队列 `ex03:q` 放入 job1/job2/job3，按先进先出取出。

::: details 查看答案
```redis
LPUSH ex03:q job1 job2 job3
RPOP ex03:q
```
`LPUSH`（左进）+ `RPOP`（右出）实现 FIFO。注意 `LPUSH ex03:q job1 job2 job3` 后，列表从左到右是 `job3 job2 job1`，所以 `RPOP` 先取到 job1。
:::

### 3.2 阻塞式消费

**题目**：消费者阻塞等待队列 `ex03:q2`，最多等 5 秒，没数据就返回空。

::: details 查看答案
```redis
BRPOP ex03:q2 5
```
`BRPOP` 在队列为空时阻塞等待，避免消费者空转轮询。这是 List 做简单任务队列的常用方式。
:::

## 四、Set（去重与关系运算）

### 4.1 统计独立访客 UV

**题目**：把访问用户 ID 加入 `ex04:uv:2026-07-01`，重复访问只算一次，统计 UV。

::: details 查看答案
```redis
SADD ex04:uv:2026-07-01 1001 1002 1003
SADD ex04:uv:2026-07-01 1002
SCARD ex04:uv:2026-07-01
```
Set 自动去重，`SCARD` 返回去重后的数量。1002 加了两次也只算一个，结果是 3。
:::

### 4.2 共同关注

**题目**：求 A、B 两个用户的共同关注。

::: details 查看答案
```redis
SADD ex04:follow:a u1 u2 u3
SADD ex04:follow:b u2 u3 u4
SINTER ex04:follow:a ex04:follow:b
```
`SINTER` 求交集，返回 u2、u3。集合运算是 Set 的一大杀手锏。
:::

## 五、ZSet（排行榜与延迟队列）

### 5.1 TopN 排行榜

**题目**：积分榜 Alice=100、Bob=95、Cindy=120，查前 2 名并给 Bob 加 10 分后查他的排名。

::: details 查看答案
```redis
ZADD ex05:rank 100 Alice 95 Bob 120 Cindy
ZREVRANGE ex05:rank 0 1 WITHSCORES
ZINCRBY ex05:rank 10 Bob
ZREVRANK ex05:rank Bob
```
`ZREVRANGE` 按分数从高到低取。`ZREVRANK` 返回的排名从 0 开始，展示给用户时要 +1。
:::

### 5.2 延迟队列

**题目**：把任务按"执行时间戳"放入延迟队列，取出所有已到期的任务。

::: details 查看答案
```redis
ZADD ex05:delay 1751328000 t1 1751328060 t2
ZRANGEBYSCORE ex05:delay -inf 1751328000 LIMIT 0 100
```
把执行时间戳当作 score，用 `ZRANGEBYSCORE` 取出 score ≤ 当前时间的任务。取出后要删除避免重复消费——并发下"取 + 删"应该用 Lua 做成原子操作（见 6.2）。
:::

## 六、Lua 原子脚本

Lua 脚本在 Redis 内部单线程执行，天然原子，适合把"检查 + 修改"这类多步操作合并。

### 6.1 原子扣减库存（防超卖）

**题目**：库存在 `ex06:stock:2001`，库存 ≥ 1 才扣减并返回新库存，否则返回 -1。

::: details 查看答案
```redis
EVAL "local v = tonumber(redis.call('GET', KEYS[1]) or '0'); if v <= 0 then return -1 end; v = v - 1; redis.call('SET', KEYS[1], v); return v" 1 ex06:stock:2001
```
关键在于"读库存 → 判断 → 扣减"三步在脚本里一次性原子完成，中间不会被其他请求插入，从根本上杜绝超卖。这比"先 DECR 再判断回滚"更可靠。
:::

### 6.2 延迟队列"取并删"原子化

**题目**：从延迟队列取出最多 100 个到期任务，并同时删除，保证并发下不重复取。

::: details 查看答案
```redis
EVAL "local z=KEYS[1]; local now=tonumber(ARGV[1]); local limit=tonumber(ARGV[2]); local items=redis.call('ZRANGEBYSCORE', z, '-inf', now, 'LIMIT', 0, limit); if #items==0 then return items end; redis.call('ZREM', z, unpack(items)); return items" 1 ex05:delay 1751328000 100
```
"取出"和"删除"合并成一个原子脚本，避免两个消费者同时取到同一批任务。（注意 `unpack` 在不同 Redis/Lua 版本行为略有差异，生产脚本要更健壮。）
:::

## 七、缓存综合（穿透 / 击穿 / 雪崩）

对应[《Redis 缓存实战》](/posts/redis/redis-cache-in-depth)，这几题把三大问题串起来。

### 7.1 缓存空值防穿透

**题目**：对数据库里也不存在的用户，如何避免每次请求都打到数据库？

::: details 查看答案
```redis
SET ex07:user:404 __NULL__ EX 60
GET ex07:user:404
```
查库为空时，往缓存写一个短 TTL 的空标记 `__NULL__`。业务读到它就当作"不存在"直接返回，不再查库。TTL 设短一点，避免数据真被创建后长时间读到空。
:::

### 7.2 TTL 抖动防雪崩

**题目**：一批同类 key 想在 10 分钟基础上错开过期，怎么设？

::: details 查看答案
在代码里给 TTL 加随机值，Redis 侧照常 `SET ... EX`：

```
ttl = 600 + random(0, 60)   # 10 分钟 + 0~60 秒随机
SET ex07:item:1 value EX <ttl>
```
错开过期时间，避免大量 key 在同一秒集体失效把数据库压垮。
:::

### 7.3 互斥锁防击穿

**题目**：热点 key 失效瞬间，只让一个请求回源重建，其他请求不要一起打库。

::: details 查看答案
```redis
SET ex07:lock:hotkey <token> NX PX 3000
```
`NX` 保证只有一个请求能拿到锁去重建缓存；没拿到锁的请求 sleep 一小会儿后重试读缓存。`PX 3000` 给锁设过期，防止重建线程挂了导致锁永不释放。释放锁要校验 token（见 8.2）。
:::

## 八、分布式锁

### 8.1 获取锁

**题目**：获取任务锁 `ex08:lock:job`，持有 10 秒。

::: details 查看答案
```redis
SET ex08:lock:job <random-token> NX PX 10000
```
- `NX`：只有 key 不存在时才设置成功（保证互斥）。
- `PX 10000`：10 秒后自动过期，防止持锁者宕机导致死锁。
- value 用**随机 token**：标识锁的归属，释放时校验，避免误删别人的锁。
:::

### 8.2 安全释放锁（防误删）

**题目**：只允许持锁者释放自己的锁，怎么保证？

::: details 查看答案
用 Lua 把"校验 token + 删除"合成原子操作：

```redis
EVAL "if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) else return 0 end" 1 ex08:lock:job <random-token>
```
为什么必须原子？如果先 `GET` 校验、再 `DEL`，两步之间锁可能刚好过期并被别人获取，你的 `DEL` 就会误删别人的锁。Lua 脚本消除了这个中间窗口。
:::

### 8.3 锁续期（看门狗）

**题目**：业务要执行 30 秒，但锁只有 10 秒，怎么避免锁提前过期被别人抢走？

::: details 查看答案
启动一个后台定时任务（看门狗），每隔几秒给锁续期，续期前必须校验 token：

```redis
EVAL "if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('PEXPIRE', KEYS[1], ARGV[2]) else return 0 end" 1 ex08:lock:job <random-token> 10000
```
校验 token 是为了确保只给"自己的锁"续期。Redisson 等成熟客户端已内置了看门狗机制，生产中建议直接用它们而非手写。
:::

## 九、限流（进阶）

### 9.1 固定窗口计数

**题目**：限制用户 1001 每分钟最多 100 次请求。

::: details 查看答案
```redis
INCR ex09:rl:1001:202607011230
EXPIRE ex09:rl:1001:202607011230 60
```
key 里拼上"当前分钟"，`INCR` 后判断是否超过 100。缺点是**窗口边界突刺**：在两分钟交界处可能短时间内放过近 200 次请求。
:::

### 9.2 ZSet 滑动窗口（更精确）

**题目**：用滑动窗口更精确地限流：任意 60 秒内不超过 100 次。

::: details 查看答案
思路：member 用唯一请求 id，score 用毫秒时间戳。每次请求先清理窗口外的旧记录，再统计窗口内数量：

```redis
ZADD ex09:sw:1001 1751328000123 req-1
ZREMRANGEBYSCORE ex09:sw:1001 -inf 1751327940123
ZCARD ex09:sw:1001
EXPIRE ex09:sw:1001 120
```
`ZREMRANGEBYSCORE` 删掉 60 秒前的记录，`ZCARD` 统计窗口内请求数。生产上通常把"添加 + 清理 + 计数 + 判断"用一个 Lua 脚本原子完成。
:::

## 十、性能与排障（理解题）

### 10.1 为什么线上禁用 KEYS

**题目**：为什么生产环境不能用 `KEYS pattern`？用什么替代？

::: details 查看答案
Redis 执行命令是单线程的，`KEYS` 会一次性遍历全部 key，key 多时会长时间阻塞，期间所有其他请求都被卡住，等于一次事故。替代方案是 `SCAN`：

```redis
SCAN 0 MATCH user:* COUNT 100
```
`SCAN` 是游标式分批扫描，每次只取一小批，不会长时间阻塞。
:::

### 10.2 定位大 key

**题目**：怀疑有大 key 拖慢了 Redis，如何排查它多大？

::: details 查看答案
先用 `SCAN` 找可疑 key，再按类型查大小：

```redis
STRLEN key   # String 长度
HLEN key     # Hash 字段数
LLEN key     # List 长度
SCARD key    # Set 元素数
ZCARD key    # ZSet 元素数
```
另外 `redis-cli --bigkeys` 可以扫描整库找出各类型最大的 key。发现大 key 后应考虑拆分或调整数据结构。
:::

### 10.3 查看慢命令

**题目**：如何查看最近的慢命令？

::: details 查看答案
```redis
SLOWLOG GET 10
```
返回最近 10 条超过阈值的慢命令，用于定位是哪些命令拖慢了实例。阈值由 `slowlog-log-slower-than` 配置。
:::

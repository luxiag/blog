# Redis 入门：从数据结构到缓存与消息队列的系统指南

Redis（Remote Dictionary Server）最出名的身份是“缓存”，但它远不止缓存：它提供多种高性能数据结构、支持过期、发布订阅、流式消息、Lua 脚本、复制与集群等能力。

本文目标：让你能把 Redis 用在真实项目里——知道它擅长什么、怎么选数据结构、怎么做缓存与一致性、怎么避免常见事故（缓存雪崩/穿透/击穿）、以及上线后怎么做持久化与高可用。

> 默认以 Redis 6/7 的常见能力为参考，不同版本命令与细节可能略有差异。

---

## 1. Redis 的整体认知：它是什么？适合做什么？

一句话：Redis 是一个**以内存为主**、支持多数据结构、提供可选持久化与高可用的键值数据库。

### 1.1 Redis 擅长的场景

- 缓存（热点数据、页面片段、计算结果）
- 计数与限流（点赞数、PV、接口限流）
- 排行榜（ZSET）
- 会话与临时状态（登录态、验证码、临时令牌）
- 消息与异步（Stream / PubSub / List 队列）
- 分布式协调（分布式锁、去重、任务调度）

### 1.2 不适合的场景

- 存“永远不丢、强一致、复杂查询”的核心账务数据（优先 RDBMS）
- 海量超大 value、超大 key 数且内存无法承受
- 把 Redis 当成“万能数据库”而忽视数据治理与持久化策略

## 2. 最重要的基础：键、值、过期与时间复杂度

### 2.1 Key 的命名规范（强烈建议）

用“命名空间 + 业务含义 + 主键”的方式：

- `user:profile:1001`
- `order:detail:90001`
- `rate_limit:ip:1.2.3.4`

好处：可读、可批量管理（SCAN）、不容易冲突。

### 2.2 TTL（过期时间）

Redis 支持 key 级别过期：

```redis
SET code:login:alice 123456 EX 300
TTL code:login:alice
```

过期的意义：

- 自动清理临时数据
- 缓存可控

### 2.3 时间复杂度意识

Redis 很快，但不是所有操作都 O(1)。比如：

- `GET/SET` 通常 O(1)
- `LRANGE`、`SMEMBERS`、`KEYS` 可能遍历很多元素，在线上要谨慎

一个进阶原则：**避免在生产对大 key 做全量遍历**。

## 3. Redis 的核心数据结构（必会）

### 3.1 String：最常用

```redis
SET user:name:1001 "Alice"
GET user:name:1001

INCR page:view:home
INCRBY counter:download 10
```

适合：缓存对象（通常 JSON）、计数器、分布式 ID（配合 INCR）。

### 3.2 Hash：存对象字段

```redis
HSET user:1001 name "Alice" age 18
HGET user:1001 name
HGETALL user:1001
```

适合：对象字段频繁更新，且不想每次读写整段 JSON。

### 3.3 List：有序列表（双端队列）

```redis
LPUSH queue:email job1
LPUSH queue:email job2
RPOP queue:email
```

适合：简单队列、时间线（小规模）。

### 3.4 Set：无序去重集合

```redis
SADD user:1001:tags "vip" "new"
SISMEMBER user:1001:tags "vip"
SMEMBERS user:1001:tags
```

适合：去重、集合运算（交集/并集）。

### 3.5 Sorted Set（ZSET）：有序集合（排行榜神器）

```redis
ZADD leaderboard 100 "alice"
ZADD leaderboard 95 "bob"
ZREVRANGE leaderboard 0 9 WITHSCORES
ZINCRBY leaderboard 5 "bob"
```

适合：排行榜、延迟队列（按时间戳 score 排序）。

### 3.6 Bitmap / HyperLogLog（了解即可）

- Bitmap：签到/日活标记（位运算）
- HyperLogLog：近似去重计数（省内存）

### 3.7 Stream：更现代的消息队列

Stream 支持消费者组、确认、重试等，是很多“轻量 MQ”场景的选择。

## 4. 缓存设计：把 Redis 用对的关键

### 4.1 缓存模式：Cache Aside（旁路缓存）

最常见套路：

1. 读：先查 Redis，没命中再查 DB，然后回填 Redis
2. 写：先更新 DB，再删除（或更新）缓存

读示例（伪代码）：

```text
val = GET cache
if miss:
  val = query DB
  SET cache val EX ttl
return val
```

写示例（常用“删除缓存”）：

```text
update DB
DEL cache
```

### 4.2 缓存一致性：为什么常用“删缓存”而不是“更新缓存”

- 更新缓存需要知道新值如何计算、容易漏字段
- 删除缓存会让下次读自然回源并回填

但删除也有窗口期，一致性要求极高的系统需要更强的策略（双删、订阅 binlog、消息队列等）。

### 4.3 三大经典问题：穿透/击穿/雪崩

#### 缓存穿透（一直查不到）

原因：请求的 key 在 DB 也不存在，导致每次都回源。

常见解决：

- 缓存空值（短 TTL）
- 布隆过滤器（Bloom Filter）
- 参数校验与限流

#### 缓存击穿（热点 key 失效瞬间）

原因：热点 key 过期，大量并发同时回源。

常见解决：

- 互斥锁（单飞）
- 热点不过期 + 异步刷新
- 提前续期（逻辑过期）

#### 缓存雪崩（大量 key 同时过期）

原因：同一时间很多 key 过期或 Redis 故障。

常见解决：

- TTL 加随机抖动（jitter）
- 多级缓存（本地缓存 + Redis）
- 限流与降级、预热

## 5. 过期策略与内存淘汰（必须懂）

### 5.1 过期删除不是“到点立刻删”

Redis 过期删除通常结合：

- 惰性删除：访问时发现过期再删
- 定期删除：后台周期扫描一部分 key

所以你会看到：过期 key 可能短时间仍占内存。

### 5.2 内存满了怎么办？maxmemory 与淘汰策略

当设置了 `maxmemory`，内存达到上限会触发淘汰策略：

- `allkeys-lru`：对所有 key 做 LRU 淘汰（常用）
- `volatile-lru`：只淘汰设置了 TTL 的 key
- `allkeys-random` / `volatile-random`
- `noeviction`：不淘汰，写入直接报错（容易引发业务雪崩）

实战建议：

- 缓存场景通常选 `allkeys-lru` 或 `allkeys-lfu`
- 业务要监控内存与淘汰次数，避免突然大量淘汰

## 6. 持久化：Redis 会丢数据吗？

Redis 以内存为主，但支持持久化。常见两种：

### 6.1 RDB：快照

- 定期生成数据快照（文件紧凑）
- 恢复快
- 可能丢失最近一段时间的数据

### 6.2 AOF：追加日志

- 记录写命令，恢复时重放
- 数据更安全（取决于刷盘策略）
- 文件可能更大，需要重写（rewrite）

实践中常见组合：**RDB + AOF**（兼顾恢复速度与数据安全）。

关键点：持久化越“勤”，性能开销越大。要按业务能承受的数据丢失（RPO）来权衡。

## 7. 高可用：复制、哨兵、集群

### 7.1 主从复制（Replication）

- 主节点写入，从节点同步
- 可做读扩展（但要理解一致性：从库可能读到旧数据）

### 7.2 Sentinel（哨兵）：自动故障转移

- 监控主从
- 主挂了自动选新主
- 客户端需要支持从哨兵获取新主地址

### 7.3 Redis Cluster：水平扩展

- 数据按槽（hash slot）分布到多个节点
- 支持在线扩容/缩容（需要配套运维）

选择建议：

- 单机够用：单实例 + 持久化
- 要高可用：主从 + 哨兵
- 要大容量与横向扩展：Cluster

## 8. 事务与 Lua：原子性操作的两种方式

### 8.1 MULTI/EXEC 事务

```redis
MULTI
INCR counter
EXPIRE counter 60
EXEC
```

注意：这类事务保证命令按顺序执行，但不等同于关系型数据库的强隔离事务。

### 8.2 Lua 脚本：更强的原子性与可控逻辑

Lua 脚本在 Redis 内部执行，常用于：

- 库存扣减
- 分布式锁续期
- 复杂的“检查 + 修改”逻辑

---

## 9. 消息与异步：从 Pub/Sub 到 Stream

### 9.1 Pub/Sub（发布订阅）

- 实时广播
- 不持久化（订阅者不在线会丢消息）

适合：通知、实时推送（可接受丢失）。

### 9.2 List 队列（简单）

```redis
BRPOP queue:email 5
```

适合：简单任务队列，但缺少确认、重试等完整语义。

### 9.3 Stream（更推荐）

- 支持消费者组
- 支持 ACK、Pending、重试

适合：需要可靠消费的轻量 MQ 场景。

## 10. 分布式锁（必须谨慎使用）

最常见需求：避免多个实例同时执行同一任务。

推荐基本做法：

- 使用 `SET key value NX PX ttl` 获取锁
- value 用随机串（标识锁归属）
- 释放锁需要校验 value（避免误删别人的锁），通常用 Lua 原子脚本

为什么要 TTL：防止持锁进程挂了永不释放。

提醒：分布式锁的正确性很容易被低估。对一致性要求极高的场景，要评估成熟方案与严格测试。

## 11. 线上排障：慢、卡、内存暴涨怎么查

### 11.1 慢

- 看是否有慢命令（慢日志）
- 看是否大 key/大 value
- 看是否 `KEYS`/`SMEMBERS` 这类全量遍历
- 看是否 CPU 100%（Lua、阻塞命令、RDB/AOF 重写）

### 11.2 卡住

- 是否单线程被阻塞（大 key 操作、阻塞命令、网络问题）
- 是否 AOF 刷盘策略导致写入抖动

### 11.3 内存暴涨

- key 数量是否激增（业务 bug）
- TTL 是否缺失（临时数据没设置过期）
- value 是否异常大（序列化对象膨胀）
- 淘汰策略是否合理（是否大量 eviction）

---

## 12. 安全与运维建议

- 不对公网裸露 Redis
- 设置密码与访问控制，配合内网/VPC
- 禁用危险命令（按团队策略）
- 监控关键指标：内存、命中率、连接数、命令耗时、淘汰次数、复制延迟
- 做好备份与恢复演练（尤其启用持久化时）

---

## 13. 一页速查：需求到方案怎么选

- 缓存对象：String（JSON）+ TTL + 防击穿策略
- 计数器：String + `INCR/INCRBY`
- 去重集合：Set
- 排行榜：ZSET
- 可靠消息：Stream（消费者组）
- 分布式锁：`SET NX PX` + Lua 释放

---

## 14. 练习题（建议动手写）

1. 用 ZSET 做一个 Top10 排行榜（加分、查榜）
2. 用 Hash 存用户资料并支持局部更新
3. 实现缓存旁路：读穿透时回源并回填（带 TTL 抖动）
4. 用 Stream 做一个生产者-消费者（带消费者组与 ACK）
5. 用 `SET NX PX` + Lua 实现分布式锁（防误删）

把这些练熟，你就能在项目里把 Redis 用得既快又稳。

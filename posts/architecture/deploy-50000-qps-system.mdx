# 5 万 QPS 项目怎么部署：从单机到高可用集群的实战方案

先说结论：**5 万 QPS 不是靠“买一台大机器”扛住的，而是靠分层、缓存、削峰、隔离和灰度一起扛住的。**

很多人一谈高并发，就马上开始堆名词：

- Nginx
- Redis
- Kafka
- 分库分表
- Kubernetes

这些都重要，但如果没有一套完整部署思路，最后很容易变成：

- 应用机器堆了很多，数据库先挂
- Redis 顶住了读流量，回源把 MySQL 打死
- 发布时瞬间流量抖动，整个集群雪崩
- 单个依赖超时，把 Tomcat / Node / .NET 线程池全部拖死

所以这篇文章不只讲“用什么”，而是讲**怎么把一个目标峰值 5 万 QPS 的项目部署成可运行、可扩容、可回滚、可观测的生产系统**。

这里默认场景是一个典型互联网业务：

- 读多写少
- HTTP API + Web 页面
- 有登录、商品/内容查询、下单或提交类写请求
- 峰值目标 5 万 QPS

如果你写的是音视频、游戏网关、IM 长连接，架构会不同，但底层思路仍然通用。

---

## 一、先纠正一个误区：5 万 QPS 不等于 5 万业务请求都打到数据库

如果你的系统设计成“每个请求都查数据库”，那别说 5 万 QPS，5000 QPS 都可能很危险。

高并发部署的前提，不是先部署，而是先分流量。

一个成熟系统里的请求，通常会被拆成几层：

1. **CDN/边缘层**：静态资源、缓存页面、热点接口
2. **网关层**：TLS 终止、鉴权、限流、路由转发
3. **应用层**：业务逻辑、聚合响应
4. **缓存层**：Redis、内存缓存
5. **异步层**：MQ、任务队列、延迟任务
6. **数据层**：MySQL、ES、对象存储、时序库

真正要做的是：

- 让尽可能多的请求止步于前面几层
- 让真正进入数据库的请求尽量少、尽量短、尽量稳

所以在部署前，第一件事不是“开几台服务器”，而是做**流量建模**。

---

## 二、容量评估：先把流量算清楚，再谈机器数

### 1. 明确 QPS 的口径

你必须先问清楚，所谓 5 万 QPS，指的是哪一种：

- 全站总请求数
- API 网关入口 QPS
- 只算核心业务接口
- 平均 QPS 还是峰值 QPS
- 峰值持续 10 秒、10 分钟，还是 2 小时

这几个口径不统一，部署方案会差很多。

通常生产上应该按这个方式估算：

```text
目标峰值 QPS = 日活请求总量 / 峰值时段秒数 * 峰值系数 * 安全冗余系数
```

例如：

- 日请求量 2 亿
- 80% 流量集中在 4 小时
- 峰值系数 2.5
- 冗余系数 1.5

那么实际部署目标就不会只按“算出来刚好 5 万”来做，而是可能要按 **7 万到 8 万 QPS 的承载能力** 设计。

### 2. 按接口类型拆开

不要把所有请求混成一个数字。至少要拆成：

- 静态资源请求
- 页面请求
- 只读查询接口
- 强一致写接口
- 后台管理接口
- 第三方回调接口

因为它们的资源消耗完全不同。

例如：

- 一个带 CDN 的静态文件请求，可能几乎不进源站
- 一个只读热点查询，大概率命中 Redis
- 一个下单接口，可能要写库、扣库存、发 MQ、记日志

同样都是 1 次请求，对系统的真实成本可以差 100 倍。

---

## 三、推荐的总体部署架构

对于 5 万 QPS，我更推荐这种经典分层：

```text
         用户
          |
     CDN / WAF
          |
   SLB / ALB / LVS
          |
   Nginx / API Gateway
          |
   Application Cluster
    |        |        |
 Redis   MQ/Kafka   Search
    |                 |
 MySQL Primary/Replica Cluster
          |
   Object Storage / Backup / Observability
```

每一层的目标都不同：

- **CDN/WAF**：挡攻击、吸收静态流量、降低回源
- **负载均衡层**：把流量均匀分发到网关或应用节点
- **网关层**：统一鉴权、限流、路由、熔断、日志采样
- **应用层**：做无状态服务，方便横向扩容
- **Redis 层**：扛住热点读请求
- **MQ 层**：把同步链路里的慢操作搬走
- **数据库层**：只处理必须落库的核心事务

注意，5 万 QPS 的关键不是某一层特别强，而是**每一层都不成为单点和瓶颈**。

## 四、入口层怎么部署：CDN、WAF、负载均衡缺一不可

### 1. CDN 不只是给图片用的

很多项目只把图片、JS、CSS 丢给 CDN，这当然没错，但对高并发项目来说，CDN 还能做更多：

- 页面缓存
- 热点 GET 接口缓存
- 地域就近访问
- 防刷和基础防护

如果某个热点详情页或者公开内容接口缓存 10 秒，就可能直接帮源站吃掉 60% 以上流量。

这 10 秒对用户通常完全无感，但对系统压力差别巨大。

### 2. WAF 和防刷要放在最前面

5 万 QPS 的生产系统，常见问题不是“用户太多”，而是：

- 爬虫刷接口
- 恶意脚本打登录
- 参数探测
- 慢请求攻击

如果这些流量先进了应用层，你的机器会被白白消耗。

所以应该在边缘层就做：

- IP 限流
- UA 黑白名单
- 地域拦截
- 登录验证码/滑块
- 基础 CC 防护

### 3. 负载均衡至少双活

入口不要只放一个 Nginx 暴露公网，这不是高并发部署，是赌运气。

至少应该有：

- 云厂商 SLB / ALB
- 多个网关实例
- 健康检查
- 自动摘除异常节点

如果是自建机房，至少也要做 Keepalived + LVS / HAProxy 双机热备。

---

## 五、网关层怎么部署：统一做限流、熔断和灰度

网关层是高并发系统里最容易被低估的一层。

它不只是“转发请求”，更像系统的交通警察。

### 1. 网关层职责

网关建议统一处理：

- TLS 卸载
- 请求头标准化
- 用户身份透传
- 接口级限流
- 熔断与超时控制
- 灰度发布路由
- 访问日志和 Trace ID 注入

### 2. 限流一定要分级

一个成熟的限流方案，至少应该有三层：

- **全局限流**：保护整体集群不被打穿
- **接口限流**：限制高成本接口
- **用户/IP 维度限流**：防刷、防恶意调用

例如：

```text
/api/search     10000 QPS
/api/detail     15000 QPS
/api/order       3000 QPS
/api/login       1000 QPS
单用户下单        5 次/秒
单 IP 登录        20 次/分钟
```

限流的本质不是“拒绝用户”，而是**防止局部异常拖垮全局**。

### 3. 熔断和超时要放在外层

一个典型事故链路是这样的：

1. 某个依赖变慢
2. 应用线程大量等待
3. 连接池耗尽
4. 新请求继续堆积
5. 整个服务雪崩

所以在网关和应用都要设置明确超时：

- 连接超时
- 读取超时
- 上游响应超时
- 重试次数上限

记住一句话：**高并发系统最怕的不是失败，而是失败得太慢。**

---

## 六、应用层怎么部署：无状态、可扩容、可替换

### 1. 应用必须尽量无状态

应用层如果把状态存本机内存，比如：

- 登录 Session 只存在单机
- 本地文件当共享资源
- 本机内存维护库存

那你一旦扩容或者机器重启，就会出很多问题。

正确做法是：

- Session 放 Redis 或 JWT
- 文件放对象存储
- 分布式锁放 Redis / ZooKeeper / etcd
- 配置集中管理

### 2. 横向扩容优先，纵向扩容兜底

5 万 QPS 项目不应该依赖“一台超强应用服务器”。

典型方式是多实例部署：

```text
应用层建议：8 台到 20 台无状态实例起步
单实例 CPU 使用率常态控制在 40% 到 60%
预留扩容空间
```

为什么不要把 CPU 打满？

因为高并发系统的风险不只来自平均流量，还来自：

- 抖动峰值
- Full GC
- 依赖超时
- 发布抖动
- 某台机器性能退化

### 3. 发布时避免“同时重启所有节点”

高并发系统发布必须滚动更新：

- 先摘流量
- 等待连接耗尽
- 再重启实例
- 健康检查通过后再加回流量

否则你很可能在流量高峰时，自己把可用实例数砍半。

---

## 七、缓存层怎么部署：Redis 不是可选项，是核心层

对于 5 万 QPS 的读多写少业务，Redis 几乎是核心基础设施。

### 1. Redis 扛什么流量

一般放这些数据：

- 热点详情
- 配置项
- 用户会话
- 排行榜
- 令牌/验证码/幂等键
- 限流计数器

### 2. Redis 部署建议

至少做到：

- 主从复制
- 哨兵或 Redis Cluster
- 持久化策略明确
- 热 key 监控
- 慢查询监控

如果业务热点非常集中，还要处理：

- 热 key 打散
- 本地缓存兜底
- 多级缓存

### 3. 一定要防缓存雪崩、击穿、穿透

这是高并发系统的经典三连坑。

#### 缓存雪崩

大量 key 同时过期，回源把数据库打爆。

解决方式：

- TTL 加随机值
- 热点 key 永不过期 + 异步刷新
- 多级缓存

#### 缓存击穿

单个热点 key 失效后，瞬间大量请求回源。

解决方式：

- 互斥锁
- singleflight
- 逻辑过期

#### 缓存穿透

请求大量不存在的数据，缓存和数据库都挡不住。

解决方式：

- 布隆过滤器
- 空值缓存
- 参数校验

如果这三件事没做，再多应用机器也救不了你。

---

## 八、数据库层怎么部署：数据库永远是要重点保护的

### 1. 先做读写分离，再谈分库分表

不是所有 5 万 QPS 都必须一上来分库分表。

如果业务大部分是读请求，常见顺序应该是：

1. SQL 优化
2. 索引优化
3. Redis 缓存
4. 主从复制 + 读写分离
5. 再考虑分库分表

很多时候前四步做完，系统已经够用了。

### 2. 什么情况下要分库分表

当你出现这些问题时，再认真考虑：

- 单表数据量过大
- 写入压力持续高
- 主库 CPU / IO 长期过高
- 大事务和热点行竞争明显
- 扩容已经不是加只读副本能解决的

### 3. 数据库部署建议

生产建议至少这样：

- 1 个主库
- 2 个只读副本
- 自动备份
- Binlog 保留
- 同城高可用
- 异地灾备

如果是核心交易系统，再加：

- 半同步复制或更强一致方案
- 容灾演练
- RPO/RTO 指标

### 4. 不要让长事务出现在主链路

高并发系统里，一条慢 SQL 或长事务，杀伤力远大于一个普通异常。

必须重点治理：

- 大分页
- `select *`
- 无索引排序
- 跨很多表 join
- 长时间持锁更新

很多“系统扛不住”的根因，最后不是部署问题，而是数据库使用方式有问题。

---

## 九、异步化：把不需要同步完成的事都移出主链路

如果你希望下单接口 200ms 内返回，就不要在同步链路里做这些事：

- 发短信
- 发邮件
- 记审计日志
- 推送推荐系统
- 刷新复杂统计报表
- 调多个低优先级下游

这些都应该通过 MQ 异步化。

### 1. 同步链路只保留核心动作

例如下单接口的同步链路应该尽量缩成：

1. 参数校验
2. 库存校验
3. 创建订单
4. 发送订单创建事件
5. 立即返回

而不是在一个请求里把所有后置动作全部做完。

### 2. MQ 也要高可用部署

不要因为引入消息队列，就把它自己做成单点。

无论是 Kafka、RabbitMQ 还是 RocketMQ，至少要关注：

- 多节点部署
- 持久化策略
- 消费积压监控
- 死信队列
- 消费幂等

异步化不是“丢给队列就完了”，而是把慢操作转移后，继续确保它**可靠完成**。

---

## 十、容器化和编排：Docker 可以，Kubernetes 更适合长期演进

### 1. 小团队可以先 Docker Compose / ECS

如果是早期项目，完全可以先用：

- Docker
- 云主机
- Nginx
- CI/CD 脚本

只要分层清楚、监控到位，也能支撑不小的流量。

### 2. 到了 5 万 QPS，Kubernetes 的价值会越来越明显

原因不是“因为流行”，而是它更适合：

- 滚动发布
- 自动扩缩容
- 健康检查
- 服务发现
- 资源隔离
- 配置和密钥管理

一个典型配置思路：

- 每个核心服务单独 Deployment
- 设置 `readinessProbe` 和 `livenessProbe`
- 配置 HPA 按 CPU / QPS / 自定义指标扩容
- 关键服务设置 PodDisruptionBudget

### 3. 但别把 K8s 当性能优化工具

Kubernetes 解决的是编排和运维问题，不会自动帮你解决：

- 慢 SQL
- 缓存击穿
- 热点库存争抢
- 接口设计不合理

架构问题，最终还得靠架构本身解决。

## 十一、监控告警：没有可观测性，就没有高并发系统

很多团队的问题不是系统扛不住，而是**系统已经在出问题了，但没人第一时间知道哪里出问题**。

### 1. 至少要监控这些指标

#### 入口层

- 总 QPS
- 各接口 QPS
- 4xx / 5xx 比例
- 平均响应时间
- P95 / P99 延迟
- 限流命中次数

#### 应用层

- CPU
- 内存
- GC 次数和耗时
- 线程池/连接池使用率
- 超时数
- 熔断数

#### Redis

- QPS
- 命中率
- 热 key
- 内存使用率
- 慢查询
- 主从延迟

#### MySQL

- QPS/TPS
- 慢 SQL
- 锁等待
- 主从延迟
- Buffer Pool 命中率
- 连接数

#### MQ

- 生产速率
- 消费速率
- 积压量
- 死信数量

### 2. 不只看平均值，要看尾延迟

高并发系统最危险的情况之一，是平均响应时间看起来还行，但 P99 已经爆了。

例如：

- 平均 80ms
- P95 300ms
- P99 2.8s

这意味着已经有大量用户体验很差，只是平均值把问题掩盖了。

### 3. Trace 要贯通

一个请求经过：

- CDN
- 网关
- 应用 A
- Redis
- 应用 B
- MySQL

如果没有 Trace ID，你排查线上问题会非常痛苦。

所以请求链路必须统一注入：

- Request ID
- Trace ID
- User ID（脱敏后）
- Region / Zone 信息

## 十二、发布策略：高并发系统最怕“上线即事故”

很多系统不是平时扛不住，而是上线那一刻扛不住。

### 1. 必须灰度发布

不要新版本一上来直接全量。

推荐步骤：

1. 1 台实例灰度
2. 观察 5 到 10 分钟
3. 扩到 10%
4. 再观察
5. 最后全量

观察重点包括：

- 错误率
- P99 延迟
- CPU/内存抖动
- 数据库连接数
- Redis 命中率变化

### 2. 必须支持快速回滚

高并发环境下，回滚能力比“发布成功率”还重要。

你至少要做到：

- 镜像版本可追踪
- 配置变更可回滚
- 数据库变更有兼容期
- 灰度流量可立即切回旧版本

### 3. 数据库变更要前向兼容

不要做这种发布：

1. 新代码依赖新字段
2. 先上线代码
3. 再跑 SQL

或者反过来一次性强耦合。

更稳的方式是：

1. 先加字段，保持兼容
2. 新老代码都能运行
3. 完成灰度后再切读写逻辑
4. 最后清理旧字段或旧逻辑

## 十三、一个比较现实的 5 万 QPS 初始部署参考

这里只给一个偏保守、可落地的参考，不是唯一答案。

### 1. 入口层

- CDN：1 套
- WAF：1 套
- 公网负载均衡：2 可用区部署
- 网关实例：4 台起步

### 2. 应用层

- 核心应用服务：8 到 12 台
- 非核心后台服务：2 到 4 台
- 异步消费者：按队列积压情况独立扩容

### 3. 缓存和消息层

- Redis：3 主 3 从或 Cluster
- Kafka / RocketMQ：3 节点起步

### 4. 数据层

- MySQL 主库：1 台
- MySQL 只读副本：2 台
- 搜索服务 ES：3 节点（如确有搜索需求）

### 5. 可观测与运维

- Prometheus + Grafana
- Loki / ELK
- Jaeger / Tempo / SkyWalking
- 自动化发布流水线

这套不一定能直接“无脑扛住所有 5 万 QPS”，但它至少具备了：

- 扩容基础
- 故障隔离能力
- 回滚能力
- 监控能力

这比单纯讨论“买几核几 G”有意义得多。

## 十四、真正决定成败的，不是技术名词，而是治理能力

最后再说一句很现实的话。

5 万 QPS 的项目能不能稳，不只是看你会不会 Redis、MQ、K8s，而是看你有没有这些治理能力：

- 能不能提前做容量评估
- 能不能把热点流量挡在前面
- 能不能把慢操作移出主链路
- 能不能给数据库减压
- 能不能在依赖异常时快速降级
- 能不能在发布出问题时立即回滚
- 能不能在事故发生 1 分钟内定位瓶颈

这些能力加起来，才叫“高并发部署”。

---

## 总结

如果你让我把“怎么部署一个 5 万 QPS 项目”压缩成最核心的几句话，那就是：

1. **先做容量评估，不要凭感觉估机器**
2. **先做流量分层，不要让所有请求直打数据库**
3. **应用层必须无状态，才能稳定横向扩容**
4. **Redis 和 MQ 是减压核心，不是可选优化项**
5. **限流、熔断、降级、灰度、回滚必须一开始就设计进去**
6. **没有监控和 Trace，再强的架构也扛不住线上事故**

高并发系统从来不是一台机器撑起来的，而是一整套工程体系撑起来的。

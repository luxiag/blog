# RBAC 与 ABAC：权限控制模型原理与 Node.js 实现

权限控制是每个业务系统都绕不开的问题，但很多项目在早期用一堆 `if (user.role === 'admin')` 硬编码判断，随着角色和资源增多，代码越来越难维护。

这篇文章系统讲两套成熟的权限控制模型：

- **RBAC（Role-Based Access Control）**：基于角色的访问控制，适合权限关系相对固定的场景
- **ABAC（Attribute-Based Access Control）**：基于属性的访问控制，适合需要细粒度、动态策略的场景

我们不只讲概念，还会用 Node.js 分别实现两套完整的鉴权中间件，让你能直接在项目里落地。

---

## 一、先建立基础认知：Authentication vs Authorization

很多人混淆这两个词：

| 概念 | 含义 | 典型技术 |
|---|---|---|
| **Authentication（认证）** | 你是谁？验证身份 | JWT、Session、OAuth |
| **Authorization（授权）** | 你能做什么？验证权限 | RBAC、ABAC、ACL |

本文讲的是 **Authorization**，即在"已经知道用户是谁"的前提下，判断他能不能做某件事。

### 权限控制的演进

最原始的方式是 **ACL（Access Control List）**，直接把用户和资源的对应关系列举出来：

```
用户 Alice → 可以读取文件 A、可以写文件 B
用户 Bob   → 只能读取文件 A
```

ACL 的问题是：用户一多，维护量爆炸。100 个用户、50 个资源，就是 5000 条规则。

**RBAC** 解决了这个问题：把权限分配给角色，用户再分配角色，权限管理变成两张关系表。

**ABAC** 进一步解决了 RBAC 的不足：当权限判断需要考虑"上下文"（时间、地点、资源属性、用户属性）时，RBAC 的角色粒度太粗，ABAC 通过策略表达式来描述更复杂的访问规则。

## 二、RBAC：基于角色的访问控制

### 核心概念

RBAC 有三个核心要素：

```
用户（User）→ 分配 → 角色（Role）→ 拥有 → 权限（Permission）
```

- **User**：系统中的使用者
- **Role**：角色是一个权限集合，比如 `admin`、`editor`、`viewer`
- **Permission**：对某个资源执行某个操作的能力，通常表示为 `resource:action`，比如 `article:create`、`user:delete`

### 数据模型设计

最基础的 RBAC 需要 5 张表：

```sql
-- 用户表
CREATE TABLE users (
  id        INT PRIMARY KEY AUTO_INCREMENT,
  username  VARCHAR(100) NOT NULL UNIQUE,
  password  VARCHAR(255) NOT NULL
);

-- 角色表
CREATE TABLE roles (
  id          INT PRIMARY KEY AUTO_INCREMENT,
  name        VARCHAR(50) NOT NULL UNIQUE,   -- 'admin', 'editor', 'viewer'
  description VARCHAR(255)
);

-- 权限表
CREATE TABLE permissions (
  id       INT PRIMARY KEY AUTO_INCREMENT,
  resource VARCHAR(50) NOT NULL,   -- 'article', 'user', 'comment'
  action   VARCHAR(50) NOT NULL,   -- 'create', 'read', 'update', 'delete'
  UNIQUE KEY uk_resource_action (resource, action)
);

-- 用户-角色关联（多对多）
CREATE TABLE user_roles (
  user_id INT NOT NULL,
  role_id INT NOT NULL,
  PRIMARY KEY (user_id, role_id)
);

-- 角色-权限关联（多对多）
CREATE TABLE role_permissions (
  role_id       INT NOT NULL,
  permission_id INT NOT NULL,
  PRIMARY KEY (role_id, permission_id)
);
```

这个设计的好处是：修改角色权限时，只需要改 `role_permissions` 一张表，所有持有该角色的用户权限同步更新，不需要逐一改动用户。

### RBAC 的四个级别

标准 RBAC 规范定义了四个层次（从简到复杂）：

| 级别 | 名称 | 增加的能力 |
|---|---|---|
| RBAC0 | 基础 | 用户-角色-权限的核心三角关系 |
| RBAC1 | 角色继承 | 角色可以继承另一个角色的权限（`manager` 继承 `editor`） |
| RBAC2 | 约束 | 互斥角色（不能同时拥有 `auditor` 和 `cashier`）、基数限制 |
| RBAC3 | 统一 | 同时支持继承和约束 |

大多数业务系统实现 RBAC1 就够了（加上角色继承）。

#### 核心：权限查询服务

用户每次请求都去数据库查权限代价太高，这里用内存缓存（生产环境用 Redis）：

```ts
// services/permission.ts
import { db } from '../db';

// 简单内存缓存，生产环境换成 Redis
const permissionCache = new Map<number, Set<string>>();

/**
 * 获取用户拥有的所有权限，格式为 "resource:action"
 * 例如: Set { 'article:read', 'article:create', 'user:read' }
 */
export async function getUserPermissions(userId: number): Promise<Set<string>> {
  // 先查缓存
  if (permissionCache.has(userId)) {
    return permissionCache.get(userId)!;
  }

  // 一条 SQL 查出用户通过所有角色拥有的所有权限
  const rows = await db.query<{ resource: string; action: string }[]>(
    `SELECT DISTINCT p.resource, p.action
     FROM users u
     JOIN user_roles ur ON ur.user_id = u.id
     JOIN role_permissions rp ON rp.role_id = ur.role_id
     JOIN permissions p ON p.id = rp.permission_id
     WHERE u.id = ?`,
    [userId]
  );

  const permissions = new Set(rows.map(r => `${r.resource}:${r.action}`));

  // 缓存 5 分钟
  permissionCache.set(userId, permissions);
  setTimeout(() => permissionCache.delete(userId), 5 * 60 * 1000);

  return permissions;
}

/**
 * 检查用户是否有某个权限
 */
export async function hasPermission(
  userId: number,
  resource: string,
  action: string
): Promise<boolean> {
  const permissions = await getUserPermissions(userId);
  return permissions.has(`${resource}:${action}`);
}

/**
 * 角色变更时清除缓存（在修改用户角色的接口中调用）
 */
export function clearUserPermissionCache(userId: number): void {
  permissionCache.delete(userId);
}
```

#### 鉴权中间件

```ts
// middleware/rbac.ts
import { Request, Response, NextFunction } from 'express';
import { hasPermission } from '../services/permission';

/**
 * RBAC 鉴权中间件工厂函数
 * 用法：router.get('/articles', requirePermission('article', 'read'), handler)
 */
export function requirePermission(resource: string, action: string) {
  return async (req: Request, res: Response, next: NextFunction) => {
    // 假设前置的 JWT 中间件已经把 userId 放到 req.user
    const userId = req.user?.id;

    if (!userId) {
      return res.status(401).json({ error: '未登录' });
    }

    const allowed = await hasPermission(userId, resource, action);

    if (!allowed) {
      return res.status(403).json({
        error: '权限不足',
        required: `${resource}:${action}`,
      });
    }

    next();
  };
}

/**
 * 多权限校验：AND 模式（用户必须同时拥有所有权限）
 */
export function requireAllPermissions(
  ...perms: Array<{ resource: string; action: string }>
) {
  return async (req: Request, res: Response, next: NextFunction) => {
    const userId = req.user?.id;
    if (!userId) return res.status(401).json({ error: '未登录' });

    for (const { resource, action } of perms) {
      const allowed = await hasPermission(userId, resource, action);
      if (!allowed) {
        return res.status(403).json({
          error: '权限不足',
          required: `${resource}:${action}`,
        });
      }
    }

    next();
  };
}
```

#### RBAC1：加入角色继承

角色继承用一张自关联表实现：

```sql
-- 在 roles 表中加一个 parent_id（或单独建关系表）
ALTER TABLE roles ADD COLUMN parent_id INT NULL REFERENCES roles(id);

-- 例如：manager 继承 editor，editor 继承 viewer
-- INSERT INTO roles VALUES (1, 'viewer', NULL, NULL);
-- INSERT INTO roles VALUES (2, 'editor', NULL, 1);   -- parent_id = 1（viewer）
-- INSERT INTO roles VALUES (3, 'manager', NULL, 2);  -- parent_id = 2（editor）
```

查询时用递归 CTE 把继承链上的角色全部取出：

```sql
-- 查用户通过角色继承链拥有的所有权限
WITH RECURSIVE role_hierarchy AS (
  -- 从用户直接拥有的角色开始
  SELECT r.id, r.parent_id
  FROM roles r
  JOIN user_roles ur ON ur.role_id = r.id
  WHERE ur.user_id = ?

  UNION ALL

  -- 递归查父角色
  SELECT r.id, r.parent_id
  FROM roles r
  JOIN role_hierarchy rh ON rh.parent_id = r.id
)
SELECT DISTINCT p.resource, p.action
FROM role_hierarchy rh
JOIN role_permissions rp ON rp.role_id = rh.id
JOIN permissions p ON p.id = rp.permission_id;
```

### RBAC 的局限

RBAC 对静态权限管理很好用，但遇到以下场景就力不从心：

- **资源所有权**：用户只能编辑**自己发的**文章，不能编辑别人的
- **时间限制**：审计员只能在工作时间（9:00-18:00）访问财务数据
- **地理位置**：只有从公司内网 IP 才能导出数据
- **数据级别**：VIP 用户可以看高精度数据，普通用户只能看聚合数据

这些需求靠角色无法表达，这就是 ABAC 要解决的问题。

## 三、ABAC：基于属性的访问控制

### 核心概念

ABAC 的判断依据不是"角色"，而是**属性（Attribute）**。每次访问控制决策由四类属性共同决定：

```
Subject（主体）  ── 用户本身的属性
  ├── user.id = 42
  ├── user.department = 'finance'
  └── user.level = 'senior'

Object（客体）   ── 被访问资源的属性
  ├── document.owner = 42
  ├── document.classification = 'confidential'
  └── document.department = 'finance'

Action（操作）   ── 要执行的动作
  └── action = 'export'

Environment（环境） ── 访问时的上下文
  ├── env.time = '14:30'
  ├── env.ip = '10.0.0.1'
  └── env.isWeekday = true
```

**策略（Policy）** 是一条逻辑规则，描述"在什么条件下，允许/拒绝访问"：

```
// 策略示例：同部门的员工才能访问本部门机密文档
ALLOW IF:
  user.department == document.department
  AND document.classification == 'confidential'
  AND action IN ['read', 'download']
```

### 策略引擎设计

ABAC 的核心是 **PDP（Policy Decision Point，策略决策点）**，它接收一次访问请求的所有属性，逐条评估策略，最终返回 `ALLOW` 或 `DENY`。

```
请求 (subject, object, action, environment)
        ↓
     PDP（策略决策点）
        ↓  查询
     PAP（策略管理点） ── 存储所有策略
        ↓  返回匹配的策略
     PDP 评估
        ↓
   ALLOW / DENY
```

### Node.js 实现

#### 定义策略

策略用 JSON 表示，每条策略由若干条件（`conditions`）组成，所有条件都满足时生效：

```ts
// types/abac.ts

// 支持的比较操作符
type Operator =
  | 'eq'         // 等于
  | 'neq'        // 不等于
  | 'in'         // 包含于数组
  | 'not_in'     // 不包含于数组
  | 'gt'         // 大于
  | 'gte'        // 大于等于
  | 'lt'         // 小于
  | 'lte'        // 小于等于
  | 'contains'   // 字符串包含
  | 'starts_with'; // 字符串开头

// 属性来源
type AttributeSource = 'subject' | 'object' | 'action' | 'environment';

// 一个条件：左侧属性路径 操作符 右侧值（或另一个属性路径）
interface Condition {
  left: {
    source: AttributeSource;
    path: string;  // 属性路径，如 'department'、'level'
  };
  operator: Operator;
  right:
    | { type: 'value'; value: unknown }                 // 固定值
    | { type: 'attribute'; source: AttributeSource; path: string }; // 另一个属性
}

// 一条策略
export interface Policy {
  id: string;
  effect: 'allow' | 'deny';  // deny 优先级高于 allow
  description: string;
  conditions: Condition[];   // 所有条件 AND 关系，全部满足才生效
}

// 一次访问请求的上下文
export interface AccessContext {
  subject: Record<string, unknown>;      // 用户属性
  object: Record<string, unknown>;       // 资源属性
  action: string;                        // 操作
  environment: Record<string, unknown>;  // 环境属性
}
```

#### 策略引擎核心

```ts
// services/abac-engine.ts
import { Policy, AccessContext, Condition } from '../types/abac';
import { get } from 'lodash'; // 用于按路径取属性值

/**
 * 取属性值，支持嵌套路径（如 'address.city'）
 */
function resolveAttribute(
  ctx: AccessContext,
  source: string,
  path: string
): unknown {
  const target =
    source === 'action'
      ? { value: ctx.action }
      : (ctx as Record<string, unknown>)[source];
  return get(target, path);
}

/**
 * 评估单个条件
 */
function evaluateCondition(condition: Condition, ctx: AccessContext): boolean {
  const leftValue = resolveAttribute(
    ctx,
    condition.left.source,
    condition.left.path
  );

  const rightValue =
    condition.right.type === 'value'
      ? condition.right.value
      : resolveAttribute(ctx, condition.right.source, condition.right.path);

  switch (condition.operator) {
    case 'eq':
      return leftValue === rightValue;
    case 'neq':
      return leftValue !== rightValue;
    case 'in':
      return Array.isArray(rightValue) && rightValue.includes(leftValue);
    case 'not_in':
      return Array.isArray(rightValue) && !rightValue.includes(leftValue);
    case 'gt':
      return (leftValue as number) > (rightValue as number);
    case 'gte':
      return (leftValue as number) >= (rightValue as number);
    case 'lt':
      return (leftValue as number) < (rightValue as number);
    case 'lte':
      return (leftValue as number) <= (rightValue as number);
    case 'contains':
      return String(leftValue).includes(String(rightValue));
    case 'starts_with':
      return String(leftValue).startsWith(String(rightValue));
    default:
      return false;
  }
}

/**
 * 评估单条策略是否命中（所有条件都满足）
 */
function evaluatePolicy(policy: Policy, ctx: AccessContext): boolean {
  return policy.conditions.every(condition =>
    evaluateCondition(condition, ctx)
  );
}

/**
 * PDP：策略决策点
 * 返回 true（允许）或 false（拒绝）
 *
 * 决策顺序：
 * 1. 只要有一条 deny 策略命中 → 拒绝（deny 优先）
 * 2. 至少有一条 allow 策略命中 → 允许
 * 3. 没有任何策略命中 → 拒绝（默认拒绝）
 */
export function evaluate(policies: Policy[], ctx: AccessContext): boolean {
  const matchedPolicies = policies.filter(p => evaluatePolicy(p, ctx));

  // deny 优先
  const hasDeny = matchedPolicies.some(p => p.effect === 'deny');
  if (hasDeny) return false;

  // 有 allow 才放行
  const hasAllow = matchedPolicies.some(p => p.effect === 'allow');
  return hasAllow;
}
```

#### ABAC 鉴权中间件

```ts
// middleware/abac.ts
import { Request, Response, NextFunction } from 'express';
import { evaluate } from '../services/abac-engine';
import { getPolicies } from '../services/policy-store';
import { AccessContext } from '../types/abac';

/**
 * 构建环境属性（时间、IP 等上下文信息）
 */
function buildEnvironment(req: Request): Record<string, unknown> {
  const now = new Date();
  const hour = now.getHours();

  return {
    ip: req.ip,
    isWorkHours: hour >= 9 && hour < 18,
    isWeekday: now.getDay() >= 1 && now.getDay() <= 5,
    timestamp: now.toISOString(),
    userAgent: req.headers['user-agent'],
  };
}

/**
 * ABAC 鉴权中间件工厂函数
 *
 * @param action      操作名，如 'read'、'update'、'export'
 * @param getResource 从请求中异步获取资源属性的函数（需要查数据库）
 */
export function requireAccess(
  action: string,
  getResource: (req: Request) => Promise<Record<string, unknown>>
) {
  return async (req: Request, res: Response, next: NextFunction) => {
    const userId = req.user?.id;
    if (!userId) {
      return res.status(401).json({ error: '未登录' });
    }

    // 构建完整的访问上下文
    const resourceAttributes = await getResource(req);

    const ctx: AccessContext = {
      subject: req.user as Record<string, unknown>,  // JWT 解析出的用户信息
      object: resourceAttributes,
      action,
      environment: buildEnvironment(req),
    };

    const allowed = evaluate(getPolicies(), ctx);

    if (!allowed) {
      return res.status(403).json({ error: '权限不足' });
    }

    next();
  };
}
```

```ts
  '/documents/:id/export',
  authenticateJWT,
  requireAccess('export', async (req) => {
    const doc = await DocumentService.findById(req.params.id);
    return {
      id: doc.id,
      department: doc.department,
      classification: doc.classification,
    };
  }),
  async (req, res) => {
    const result = await DocumentService.export(req.params.id);
    res.json(result);
  }
);

export default router;
```

## 四、RBAC 与 ABAC 对比

| 维度 | RBAC | ABAC |
|---|---|---|
| **核心依据** | 用户角色 | 属性（用户 + 资源 + 环境） |
| **策略表达** | 角色 → 权限 映射关系 | 布尔条件表达式 |
| **粒度** | 资源级（能不能访问某类资源） | 实例级（能不能访问某条具体记录） |
| **动态性** | 低（权限变更需修改角色配置） | 高（策略可基于运行时属性动态决策） |
| **实现复杂度** | 低 | 高 |
| **性能开销** | 低（缓存权限集合） | 较高（每次请求需获取资源属性并评估策略） |
| **适用场景** | 企业内部系统、CMS、后台管理 | 多租户 SaaS、合规审计、金融/医疗系统 |

### 选型建议

**选 RBAC 的场景：**
- 用户角色类型固定（admin / editor / viewer）
- 权限颗粒度到"资源类型"就够（能不能操作文章，不需要区分哪篇文章）
- 团队规模小，权限逻辑相对简单

**选 ABAC 的场景：**
- 需要"数据权限"（用户只能看自己部门的数据）
- 需要时间、IP、风险等级等上下文因素参与鉴权
- 权限规则频繁变化，需要动态配置而不想改代码

**混合使用（最常见的实际方案）：**

大多数成熟系统两者都用：RBAC 做粗粒度的功能权限（这个模块能不能进），ABAC 做细粒度的数据权限（这条记录能不能读）。

```ts
// 混合模式：先用 RBAC 判断功能权限，再用 ABAC 判断数据权限
router.put(
  '/documents/:id',
  authenticateJWT,

  // 第一关：RBAC 检查用户是否有文档编辑功能权限
  requirePermission('document', 'update'),

  // 第二关：ABAC 检查用户是否能编辑这条具体的文档
  requireAccess('update', async (req) => {
    const doc = await DocumentService.findById(req.params.id);
    return { authorId: doc.authorId, department: doc.department };
  }),

  async (req, res) => {
    const updated = await DocumentService.update(req.params.id, req.body);
    res.json(updated);
  }
);
```

## 五、生产环境注意事项

### 权限缓存与失效

RBAC 的权限查询结果应该缓存，但缓存必须在以下时机主动清除：

```ts
// 以下操作后必须清除对应用户的权限缓存
// 1. 修改用户的角色分配
async function assignRole(userId: number, roleId: number) {
  await db.query('INSERT INTO user_roles (user_id, role_id) VALUES (?, ?)', [userId, roleId]);
  clearUserPermissionCache(userId); // 清缓存
}

// 2. 修改角色的权限分配（影响所有持有该角色的用户）
async function revokeRolePermission(roleId: number, permissionId: number) {
  await db.query(
    'DELETE FROM role_permissions WHERE role_id = ? AND permission_id = ?',
    [roleId, permissionId]
  );
  // 清除所有持有该角色的用户的缓存
  const userIds = await getUsersByRole(roleId);
  userIds.forEach(id => clearUserPermissionCache(id));
}
```

### 权限校验的审计日志

权限被拒绝时，应该记录日志供安全审计：

```ts
// 在中间件中加入审计日志
if (!allowed) {
  logger.warn('access_denied', {
    userId: req.user?.id,
    action,
    resource: resourceAttributes,
    ip: req.ip,
    timestamp: new Date().toISOString(),
  });
  return res.status(403).json({ error: '权限不足' });
}
```

:::warning
**不要在 403 响应中暴露资源是否存在**。如果用户没有权限访问 `/documents/123`，直接返回 403 而不是 404，否则攻击者可以通过枚举 ID 来探测资源存在性。
:::

:::tip
**ABAC 的策略变更需要测试**。策略引擎的逻辑一旦出错，可能导致大面积权限失效或越权。建议把策略写成可测试的单元，用 `evaluate(policies, ctx)` 直接单测每一条策略在各种属性组合下的预期结果。
:::

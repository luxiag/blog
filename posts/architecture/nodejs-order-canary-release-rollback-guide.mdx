# Node.js 订单系统灰度发布与快速回滚实战：流程、门禁与检查清单

订单系统最怕“上线即事故”。

灰度发布的核心目标不是“慢慢发”，而是：

1. 尽早发现问题
2. 把影响限制在小范围
3. 能在几分钟内回滚

---

## 一、发布策略：小流量验证，逐步放量

推荐四段式灰度：

1. `1%` 流量（5-10 分钟）
2. `10%` 流量（10-20 分钟）
3. `30%-50%` 流量（20-30 分钟）
4. `100%` 全量

每个阶段都必须通过门禁指标，才允许进入下一阶段。

---

## 二、发布前门禁（必须通过）

发布前建议至少满足：

1. 单元测试与集成测试通过
2. 压测基线无明显回退
3. 关键接口 P99 在阈值内
4. 数据库变更已做前向兼容
5. 回滚版本镜像可用
6. 关键开关（降级/限流/熔断）可动态启用

如果这些都没准备好，不建议发核心交易链路。

---

## 三、数据库变更原则（避免回滚困难）

发布和 DB 变更要解耦，遵循“可回滚优先”：

1. 先加字段，不删旧字段
2. 新老代码一段时间内双兼容
3. 先双写再切读
4. 最后才清理旧字段

不要做“代码依赖新字段，但字段尚未上线”的强耦合发布。

---

## 四、灰度期间重点观察指标

### 1. 系统指标

1. `/api/orders` 错误率
2. `/api/orders` P95/P99
3. Node Event Loop Delay
4. CPU / 内存

### 2. 业务指标

1. 下单成功率
2. 支付成功率
3. 订单状态异常数
4. Outbox 积压

### 3. 下游依赖指标

1. MySQL 慢 SQL
2. Redis 延迟
3. MQ 消费积压

灰度看板建议单独做“新版本 vs 旧版本”对比。

---

## 五、发布流程（可执行版）

### 阶段 A：发布 1%

1. 部署新版本到灰度实例
2. 仅放 1% 流量
3. 观察 10 分钟

通过条件示例：

1. 5xx 未高于旧版本 +0.2%
2. P99 未高于旧版本 +20%
3. 业务成功率无明显下降

### 阶段 B：放量 10%

1. 将流量提升到 10%
2. 保持观察 10-20 分钟
3. 核对订单状态一致性

### 阶段 C：放量 30%-50%

1. 扩容新版本副本
2. 放量到 30%-50%
3. 重点观察下游容量变化

### 阶段 D：全量

1. 切到 100%
2. 保留旧版本一段时间可随时切回
3. 完成发布复核

---

## 六、快速回滚 SOP（重点）

### 触发条件示例

满足任一条件立即回滚：

1. 关键接口 5xx > 1%
2. 下单成功率下降 > 2%
3. 支付回调异常激增
4. 数据一致性校验失败

### 回滚步骤

1. 停止继续放量
2. 流量切回旧版本
3. 保留问题实例用于排查
4. 开启降级开关兜底
5. 执行数据校验与补偿任务
6. 发布事故通报

目标是“先止血，再定位”。

---

## 七、Node.js 版本发布健康探针建议

健康检查至少区分：

1. `liveness`：进程是否存活
2. `readiness`：是否可以接流量

示例：

```ts
app.get('/health/live', async () => ({ ok: true }))

app.get('/health/ready', async (_, reply) => {
  const dbOk = await pingDb()
  const redisOk = await pingRedis()

  if (!dbOk || !redisOk) {
    return reply.code(503).send({ ok: false })
  }

  return { ok: true }
})
```

灰度环境中不健康实例要自动摘流量。

---

## 八、发布开关设计（强烈建议）

建议至少有以下运行时开关：

1. 下单非核心逻辑降级开关
2. 支付回调异步化开关
3. Outbox worker 并发开关
4. 推荐/营销信息熔断开关

这样在灰度异常时，不必立刻回滚整个版本。

---

## 九、发布后数据校验脚本示例

### 1. 支付成功但订单未支付

```sql
SELECT o.order_no
FROM orders o
JOIN payments p ON p.order_no = o.order_no
WHERE p.status = 'SUCCESS'
  AND o.status NOT IN ('PAID', 'FULFILLING', 'FINISHED', 'REFUNDING', 'REFUNDED');
```

### 2. 已取消但存在履约记录

```sql
SELECT o.order_no
FROM orders o
JOIN fulfillments f ON f.order_no = o.order_no
WHERE o.status = 'CANCELED';
```

发布后建议自动跑一次校验任务。

---

## 十、发布检查清单（可直接用）

### 发布前

1. 回滚镜像存在并可启动
2. DB 变更前向兼容
3. 指标看板与告警正常
4. 灰度开关可用
5. 值班人员到位

### 灰度中

1. 每阶段记录开始与结束时间
2. 记录关键指标快照
3. 达阈值立即暂停

### 发布后

1. 数据一致性校验通过
2. 告警恢复到常态
3. 输出发布报告

---

## 十一、常见误区

1. 灰度只看系统指标，不看业务成功率
2. 灰度窗口太短，问题尚未暴露就全量
3. 发布与数据库改动强绑定
4. 无回滚预案，出问题只能硬扛

---

## 总结

Node.js 订单系统的灰度发布，不是“慢慢推版本”，而是建立一套可重复执行的风险控制流程：

1. 发布前有门禁
2. 灰度中有指标
3. 异常时能止血
4. 失败时能快速回滚

只要把这四件事做扎实，核心交易系统上线风险会大幅下降。

# Node.js 订单系统故障演练与应急预案：演练脚本、SOP 与复盘模板

多数线上事故不是“没技术”，而是“没演练”。

你可以把故障演练理解为：

> 在可控环境中，提前把线上会踩的坑踩一遍。

这篇文章给你一套可执行的 Node.js 订单系统演练方法。

---

## 一、演练目标（先定成功标准）

每次演练必须有明确目标，例如：

1. 下单服务故障时，5 分钟内完成止血
2. MySQL 主库抖动时，错误率控制在 1% 内
3. MQ 积压时，30 分钟内恢复到安全水位
4. 支付回调异常时，不出现订单状态错乱

目标要可量化，否则无法评估是否成功。

---

## 二、演练范围与边界

建议先从“可控小范围”开始：

1. 预发环境或灰度环境
2. 单业务域（订单创建、支付回调、Outbox 投递）
3. 演练窗口内禁止高风险发布
4. 明确一键回滚开关

演练不是“制造事故”，而是“可控验证恢复能力”。

---

## 三、订单系统常见故障场景清单

建议优先演练这 8 类：

1. 应用 CPU 打满
2. Node 进程内存飙升
3. MySQL 慢查询/锁等待
4. Redis 不可用或高延迟
5. MQ 堵塞与消费积压
6. 支付回调超时/重复回调
7. 下游服务 5xx 激增
8. 配置中心异常导致参数错配

---

## 四、演练组织角色

一次完整演练建议有 4 个角色：

1. 指挥官（决策与节奏）
2. 注入执行人（故障注入）
3. 观察员（指标与日志记录）
4. 业务代表（评估用户影响）

没有角色分工，演练很容易混乱。

---

## 五、演练前检查清单

执行前逐项确认：

1. 告警通道可用（钉钉/Slack/PagerDuty）
2. 看板可用（Grafana/日志/Trace）
3. 回滚脚本和开关已验证
4. 数据库备份可恢复
5. 演练通知已发（避免误判为真实事故）

---

## 六、故障注入示例（Node.js）

以下示例建议仅用于预发或受控灰度环境。

### 1. 注入下游超时

在配置中增加故障开关：

```ts
export const chaosConfig = {
  paymentTimeoutRate: Number(process.env.CHAOS_PAYMENT_TIMEOUT_RATE || 0),
}
```

调用支付服务时：

```ts
function shouldInject(rate: number) {
  return Math.random() < rate
}

export async function callPayment(payload: any) {
  if (shouldInject(chaosConfig.paymentTimeoutRate)) {
    await new Promise((r) => setTimeout(r, 5000))
    throw new Error('Injected payment timeout')
  }

  return httpClient.post('/payment', payload, { timeout: 800 })
}
```

### 2. 注入数据库慢查询

```sql
SELECT SLEEP(2);
```

或在应用层故意增加慢 SQL 路由，仅演练窗口开启。

### 3. 注入 MQ 消费暂停

通过开关让消费者暂时不消费：

```ts
if (process.env.CHAOS_PAUSE_CONSUMER === 'true') {
  return
}
```

## 七、演练过程 SOP（标准流程）

### 1. 启动阶段

1. 指挥官宣布开始
2. 观察员记录 T0 时刻基线指标
3. 执行人注入单一故障

### 2. 观察阶段

观察 5-10 分钟核心指标：

1. 下单成功率
2. `/api/orders` P99
3. 5xx 错误率
4. Outbox 积压
5. MQ lag

### 3. 响应阶段

按预案执行止血动作：

1. 降级非核心功能
2. 熔断异常下游
3. 提升关键服务副本数
4. 限流防止放大

### 4. 恢复阶段

1. 关闭故障注入
2. 观察恢复曲线
3. 清理积压任务
4. 验证数据一致性

---

## 八、应急止血动作模板

建议沉淀成 Runbook，演练和真实事故都按它执行。

### 场景 A：下单 P99 持续升高

1. 立即查看下游依赖耗时排行
2. 对最慢依赖启用熔断
3. 降级非核心链路（推荐、营销）
4. 临时提高下单服务副本

### 场景 B：支付回调异常

1. 先保证回调接口幂等
2. 暂时落库回调事件，延后异步处理
3. 对账任务补齐状态

### 场景 C：Outbox 积压上涨

1. 提升 publisher worker 并发
2. 排查 MQ broker 延迟
3. 处理死信并重放

---

## 九、演练验证标准

每次演练至少验证：

1. 监控是否及时发现问题
2. 告警是否正确触达
3. 团队是否按 SOP 执行
4. 止血是否在目标时间完成
5. 恢复后数据是否一致

没有验证标准，演练只能算“做过”，不能算“有效”。

## 十、数据一致性校验脚本示例

演练后建议跑自动校验任务。

```sql
-- 支付成功但订单非 PAID 的异常单
SELECT o.order_no
FROM orders o
JOIN payments p ON p.order_no = o.order_no
WHERE p.status = 'SUCCESS'
  AND o.status NOT IN ('PAID', 'FULFILLING', 'FINISHED', 'REFUNDING', 'REFUNDED');
```

```sql
-- 已取消但有履约记录
SELECT o.order_no
FROM orders o
JOIN fulfillments f ON f.order_no = o.order_no
WHERE o.status = 'CANCELED';
```

## 十一、复盘模板（建议固定格式）

每次演练结束后 24 小时内完成复盘。

```text
1. 演练编号与目标
2. 注入故障类型与时间线
3. 指标变化（P99/错误率/积压）
4. 响应动作与耗时
5. 恢复时间与影响范围
6. 暴露问题清单（监控、代码、流程、组织）
7. 改进项负责人 + 截止日期
```

复盘不追责个人，重点找系统性改进。

---

## 十二、演练频率建议

建议节奏：

1. 每月小演练（单场景）
2. 每季度大演练（跨系统）
3. 重大版本前专项演练

把演练变成常规动作，而不是事故后补课。

---

## 十三、常见误区

1. 演练只测技术，不测协作流程
2. 只看系统指标，不看业务指标
3. 演练后不复盘、不跟进改进项
4. 演练场景永远固定，无法覆盖新风险

---

## 十四、最小落地方案（今天就能做）

1. 选 1 个核心场景（支付超时）
2. 加 1 个可控故障注入开关
3. 配 3 条核心告警（P99/5xx/积压）
4. 写 1 份 SOP
5. 做 1 次 30 分钟演练
6. 产出 1 份复盘

这 6 步做完，你的系统抗故障能力会明显提升。

---

## 总结

Node.js 订单系统的稳定性不是靠“永不出错”，而是靠：

1. 可观测
2. 可止血
3. 可恢复
4. 可复盘

故障演练的价值就在于，把这四件事从“理论上会”变成“现场能做”。

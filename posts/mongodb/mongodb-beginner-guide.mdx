# MongoDB 入门：从文档模型到聚合与索引的系统指南

MongoDB 是最常见的文档型数据库之一。它把数据存成 **JSON 风格的文档（BSON）**，天然适合表示“一个对象连同它的子结构”的场景，比如用户资料、订单详情、内容管理、日志与事件。

本文目标：让你对 MongoDB 的能力边界有清晰认知，能写出常用查询与聚合，知道如何建索引、如何建模，以及上线后怎么做安全、备份与性能排查。

> 说明：MongoDB 常用交互方式包括 `mongosh`（交互式 Shell）和驱动（Node/Java/Go/...）。本文示例以 `mongosh` 风格为主。

---

## 1. MongoDB 的整体认知：它擅长什么，不擅长什么

### 1.1 MongoDB 解决的问题

- **文档模型**：一条记录可以嵌套对象/数组，读写一个业务对象更自然
- **灵活模式**：字段可选、结构可演进（但并不等于“无结构”）
- **强大的聚合**：通过聚合管道完成统计、分组、Join（`$lookup`）
- **水平扩展**：通过分片（Sharding）扩展容量与吞吐

### 1.2 你需要谨慎的地方

- 复杂多表强一致关联的 OLTP 模式，关系型数据库通常更顺手
- 超复杂的跨表报表/分析（尤其是多维度、临时组合），往往数据仓库/OLAP 更合适
- “随便加字段就行”的心态会带来数据质量与查询性能问题：MongoDB 需要**模式治理**

## 2. 核心概念：数据库、集合、文档

在 MongoDB 里对应关系大致是：

- Database（数据库）：一组集合
- Collection（集合）：类似“表”
- Document（文档）：类似“一行记录”，结构为 JSON 风格

一个文档示例：

```js
{
  _id: ObjectId("..."),
  userId: 1,
  status: "PAID",
  items: [
    { productId: 2001, quantity: 2, unitPrice: 19.9 },
    { productId: 2002, quantity: 1, unitPrice: 99.0 }
  ],
  createdAt: ISODate("2026-01-10T00:00:00Z")
}
```

### 2.1 BSON 与 ObjectId

MongoDB 底层存的是 BSON（Binary JSON），比 JSON 多了一些类型：

- `ObjectId`：常见的默认主键类型，包含时间戳等信息
- `Date`：日期类型
- `Decimal128`：高精度小数

很多初学者踩坑来自“以为是字符串，实际是类型”。比如 `ObjectId("...")` 不是普通字符串。

## 3. 快速上手：创建库、集合与插入数据

```js
use shop

db.users.insertOne({
  name: "Alice",
  email: "alice@example.com",
  createdAt: new Date()
})

db.orders.insertMany([
  {
    userId: 1,
    status: "PAID",
    items: [
      { productId: 2001, quantity: 2, unitPrice: 19.9 },
      { productId: 2002, quantity: 1, unitPrice: 99 }
    ],
    createdAt: new Date("2026-01-10")
  },
  {
    userId: 2,
    status: "CREATED",
    items: [{ productId: 2001, quantity: 1, unitPrice: 19.9 }],
    createdAt: new Date("2026-01-11")
  }
])
```

## 4. 查询（find）：过滤、投影、排序与分页

### 4.1 基本查询

```js
db.orders.find({ status: "PAID" })
```

### 4.2 投影（只返回需要的字段）

```js
db.orders.find(
  { status: "PAID" },
  { userId: 1, status: 1, createdAt: 1, _id: 0 }
)
```

投影的意义和 SQL 里避免 `SELECT *` 类似：减少网络与解码开销。

### 4.3 常见条件：比较、范围、IN

```js
db.orders.find({ userId: { $gt: 10 } })

db.orders.find({
  createdAt: { $gte: new Date("2026-01-01"), $lt: new Date("2026-02-01") }
})

db.orders.find({ status: { $in: ["PAID", "SHIPPED"] } })
```

### 4.4 AND / OR

MongoDB 默认是 AND：

```js
db.orders.find({ userId: 1, status: "PAID" })
```

OR 用 `$or`：

```js
db.orders.find({
  $or: [
    { status: "PAID" },
    { status: "SHIPPED" }
  ]
})
```

### 4.5 数组与嵌套对象查询

数组里任意元素匹配：

```js
db.orders.find({ "items.productId": 2001 })
```

更精确匹配（同一个数组元素同时满足多个条件）用 `$elemMatch`：

```js
db.orders.find({
  items: { $elemMatch: { productId: 2001, quantity: { $gte: 2 } } }
})
```

### 4.6 排序与分页

```js
db.orders
  .find({ userId: 1 })
  .sort({ createdAt: -1 })
  .limit(20)
  .skip(40)
```

提示：深分页（skip 很大）会变慢。进阶场景更推荐“游标分页”（基于时间或 `_id`）：

```js
db.orders
  .find({ userId: 1, createdAt: { $lt: new Date("2026-01-20") } })
  .sort({ createdAt: -1 })
  .limit(20)
```

## 5. 写入（insert/update/delete）：常见模式与坑

### 5.1 更新：$set / $inc / $push

```js
db.users.updateOne(
  { email: "alice@example.com" },
  { $set: { name: "Alice Chen" } }
)

db.products.updateOne(
  { _id: ObjectId("...") },
  { $inc: { stock: -1 } }
)

db.orders.updateOne(
  { _id: ObjectId("...") },
  { $push: { items: { productId: 3001, quantity: 1, unitPrice: 9.9 } } }
)
```

### 5.2 替换 vs 局部更新

- `replaceOne` 会用新文档替换旧文档（没写的字段会丢）
- `updateOne` 配合 `$set` 是局部更新

初学者常见事故：把“想改一个字段”写成“替换整条文档”，导致数据丢失。

### 5.3 upsert：不存在就插入

```js
db.users.updateOne(
  { email: "alice@example.com" },
  { $set: { name: "Alice", updatedAt: new Date() } },
  { upsert: true }
)
```

## 6. 聚合（Aggregation Pipeline）：MongoDB 的“数据加工流水线”

聚合管道的核心直觉：

- 把数据当成一条条文档
- 依次经过多个阶段（stage）
- 每个阶段输出下一阶段的输入

最常用阶段：

- `$match`：过滤（越早越好）
- `$project`：选择/计算字段
- `$group`：分组聚合
- `$sort` / `$limit`
- `$lookup`：关联（类似 Join）
- `$unwind`：展开数组

### 6.1 统计每个用户订单数

```js
db.orders.aggregate([
  { $match: { status: "PAID" } },
  { $group: { _id: "$userId", orderCount: { $sum: 1 } } },
  { $sort: { orderCount: -1 } }
])
```

### 6.2 计算订单总金额

```js
db.orders.aggregate([
  { $match: { status: "PAID" } },
  {
    $project: {
      userId: 1,
      createdAt: 1,
      totalAmount: {
        $sum: {
          $map: {
            input: "$items",
            as: "it",
            in: { $multiply: ["$$it.quantity", "$$it.unitPrice"] }
          }
        }
      }
    }
  },
  { $sort: { createdAt: -1 } }
])
```

### 6.3 $lookup：跨集合关联

如果你把用户存在 `users` 集合中：

```js
db.orders.aggregate([
  { $match: { status: "PAID" } },
  {
    $lookup: {
      from: "users",
      localField: "userId",
      foreignField: "id",
      as: "user"
    }
  },
  { $unwind: "$user" },
  { $project: { _id: 1, status: 1, createdAt: 1, "user.name": 1 } }
])
```

提示：`$lookup` 很强，但不是免费午餐。高并发 OLTP 场景下，如果关联很重，往往更推荐在建模层做“适度冗余”。

## 7. 索引：让查询变快的核心

### 7.1 创建索引

```js
db.orders.createIndex({ userId: 1, createdAt: -1 })
db.orders.createIndex({ status: 1 })
db.orders.createIndex({ "items.productId": 1 })
```

### 7.2 复合索引与前缀

复合索引 `{ userId: 1, createdAt: -1 }` 通常能同时支持：

- `find({ userId: 1 })`
- `find({ userId: 1 }).sort({ createdAt: -1 })`

设计索引时，把高频查询的 `filter + sort` 当成一个整体来考虑。

### 7.3 唯一索引

```js
db.users.createIndex({ email: 1 }, { unique: true })
```

唯一索引是“数据质量的最后一道防线”。

### 7.4 TTL 索引（自动过期删除）

适合验证码、会话、临时事件等：

```js
db.sessions.createIndex(
  { expiresAt: 1 },
  { expireAfterSeconds: 0 }
)
```

### 7.5 用 explain 观察是否走索引

```js
db.orders
  .find({ userId: 1 })
  .sort({ createdAt: -1 })
  .limit(20)
  .explain("executionStats")
```

关注点：

- 扫描文档数量是否离谱
- 是否出现全表扫描（COLLSCAN）
- 是否能用索引满足排序

## 8. 建模与设计：MongoDB 的“反范式”思维

在关系型数据库里常说“范式化”。在 MongoDB 里更常见的是：

- **嵌入（Embedding）**：把子结构直接放进文档（读快、写一致）
- **引用（Referencing）**：只存引用 ID，需要时再查或 `$lookup`

### 8.1 什么时候适合嵌入？

- 子数据和主数据“强绑定”，经常一起读
- 子数组规模可控（不要无限增长）

例如订单与订单项，经常适合嵌入：订单项天然属于订单。

### 8.2 什么时候适合引用？

- 子数据会无限增长（例如用户的操作日志）
- 子数据需要独立查询与分页
- 共享实体（例如商品信息被很多订单引用）

### 8.3 适度冗余：为了读性能而复制字段

典型做法：在订单里冗余 `userName`、`productName` 的快照字段。

好处：读订单列表不需要关联查询。

代价：字段变更要处理同步策略（通常订单快照不回写）。

## 9. 事务与一致性：MongoDB 也能做事务，但要用对

MongoDB 支持多文档事务（在复制集/分片集群中也可用），但它更适合：

- 必须跨多个文档保持一致的关键路径
- 且事务范围足够小、耗时足够短

直觉：事务会增加锁与资源占用，**不要把它当成默认手段**。

事务示例（概念演示，具体写法依赖驱动）：

```js
// 伪代码：不同语言驱动 API 不同
session.startTransaction()
try {
  orders.updateOne({ _id }, { $set: { status: "PAID" } }, { session })
  wallets.updateOne({ userId }, { $inc: { balance: -amount } }, { session })
  session.commitTransaction()
} catch (e) {
  session.abortTransaction()
}
```

## 10. 高可用与扩展：复制集与分片

### 10.1 复制集（Replica Set）：高可用的基础

复制集通常包含：

- Primary：主节点（写入）
- Secondary：从节点（复制数据，可做读扩展）
- 仲裁/隐藏节点：按需配置

复制集解决的问题：

- 主挂了可以自动选主
- 数据多副本容灾

你需要知道的工程点：

- 读写关注点（read/write concern）决定一致性与性能的权衡
- 如果你把读流量打到 Secondary，要理解“读到旧数据”的可能性

### 10.2 分片（Sharding）：水平扩展

分片把数据按“分片键”拆到多个 shard 上。

核心难点：**选对分片键**。

直觉选择：

- 需要高基数、分布均匀
- 常用于查询条件（否则容易 scatter-gather 扫全集群）
- 避免单调递增导致热点（例如纯时间戳做分片键可能造成写热点）

## 11. 备份与恢复：上线前必须做演练

常见方式：

- 逻辑备份：`mongodump` / `mongorestore`
- 物理/快照备份：云盘快照、存储级快照、备份系统

进阶经验：

- 备份不是“做了就算”，要定期恢复演练
- 明确 RPO/RTO（能丢多少数据、多久能恢复）

---

## 12. 安全：避免“数据库裸奔”

至少做到：

- 开启认证与授权（不要用默认无密码）
- 账号最小权限（只给必要的读写）
- 网络隔离（内网、白名单、VPC）
- 开启 TLS（需要跨网传输时尤其重要）
- 监控审计（访问日志、慢查询、异常登录）

---

## 13. 性能排查：从“感觉慢”到“定位慢”

常用抓手：

- `explain("executionStats")`：看是否 COLLSCAN、扫描量
- 慢查询日志与监控：定位高频慢操作
- 观察索引是否匹配查询与排序

最常见的优化套路：

1. 先用投影减少返回列
2. 把最强过滤放在最前面（`$match` 越早越好）
3. 为高频查询建立复合索引（过滤 + 排序一起考虑）
4. 避免超大文档与无限增长数组（必要时拆分）

---

## 14. 常见坑合集（建议收藏）

- `ObjectId` 当字符串查不到：类型不一致
- 深分页 `skip` 很大变慢：用游标分页
- 数组多条件不用 `$elemMatch` 查错：条件落在不同元素上
- 索引建了但没用上：查询写法与排序不匹配
- “灵活模式”导致字段类型混乱：需要模式约束与数据治理

---

## 15. 学习路线（从入门到实战）

1. 熟练 `find` 的过滤、投影、排序
2. 熟练聚合管道 `$match/$group/$project/$sort`
3. 能根据查询设计复合索引，并用 `explain` 验证
4. 掌握建模：嵌入 vs 引用 vs 冗余
5. 了解复制集、读写一致性与分片键选择
6. 把备份恢复与安全配置跑通
